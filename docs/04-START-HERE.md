# START-HERE：WhyCode 开发指南

> Agent 的常驻入口是根目录 [AGENTS.md](../AGENTS.md)。本文维护详细开发红线、工作流程和文档地图，按任务读取相关章节；环境、验证和 PR 流程见 [CONTRIBUTING.md](../CONTRIBUTING.md)。

## 1. 项目是什么

WhyCode 是一款 Windows 优先的通用桌面 Agent，尤其擅长代码与工程任务，也支持研究、写作、规划、附件和 Office 制品。技术形态为 Electron + React + TypeScript monorepo；核心能力包括多模型接入、安全工具执行、持久会话、上下文压缩、TaskPlan、多 Agent 协商和通用子代理。

项目已经开源但仍处于开发阶段。除非用户以后对已发布数据另行提出要求，**不为旧测试/开发会话编写兼容、迁移、双读或展示兜底**。

## 2. 确定当前事实

产品范围看文档一，实现机制看文档二，精确协议看文档三和对应代码；未竟事项、验证边界和阻塞只看文档五。代码与文档不一致时，结合用户要求、测试和实际行为定位差异，不能直接把缺陷当作新契约。完成日期、commit、测试数量和验收过程留在 Git 历史。

安装与运行见 CONTRIBUTING；修改 Core 后需重启 dev，不能假定 Electron Main 会热载。API key 只由 Main 通过 `safeStorage` 保存，Renderer 不得取回明文。

## 4. 工作规则（必须遵守）

1. **开工**：检查 Git 状态和文档五，按 AGENTS 的任务入口读取相关文档、实现和测试；需要追溯时查看相关文件历史。基于已同步且包含现有有效工作的 main 切分支，或继续适合当前任务的功能分支，保留无关改动。
2. **开发**：代码修改先读 §5.1；涉及 Renderer/UI 时再读 §5.2 与文档二 §12 的相关小节。新能力或架构决策先调研，优先参考 Claude Code、开源 Codex CLI，并用 DSH 等相关实现交叉验证；普通修复先查本仓库的契约和测试，不重复研究无关项目。不确定事实先查证；仍缺产品决策或必要信息时向用户澄清，不能凭空补全。
3. **专项工作流**：只在任务命中时读取对应项目 Skill。新增、替换、退役或审核模型，以及同步 CLIProxyAPI 路由时，必须先完整读取 `.agents/skills/whycode-model-catalog/SKILL.md`。
4. **收工（每次任务结束前，缺一不可）**：
   - 只把仍未完成、待验证、受阻和下一步写入 `05-暂存区便签.md`；已经完成的过程不要留下；
   - 新增或改变了稳定产品事实时更新文档一，改变架构/生命周期时更新文档二，改变模型或协议契约时更新文档三；
   - 只检查本次影响到的文档与引用，保持单一权威来源，不为“显得有更新”而改文档；
   - 阶段性停止且存在明确的未来方向时，把非承诺方向、触发条件和前置依赖写入文档一，不伪装成进行中事项；
   - 按 CONTRIBUTING 选择本地验证并整理提交，报告实际结果及未测边界。
5. **git**：功能分支通过 PR 和 CI 进入 main；推送、验收合并及分支清理遵守 CONTRIBUTING 的职责分工。禁止提交密钥、构建产物、node_modules、scratch 文件或外部参考项目源码。
6. **文档写入原则**：先判断归属再写。同一稳定事实只保留一个详细来源，其它文档只链接；当前视角写“现在是什么”，不记录“当时怎么改”；Git 历史承担完成历史，便签承担短期交接。

## 5. 开发质量红线（所有模型必须遵守）

### 5.1 通用代码红线

1. **先找后写**：写新函数/组件前先搜同类实现，能复用或扩展就不新建；发现重复立即合并。
2. **不为未来写代码**：只实现当前模块需要的；“以后可能用”的抽象、配置项和参数一律不写。接口预留仅限正式需求明确要求的边界。
3. **删胜于加**：改动导致旧代码无用时同步删除；禁止注释掉留着，禁止 `xxx-old` / `xxx-v2` 并存。
4. **行数是审查触发线，不是机械上限**：单文件约 300 行、单函数约 50 行时重点检查职责与可读性；能拆且更清晰就拆，内聚逻辑拆开反而增加跳转时可保留。禁止为了凑行数做碎片化拆分，也禁止借此向大文件无节制堆逻辑。
5. **依赖最小，不重复造轮子**：新增 npm 包必须先说明为什么现有依赖做不到，将仍影响后续维护的理由记录在所属架构章节，未决事项写入便签；成熟基础能力不得仅为少一个依赖而自行实现，除非能证明自研在安全、维护和测试上更可控。
6. **注释只写“为什么”**：不写翻译代码行为的注释，不留 `console.log` 等调试残留。
7. **每次收工自查**：本次改动有没有让任何文件更难读；有就当场清理，不留给下一个模型。
8. **治因不治症，禁止补丁式堆叠**：修改前先定位根因和现有职责边界，默认直接修正产生问题的逻辑；不得用外围特判、重复校验、兜底或补偿流程掩盖本可修复的根因。优先复用、调整或删除现有代码；现有数据与控制流足够时，不新增中间结构、状态字段、计数器、缓存、标志位或抽象层。确因兼容性、外部依赖、线上止血或职责边界无法直接修复时才可采用补丁，并必须说明原因、边界和后续处理，且不得形成第二套业务逻辑。
9. **开发期旧对话不做兼容**：已有测试/开发会话可以随实现演进失效；禁止为继续读取旧对话增加 schema 默认值、迁移器、旧事件分支、双格式解析或展示兜底。只有用户以后对已发布数据明确提出兼容要求时才重新设计迁移边界。
10. **产物干净、用户可控**：WhyCode 生成或管理的持久产物必须有明确的归属、存储位置、生命周期和完整清理入口，让用户可主动恢复干净状态。新增或修改相关能力时，清理须与创建一并设计并验证，覆盖本地与远端的工作目录、组件、同步副本、临时文件及缓存等；清理前说明删除与保留范围，完整清理时先停止相关写入并释放资源，再删除所属产物。不得误删用户原有文件或未授权的共享数据；部分失败须如实提示、保留重试入口，不能假报成功或留下用户无法管理的残留。
11. **校验守住真实边界**：模型输入、IPC、持久文件、进程和网络输入在所属入口校验，未知模型能力、权限、路径、网络目标或恢复状态不放行；同进程已验证的类型化调用不重复构造校验或兜底，不能根据名称或偶然成功推断能力。

### 5.2 前端开发附加红线（涉及 Renderer/UI 时必须遵守）

1. **唯一基线**：动工前阅读文档二 §12 中与改动有关的信息架构、视觉和交互规则；浏览器、终端、文件预览、Git 等专项小节按影响面读取。基线只在那里维护，不在需求或便签复制第二份。
2. **复用现有原语**：优先使用既有 Radix 菜单、选择器、共享 tokens 与布局组件；禁止原生 `select`、一次性下拉框、平行弹窗体系或组件内散落同义尺寸。
3. **克制分层**：以 Codex 式极简为主体；卡片只表达明确分组，工具、正文和主时间线不得被装饰化，不能靠高饱和颜色或过量留白制造层次。
4. **性能边界**：手绘/纹理效果只能使用可缓存静态资源和背景伪元素；禁止 turbulence、实时 filter、Canvas/逐帧 JS、非状态反馈型持续动画或对正文容器整体变换。hover 只能复用全局有界 transition，不得常驻 `will-change`。
5. **响应式与可用性**：每次界面改动都要检查窄窗口、长文本、焦点、键盘/IME、菜单清晰度和内容溢出；自动收起不得覆盖用户主动开合状态，关键模型/任务状态必须保持可见。
6. **不越过前端职责**：纯界面任务不得顺带改 Core、IPC、JSONL、会话 schema 或权限语义；确有需要时先单独设计并取得用户确认。旧组件失去职责后同步删除，不保留旧 UI、双路径或开发期兼容分支。

## 6. 异步资源与错误处理

修改异步、取消、后台任务、进程、浏览器或清理逻辑时，结合所属模块契约检查：

1. **真实所有者**：明确资源属于会话、turn、窗口、应用还是共享连接。UI 挂载或当前选中会话不能替代后台生命周期；同一操作的事实由一个拥有者维护，不增加镜像状态。
2. **等待释放完成**：发出 abort、kill 或关闭请求不等于工作已经停止。按依赖顺序阻止迟到回调继续发布状态，取消任务并等待退出，再释放所属资源；保留分别承担取消、回滚和终态结算的必要机制。
3. **提交后发布**：成功提交后再发布对应事实，UI、查询和恢复使用同一来源；快照与实时事件必须能在明确边界接续。临时进度不得伪装为已提交结果。
4. **失败有归属**：用明确类型或稳定状态区分可预期错误，保留 cause，不解析展示文案分支。说明错误由谁处理、效果是未发生、部分完成、已提交还是未知，以及何时可以重试。
5. **捕获不等于恢复**：取消和异步拒绝须在拥有者处收束，避免未处理异常；不能吞错后报成功。无法确认状态安全时停止依赖操作并如实反馈。重试只用于可安全重复的操作，须可取消且有明确预算。

验证实际状态、用户可见结果与资源释放，不能只断言异常被捕获或函数返回成功。测试选择与真实入口要求统一见 [CONTRIBUTING](../CONTRIBUTING.md#验证规则)。
