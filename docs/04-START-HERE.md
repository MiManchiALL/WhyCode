# START-HERE：参与 WhyCode 开发必读

> 这是唯一入口文档。先读本文，再按文档地图进入当前模块；不要把本文扩写成完成日志或架构百科。

## 1. 项目是什么

WhyCode 是一款 Windows 优先的通用桌面 Agent，尤其擅长代码与工程任务，也支持研究、写作、规划、附件和 Office 制品。技术形态为 Electron + React + TypeScript monorepo；核心能力包括多模型接入、安全工具执行、持久会话、上下文压缩、TaskPlan、多 Agent 协商和通用子代理。

项目已经开源但仍处于开发阶段。除非用户以后对已发布数据另行提出要求，**不为旧测试/开发会话编写兼容、迁移、双读或展示兜底**。

## 2. 当前状态

- 主链路已具备完整 Main Agent、权限/审批、Local/managed/Worktree、会话持久化与 Fork、上下文压缩、TaskPlan、协商与子代理。
- 工具范围已覆盖文件、搜索、命令与后台唤醒、网页、MCP、图片/截图、PDF、Office 和 Skill。
- Desktop 已形成统一会话侧栏、中央时间线、上下文用量、会话定位轨、输入框以及环境/子代理/任务计划侧栏。
- 当前开发应以代码和 `01`～`03` 的现状契约为准；本轮未竟事项、验证边界和阻塞只看 `05-暂存区便签.md`。
- 安装与运行：项目依赖自包含于仓库相关缓存，通常执行 `pnpm install`、`pnpm dev`；修改 Core 后需重启 dev，不能假定 Electron Main 会热载。
- API key 只由 Electron Main 通过 `safeStorage` 保存；Renderer 永远不得取回明文密钥。

只有整体阶段、当前开发焦点或开工入口发生变化时才更新本节。单个功能的完成日期、commit、测试数量和客户端验收记录只留在 Git 历史。

## 4. 工作规则（必须遵守）

1. **开工**：读本文 → 读 `05-暂存区便签.md` → 读当前模块相关文档 → `git log --oneline -10` 了解最近变更 → 基于最新 main 切/续 feature 分支。
2. **开发**：遵守本文质量红线和文档二的工程约束；涉及 Renderer/UI 时，动工前必须完整阅读本文 §5.2 与文档二 §12。每个模块先调研再决定再动工，**以 Claude Code 与开源的 Codex CLI 为主要设计参考，再用主流开源 Agent 交叉验证**，但不照搬任何一方；不清楚的**不许猜**，记入便签并询问用户。
3. **收工（每次任务结束前，缺一不可）**：
   - 只把仍未完成、待验证、受阻和下一步写入 `05-暂存区便签.md`；已经完成的过程不要留下；
   - 新增或改变了稳定产品事实时更新文档一，改变架构/生命周期时更新文档二，改变模型或协议契约时更新文档三；
   - 只有整体阶段或当前开发焦点变化时才更新本文 §2；
   - 检查五份文档是否确有过时内容，保持单一权威来源，不为“显得有更新”而改文档；
   - 阶段性停止且存在明确的未来方向时，把非承诺方向、触发条件和前置依赖写入文档一，不伪装成进行中事项；
   - 提交 commit，信息用中文并准确说明结果。
4. **git**：main 只放验证跑通的代码与最新文档；功能分支合并后删除；模块差不多完成时询问用户是否合并。禁止提交密钥、构建产物、node_modules、scratch 文件或外部参考项目源码。
5. **文档写入原则**：先判断归属再写。同一稳定事实只保留一个详细来源，其它文档只链接；当前视角写“现在是什么”，不记录“当时怎么改”；Git 历史承担完成历史，便签承担短期交接。

## 5. 开发质量红线（所有模型必须遵守）

### 5.1 通用代码红线

1. **先找后写**：写新函数/组件前先搜同类实现，能复用或扩展就不新建；发现重复立即合并。
2. **不为未来写代码**：只实现当前模块需要的；“以后可能用”的抽象、配置项和参数一律不写。接口预留仅限正式需求明确要求的边界。
3. **删胜于加**：改动导致旧代码无用时同步删除；禁止注释掉留着，禁止 `xxx-old` / `xxx-v2` 并存。
4. **行数是审查触发线，不是机械上限**：单文件约 300 行、单函数约 50 行时重点检查职责与可读性；能拆且更清晰就拆，内聚逻辑拆开反而增加跳转时可保留。禁止为了凑行数做碎片化拆分，也禁止借此向大文件无节制堆逻辑。
5. **依赖最小，不重复造轮子**：新增 npm 包必须先说明为什么现有依赖做不到，并记入便签；成熟基础能力不得仅为少一个依赖而自行实现，除非能证明自研在安全、维护和测试上更可控。
6. **注释只写“为什么”**：不写翻译代码行为的注释，不留 `console.log` 等调试残留。
7. **每次收工自查**：本次改动有没有让任何文件更难读；有就当场清理，不留给下一个模型。
8. **治因不治症，禁止补丁式堆叠**：修改前先定位根因和现有职责边界，默认直接修正产生问题的逻辑；不得用外围特判、重复校验、兜底或补偿流程掩盖本可修复的根因。优先复用、调整或删除现有代码；现有数据与控制流足够时，不新增中间结构、状态字段、计数器、缓存、标志位或抽象层。确因兼容性、外部依赖、线上止血或职责边界无法直接修复时才可采用补丁，并必须说明原因、边界和后续处理，且不得形成第二套业务逻辑。
9. **开发期旧对话不做兼容**：已有测试/开发会话可以随实现演进失效；禁止为继续读取旧对话增加 schema 默认值、迁移器、旧事件分支、双格式解析或展示兜底。只有用户以后对已发布数据明确提出兼容要求时才重新设计迁移边界。

### 5.2 前端开发附加红线（涉及 Renderer/UI 时必须遵守）

1. **唯一基线**：动工前完整阅读文档二 §12；信息架构、视觉参数和组件用法只在那里维护，不在需求或便签复制第二份。
2. **复用现有原语**：优先使用既有 Radix 菜单、选择器、共享 tokens 与布局组件；禁止原生 `select`、一次性下拉框、平行弹窗体系或组件内散落同义尺寸。
3. **克制分层**：以 Codex 式极简为主体；卡片只表达明确分组，工具、正文和主时间线不得被装饰化，不能靠高饱和颜色或过量留白制造层次。
4. **性能边界**：手绘/纹理效果只能使用可缓存静态资源和背景伪元素；禁止 turbulence、实时 filter、Canvas/逐帧 JS、非状态反馈型持续动画或对正文容器整体变换。hover 只能复用全局有界 transition，不得常驻 `will-change`。
5. **响应式与可用性**：每次界面改动都要检查窄窗口、长文本、焦点、键盘/IME、菜单清晰度和内容溢出；自动收起不得覆盖用户主动开合状态，关键模型/任务状态必须保持可见。
6. **不越过前端职责**：纯界面任务不得顺带改 Core、IPC、JSONL、会话 schema 或权限语义；确有需要时先单独设计并取得用户确认。旧组件失去职责后同步删除，不保留旧 UI、双路径或开发期兼容分支。

## 6. 模型目录更新规范（新增、替换或退役模型时必须遵守）

1. **先取得一手契约，再改厂商目录**：以厂商当前官方模型页、API/迁移/弃用文档为主，记录核对日期；至少确认正式 API ID、稳定/预览状态和生命周期、输入输出模态、流式与工具调用、结构化输出、上下文/最大输出、缓存、推理内容形态、可调推理档位及默认值、协议端点和必须回传的 provider metadata。还要核对当前 AI SDK 能否无损表达这些字段；官方没有证明的能力一律不猜，不因名称相近继承。
2. **先明确“保留还是替换”**：保留表示新旧型号各有独立画像和测试；替换表示从活动目录、注册表、默认配置、设置页、测试和正式文档中完整删除旧型号，不保留跨版本别名、隐藏兼容分支或第二套 providerOptions。厂商迁移建议不等于 WhyCode 自动迁移：除非用户明确要求，旧会话的 `modelId` 不重写，对话和附件不删除。
3. **退役历史可读、不可静默换模**：同一当前可恢复 schema 内，历史会话即使引用已退役型号也必须能够打开并完整展示；顶栏保留该会话最后使用的原型号名并以红色“已停止支持”显示，下拉框不伪造选中项。发送前由 Main 的当前模型解析边界明确要求用户主动选择现有型号。禁止偷偷回退默认模型、改写 JSONL，或把旧版本 ID 当作新版本别名；用户明确切换后只更新当前会话，不能连带改写其它历史会话。退役显示名属于引用型历史元数据：只为最后仍选择该型号的会话保留；会话删除必须在事实源删除前按其余会话引用清理，不能留下孤儿配置，也不能误删其它会话仍需的名称。
4. **保持单一事实源并同步删除旧代码**：`providers/catalog.ts` 只维护厂商型号的精确 ID 与官方固有画像，`registry.ts` 只维护协议工厂；UI、Main 和 Provider 不复制能力表。CLIProxyAPI 只在既有兼容目录中保存每条审核路由的最小约束，由唯一合成函数产生有效画像，不另建完整 CLI 模型注册表。不得按版本号散落 `if/else`、保留任意型号兜底、复制整份能力对象或增加平行 providerOptions。更新造成的常量、类型、IPC、配置字段、测试夹具和说明失效时同步删除；一次性旧配置迁移只能保留历史显示所需的最小数据，不能复活旧运行时逻辑。
5. **厂商目录与 CLIProxyAPI 分阶段更新**：阶段 A 新增、替换或退役厂商型号时，先按第 1～4 条完成并记录完整厂商画像，只更新内置厂商，`cli-proxy-models.ts` 保持不动；CLIProxyAPI 尚无权威同型号路由契约时，该型号不得出现在 CLIProxyAPI 可启用列表。阶段 B 只有用户明确说明“内置厂商已更新，现在更新 CLIProxyAPI 的某型号”时才开始：若既有厂商画像仍是当前契约，直接复用，只补查当前 CLIProxyAPI 发布版及源码、`internal/registry/model_updater.go` 指向的官方远程目录与对应提交、内嵌离线目录、Provider/客户端专用元数据、启动边界、OAuth 别名、入口协议、推理参数翻译和账号限制；厂商契约已变化时只刷新受影响事实。候选必须由官方内嵌或远程目录证明指向同一真实型号，再与目标实例鉴权后的标准 `/v1/models` 求交集；后者通常只可靠提供 ID 和可用性，不能据此动态生成画像。不能只搜二进制内嵌表，也不能把路由名称、可响应或模型自述单独当作型号身份证据。路由名可以不同，但旧版、近似名和未审核 alias 不能冒充新型号。CLIProxyAPI 的常规同步范围只包括 OpenAI、Anthropic 与 Gemini，并且每次只更新用户当轮明确点名的其中型号；同一请求还点名其它厂商的内置型号，不代表它也应接入 CLIProxyAPI。
6. **CLI 路由能力必须按字段合成，不能整份继承或普通覆盖**：型号身份、官方说明及知识边界以厂商画像为准；上下文/输出取厂商与路由上限的较小值，推理档位取交集，路由明确给出的闭集缺项不能从厂商补回，显式 `false` 优先且 CLI 数据不得反向开启厂商画像未验证的能力。缺失只表示未知：只有已审核同型号且确认该字段由路由完整透传时才能继承，否则关闭或暂不接入。路由独立默认值必须记录；模型名中的 low/high 可以表示路由默认，但不能代替请求体档位。同一 ID 若可能由多个 OAuth Provider 提供而标准 `/models` 无法区分，取所有可能路由的安全交集，无法得到可靠交集时拆分或不开放。`supported_parameters`、输入模态和推理档位是不同字段，不能互相推断；Codex `ultra` 等包含运行时编排语义的产品模式不得冒充通用 API 推理强度。审核结果固定随 WhyCode 发布，应用启动时不从可变 GitHub 目录拼装画像。
7. **推理强度按“会话选择 → 当前连接有效画像 → 协议翻译”处理**：内置目录逐型号声明厂商档位和默认值，CLI 连接再按第 6 条收窄；UI 只展示当前连接真实档位，内部 `default` 映射为该连接默认显示，没有可验证档位时固定灰色“推理：默认”。选择与连接限定 `modelId` 一起属于会话事实，切换模型时回到 default；模型或路由升级后，旧选择若不在新闭集中，恢复和发送边界归一到当前连接 default，绝不能继续发送非法值。Provider 按实际协议翻译为 Responses `reasoning.effort`、OpenAI Chat `reasoning_effort`、Anthropic adaptive thinking + `output_config.effort`；内置中转和 CLIProxyAPI 共用这条链路，禁止通过 UI 或模型名括号后缀控制。
8. **更新必须验证完整链路**：至少覆盖厂商目录/注册表与设置快照、CLIProxyAPI 审核候选、逐路由能力约束和目标实例 `/models` 解析、官方与 CLI 同型号互不污染、上下文上限进入自动压缩、档位交集/默认值/非法旧选择归一、实际路由 ID 和三种协议请求线格式、推理签名/摘要的后续工具轮次回传、图片/工具/结构化输出边界、只显示已配置连接、模型切换与重启恢复、旧配置迁移、已退役模型历史打开/切换/删除和发送拦截；随后运行受影响测试、全仓 typecheck、生产 build、`git diff --check` 和密钥/旧型号/死代码检查。能做真实端点烟测时关闭自动重试并把结论记入便签；未做或因无 key 不能做必须如实标明，不能把离线适配器测试写成真实模型验收。
