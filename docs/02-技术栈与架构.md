# WhyCode 技术栈与系统架构

> 本文是 WhyCode 当前实现的架构说明：负责模块边界、生命周期、数据流和工程约束，不记录提交历史、测试次数或开发过程。精确的模型可见消息、工具参数和持久化协议见 `03-Agent与协议契约.md`；具体类型与 schema 仍以对应代码单源为准。

## 1. 技术栈与运行形态

- **桌面宿主**：Electron，Windows 优先。
- **语言与构建**：TypeScript、Node.js 22+、pnpm monorepo、electron-vite。
- **Renderer**：React、Tailwind CSS、Radix UI、Lucide、Streamdown、KaTeX。
- **模型接入**：AI SDK 适配层加 WhyCode 自有 Provider 能力画像。
- **运行时校验**：Zod；模型、IPC、JSONL 和工具边界均 fail-closed。
- **持久化**：append-only JSONL 会话事实源；偏好、密钥和受管资源由 Desktop Main 分别管理。
- **测试**：Vitest；根命令为 `pnpm test`、`pnpm typecheck`、`pnpm build`。

进程职责：

```text
Renderer (React)
  │ typed IPC
  ▼
Electron Main ── OS / filesystem / safeStorage / processes / windows
  │ host adapters
  ▼
Core ── Agent / protocol / permissions / context / session semantics
  │
  ├─ Provider APIs
  ├─ MCP / Web
  └─ Utility Process / workers for bounded heavy work
```

### 1.1 强制边界

1. `packages/core` 不依赖 Electron、DOM 或 Renderer；测试中可独立运行。
2. Renderer 不直接读取密钥、会话文件、项目文件或子进程；它只消费 Main 投影的状态与事件。
3. Main 负责 OS 能力与资源所有权，但不复制 Core 的 Agent、权限或协议判断。
4. 同一事实只有一个权威来源。UI 派生状态、缓存和摘要不能反向成为业务事实源。
5. CPU/内存明显的解析、渲染和转换不得阻塞 Electron Main；使用有界 worker 或 Utility Process。

## 3. Agent 与事件生命周期

### 3.1 AgentSession

`packages/core/src/agent/session.ts` 是普通 Main 的执行入口。一个用户 turn 在开始时冻结当前连接、模型、推理强度、权限与可用工具，之后的工具续轮始终使用同一快照；用户在运行中修改设置只影响下一 turn。

Main 不设置固定总模型步骤上限。停止条件来自自然完成、用户停止、需要用户回答、后台等待、Provider/协议错误、上下文边界和通用循环健康保护。B/C 协议回合仍有协议级上限；子代理 activation 不设固定步骤数，但服从相同的取消、超时、重复调用熔断、上下文和权限边界。

每个模型步骤是事务：

1. 基于已提交活动上下文发起模型请求。
2. 流式事件只进入当前步骤缓冲。
3. 工具参数完整后统一校验、授权并执行。
4. 步骤只有在完整且可交付时才提交；失败、取消或不可交付协议串整体丢弃并恢复视图快照。
5. 已提交工具不会因后续空响应或协议修复而重放。

相同工具及等价参数连续重复三次触发通用循环熔断。模型流连续 120 秒没有任何数据则超时；长命令本身使用命令生命周期，不占用模型流超时。

### 3.2 过程与最终正文

Renderer 不根据模型名、措辞、时间或“当前只看到文本”预测未来。模型步骤提交后才分类：

- 该步骤包含工具调用：正文属于执行过程，保持既有展开状态。
- 该步骤没有工具且有可交付正文：正文是最终回答，过程按统一规则收起。
- `AskUserQuestion` 是工具调用，不是最终回答；等待卡出现时执行过程保持展开。

用户主动停止时，尚未提交 step 中已经显示的正文仍属于执行过程：过程保持展开，只把末尾尚未封口的工具批次折叠成摘要。只有已经通过 `step-committed` 确认的纯文本最终回答才保持收起；不能根据中止瞬间“尚未看到工具”推测正文已经进入最终回答。手动开合属于当前进程内的视图状态，不改变 transcript。

运行中用户输入仅进入排队状态时不封口工具批次；只有消息在稳定边界正式注入、真实 user message 进入时间线后，才封口此前的末批工具。重新编辑或丢弃排队消息不会改变工具展示。封口只改变工具批次投影，不收起整个执行过程，也不改写原始 Block 顺序。

### 3.3 Steering、停止与后台续轮

- 运行中的用户输入按真实 user message 在稳定步骤边界注入，不用关键词猜意图。
- 排队消息以稳定输入 ID 为单位操作：重新编辑会安全退回草稿，丢弃会从 canonical pending inputs 移除，立即发送复用 urgent steering；三个动作都与当前步骤注入竞争保持原子。
- 用户 Stop 终止当前 runLoop；未提交的推理、工具与计划变化不能进入模型历史。
- `RunCommand` 默认在当前工具步骤前台等待；必须跨回合继续运行的进程只有显式 `runInBackground=true` 才交给宿主后台管理并投影到 Header。只有同时设置 `wakeOnCompletion=true` 的任务会在自然完成或失败后通知并续接原会话。
- 后台任务、子代理、审批和命令都以 sessionId 绑定，切换 UI 会话不会转移所有权。

### 3.4 CoreEvent 与 ViewEvent

CoreEvent 是运行时与持久化的稳定语义事件；ViewEvent 是从已提交事实派生的用户可见投影。新增事件必须同时回答：

- 是否进入模型上下文；
- 是否写入 JSONL；
- 恢复时如何重放；
- Fork/压缩/回滚是否复制；
- Renderer 是否展示；
- 中止时是否保留。

流式 delta 不应制造大量 React 长生命周期对象。Desktop 先按相邻同类事件合并并以 `requestAnimationFrame` 有界刷新；步骤提交、丢弃、工具边界和会话切换立即冲刷缓冲。

## 4. Provider 与模型目录

### 4.1 单一能力画像

- `packages/core/src/providers/catalog.ts` 保存内置厂商的精确模型 ID 与官方固有画像。
- `packages/core/src/providers/registry.ts` 保存协议工厂，不复制能力表。
- CLIProxyAPI 的审核路由约束集中在 Desktop 的兼容目录中，并由唯一合成函数与厂商画像取安全交集。
- Renderer、Main、自动压缩和工具注册都消费同一有效画像，不各自猜测能力。

能力包括上下文/输出上限、输入模态、工具调用、结构化输出、推理展示与可选强度等。未知字段不是支持；CLI 路由不能反向开启厂商未验证能力。

标准 `/models` 只证明当前实例公布某个 ID，不证明该 ID 的完整能力。实例目录与静态审核候选求交集后才能供用户选择；目录读取失败不得凭旧名称动态创造型号。

### 4.2 请求隔离与密钥

- 内置厂商、CLIProxyAPI 和搜索服务的密钥由 Electron `safeStorage` 分别加密；Renderer 只接收 `hasKey`。
- 同一 AgentSession 使用稳定且唯一的 `transportSessionId`，不同会话不得复用。CLIProxyAPI 映射为传输 header，官方直连可忽略；该 ID 不写入消息、摘要或可见正文。
- Provider 将各厂商流统一成 Core 事件，并负责工具调用、推理内容和 provider metadata 的后续轮次回传。

模型目录的新增、替换、退役和 CLIProxyAPI 路由维护必须遵守 `.agents/skills/whycode-model-catalog/SKILL.md`。

## 5. 工具、权限与检查点

### 5.1 工具注册

普通 Main 获得稳定完整的基础工具目录；工具不会按自然语言类别或 TaskPlanState 动态增删。角色、Provider 能力和宿主能力可以物理移除不适用工具：B/C、协议回合、子代理和非视觉模型各自使用明确白名单。

每个工具由以下部分组成：

- 稳定名称与 Zod 输入 schema；
- 与实现同目录的精简说明；
- 权限与副作用分类；
- Core handler 和可选 Desktop host adapter；
- 结构化成功/错误结果；
- 与模型无关的测试。

精确参数见 `03-Agent与协议契约.md` §3，代码单源为 `packages/core/src/tools/` 及各工具目录。

### 5.2 文件和命令职责

- 读取、创建、修改、删除和移动明确文件分别使用专用工具，即使目标在项目外；权限层处理越界审批。
- 已有文本优先 `EditFile`，新建或确需整文件重写才用 `WriteFile`。
- `RunCommand` 不冒充文件编辑器，也不提供文件回滚；命令产生的任意副作用必须由用户意图与权限覆盖。
- 普通 Main 的 `RunCommand` 是唯一命令入口：前台分支随当前 turn 取消且不登记后台任务；显式后台分支复用宿主命令管理器并投影到 Header，其中仅 `wakeOnCompletion=true` 的运行任务显示铃铛并登记终态续轮。子代理和讨论 Agent 只获得同名的前台 schema。
- `ListDir`、`Glob`、`Grep`、`ReadFile` 有分页、大小和并发边界；本地搜索优先 ripgrep，缺失时才使用有界回退。

### 5.3 权限

权限引擎同时检查模式、工具副作用、目标路径、当前工作区、会话 scratch 和阶段角色。审批只扩大当前被列出的精确调用，不改变基础模式，也不能越过只读硬边界。

同一模型步骤并行产生的待审批调用合并成一张精确清单；一次批准/拒绝只覆盖该清单。批准后及真正执行前再次用最新权限重查。项目副作用串行执行，读取可在无依赖时并行。

讨论档允许 Main/B/C 读取项目并在各自 scratch 内写入或执行，禁止修改原项目、提交或产生外部副作用。子代理继承父权限后只能收窄，不能借画像、prompt 或工具参数扩大。

### 5.4 检查点

文件工具在写入前建立精确资源检查点：保存目标、旧字节和事务归属；回滚时先检测当前内容冲突，禁止覆盖用户或其它任务的新改动。同一用户轮次即使包含多个内部检查点，UI 只展示一个“回滚本轮”入口。

检查点和对话恢复是两个范围：用户可只恢复文件，也可恢复文件与会话状态。`RunCommand` 不扫描整个工作区建立隐式快照。

## 6. 上下文与指令

### 6.1 请求组成

一次普通 Main 请求由以下稳定层次组成：

1. 会话创建时冻结的 System；
2. 当前项目指令消息；
3. 当前根任务冻结的 Skill 目录；
4. 活动消息历史或 compact summary + 原始尾部；
5. 当前运行态提醒、TaskPlanState、当前 turn 子代理状态、Skill 正文和最新用户/工具内容。

动态时间、计划、权限、目录和进度不得拼进 System。精确消息顺序与缓存规则见 `03-Agent与协议契约.md` §1。

### 6.2 项目指令与自定义 System

`packages/core/src/instructions/` 发现全局 `~/.whycode/AGENTS.md`，再从最近 Git 根到当前目录按层读取项目规则；每层 `AGENTS.override.md` 优先于 `AGENTS.md`。合并消息有内容哈希、总预算和 append-only 审计事件，文件变化时只保留一个活动版本。

高级用户可通过 `~/.whycode/system-prompt.json` 与正文文件为新会话选择 off/append/replace。快照只在会话第一次请求前读取一次并固化；当前会话切模型、压缩或恢复都不重读。

### 6.3 压缩

自动与手动压缩共享一个入口：

1. 对白名单内可重现工具结果执行幂等 microcompact，用稳定占位替换大结果。
2. 需要 full compact 时按 token 预算保留约 20k 的安全原始尾部；切点只能落在安全 user/assistant 边界，tool call/result 不拆。
3. 尾部已包含一个完整用户任务时，只对更早历史生成九节结构化历史摘要。
4. 尾部仍处于同一超长 turn 时，另为该 turn 前缀生成“原始请求、早期进展、后续所需上下文”摘要。
5. 重建时重新注入当前项目指令、Skill 投影和 canonical TaskPlanState。

自动压缩在同一 turn 内按压力检查点触发；不能等 turn 结束后才压缩。摘要不复述完整 Skill 或把已中断请求伪造成当前待办。实现见 `packages/core/src/context/`，摘要契约见 `03-Agent与协议契约.md` §4。

## 7. 会话、工作区与 Fork

### 7.1 会话事实源

每个会话有独立 append-only JSONL。恢复时先验证事件顺序和 schema，再分别重建模型活动消息、用户可见 ViewEvent、TaskPlanState、附件引用、模型选择与运行恢复事实。Renderer 缓存不是恢复来源。

当前开发阶段 schema 可以直接升级；不添加旧事件默认值、双格式读取或迁移器。损坏或不支持的会话应明确失败，仍可由用户删除。

删除会话先在事实源写删除意图并阻止新工作，然后分阶段停止运行时、释放资源和定向删除其受管目录。较大的 Worktree 清理在后台进行，不能锁死其它会话或 Renderer；当前被删会话先切换到可用页面。

### 7.2 工作区模式

| 模式 | 项目/交付目录 | 会话删除 | Fork |
|---|---|---|---|
| Local | 用户选择的真实目录 | 不删除用户目录 | 继续引用同一目录 |
| Worktree | WhyCode 管理的 Git worktree | 后台定向移除 worktree | 延续同一受管工作树语义 |
| managed | `Documents/WhyCode Workspace/<sessionId>` 独占目录 | 定向删除 | 复制点击边界的独立目录快照 |

所有模式都拥有 `userData/scratch/<sessionId>/Main/`。协商使用同一会话树下的任务/角色目录；子代理使用 `subagents/<subagentId>/`。scratch 随恢复和后台唤醒保留，删除会话时定向清理，启动时只回收没有会话事实的孤儿。

### 7.3 Fork

Fork 只锚定完整、已提交且有非空最终正文的模型 turn。Core 从源会话活动父链复制当时真实模型上下文和持久状态，不用 UI 消息重建，也不让模型重新总结。

新会话具有新的 sessionId、JSONL、运行时、附件/检查点副本和 scratch 快照；源会话不变。后台命令、自动唤醒、临时审批记忆和项目 MCP 临时信任仍归来源，不转移。血缘只用于来源展示、命名和诊断，不形成共享运行时。

### 7.4 BTW 侧对话

BTW 使用独立的 `btw-input` / `btw-response` canonical JSONL 事实。它们参与用户可见时间线、附件引用、Fork 文件重定位和重启恢复，但不参与 Main 活动消息、压缩或 TaskPlan。每次请求读取 Main 的稳定消息快照；BBTW 额外拼入同一侧链此前已提交的问答，停止轮次同时带入已有回复片段与标准中断标记。每条已发送侧输入占一轮，整条链最多三轮，运行结束后不修改 AgentSession 的 Main messages。

Desktop 让 BTW 与普通消息共用会话 FIFO 和运行名额；用户停止只终止当前生成并保留侧链，普通消息或新的 BTW 才切换输入语境。最新侧消息可按同一 `conversationId` 与 `turnIndex` 原位编辑重发，旧回复从活动投影移除且不增加轮次。流式事件仅借用有界时间线缓冲支持切换会话，终态由 canonical 事实统一恢复，不能再落一份 ViewEvent 副本。

已结束的 BTW 侧链只在下一条用户消息出现并确认不再续接时折叠，三轮额度用完本身不触发折叠。对话轨继续保留侧链中每轮的独立锚点：展开时定位原消息，折叠时统一定位到该侧链摘要。

## 8. TaskPlan

`packages/core/src/tasks/` 维护唯一当前 `TaskPlanState`，不保存历史计划。普通 Main 始终注册 `CreateTaskPlan`、`ResumeTaskPlan`、`UpdateTaskItem`、`CloseTaskPlan`：

- 初始计划只包含 3～7 个宏观、结果导向里程碑，最后一项是唯一验证里程碑。
- 进入某项前先标记 `in_progress`，再读取相关代码并直接实施；详细操作步骤不进入计划菜单。
- `UpdateTaskItem` 负责增加、删除、修改、重排和状态推进；结构变化原子提交。
- 正常完整最终正文在同一步自动关闭计划；用户停止、等待回答、明确暂缓或等待后台/子代理终态时保留。
- 新 turn 不继承上个 turn 的 engaged 权限。需要继续时按状态 Resume；明确放弃/切换目标时 Close 后重新扫描并 Create。
- 计划工具的每个结果都携带最新 canonical TaskPlanState；压缩和恢复从权威状态重新注入。

精确字段、状态转换和 `AskUserQuestion` 续接规则见 `03-Agent与协议契约.md` §5。

## 9. 多 Agent

### 9.1 协商

`packages/core/src/consensus/` 实现 main-only、quick-review、full-consensus。候选和投票通过 `SubmitProtocolOutput` 合成工具提交并经动态 Zod schema 校验；Agent ID、轮次和 candidate ID 由 Orchestrator 分配。

B/C 以独立受限会话工作，拥有各自 scratch 和跨任务压缩记忆；它们不接收图片、PDF、Skill、MCP、TaskPlan 或项目写权限。协议成功提交即结束该协议 turn，普通协议正文不进入用户最终回答。最终执行仍回到 Main。

协议原文位于仓库外 `E:\Agent\multi-agent-decision-protocol.md`。修改 `core/src/consensus/` 时必须同时核对该文档与现有协议回归。

### 9.2 子代理

`packages/core/src/subagents/` 提供固定画像：

- **Explore**：只读代码、文件和公开资料，适合探索与方案调研。
- **Reviewer**：只读审查实现并可运行验证命令，适合质量和风险评估。
- **General**：可在继承权限内完成边界明确的实现或转换任务。

父会话最多并发 8 个子代理，该额度独立于用户会话运行上限。新建时同时持久化简短任务描述；每次 activation 创建独立 transcript 和 scratch，结束立即释放 AgentSession，需要继续时用稳定 subagent ID 从 transcript 冷启动。运行时不会因历史资源存在而自行续接；父模型可用 `ListSubagents` 按状态、ID 和任务描述重新发现并复用当前会话的既有子代理。

新建子代理默认冻结父会话当前模型；用户也可把子代理模型固定为任一已配置连接。宿主在创建边界同时规范化该模型支持的推理档位并写入 manifest，后续 activation 始终沿用子代理自身快照，不随父会话或全局设置变化。

子代理不能调用 `AskUserQuestion`、Fork/控制父会话或扩大权限；可以拥有自己的独立 TaskPlanState。运行时始终生成 `completed | error | aborted | limit | refusal` settlement 并通知父会话，即使子代理报错、耗尽上下文或没有主动汇报。

父 turn 以 activation 为单位跟踪本 turn 启动或继续的子代理。每个 settlement 在稳定边界立即进入同一 turn；父代理继续不重叠工作，已无工作但仍有未交付 activation 时进入事件等待，不轮询、不结束 turn，用户仍可正常插话。只有本 turn 全部 activation 终态已交付后，普通无工具正文才允许成为最终回答并结束 turn；全部交付只解除等待闸门，不会截断父任务仍需完成的工作或核验。用户 Stop 会取消本会话尚未结束的子代理；仅当本次确实取消了子代理时，父 transcript 的持久中断标记才附带其稳定 ID 与任务描述，不保留旧 turn 状态投影。

## 10. 图片、PDF 与 Office

### 10.1 图片

附件采用 staging → 校验/哈希 → commit/rollback 事务。JSONL 保存稳定引用，不保存 Base64；请求边界才读取和编码真实字节。当前用户输入支持 PNG/JPEG/WebP，单条消息最多 10 张；普通视觉工具与 MCP 单步骤最多 4 张。

视觉 Main 原生接收像素。非视觉 Main 只有配置了有效视觉辅助模型时才获得 `AnalyzeImage`；辅助模型只接收独立视觉问题和选定图片，不接收主会话历史、项目或工具。B/C 与协议回合物理移除视觉输入。

### 10.2 PDF

视觉模型可把小 PDF 按页展开为内部 JPEG；更大文件显式调用 `ReadPdf` 分页读取。非视觉模型读取有界提取文字。WebFetch 命中 PDF 后进入同一附件事务，再由 `ReadPdf` 处理，不保留第二套网页 PDF 解析链路。

PDF 派生页图只作为模型输入，不自动显示在聊天中。类型、页数、文件大小、字符总量和缓存均有硬上限；详情由 `packages/core/src/pdf/limits.ts` 与 `03-Agent与协议契约.md` §3 定义。

### 10.3 Office

Office 通过 `BuildOfficeArtifact`、`InspectOffice` 和视觉模型可用的 `RenderOffice` 形成单一工作流。构建脚本在收窄的 SES 环境运行，不能访问 Node 环境；输出先进入 staging，完成模板比较、公式重算、结构检查与可选视觉验收后再原子发布。

非视觉模型可以创建和检查 Office 文件，但只能声明结构验收；视觉模型在最终版本上增加全页渲染复核。内置 documents/presentations/spreadsheets Skill 是工作流规范，实际 schema 以工具代码和 `03-Agent与协议契约.md` §3 为准。

## 11. Skills、Web 与 MCP

### 11.1 Skills

Skill 来源：

- 项目级：Git 根到当前目录各层 `.agents/skills/`；
- 用户级：`~/.whycode/skills/` 普通子目录；
- 系统级：`~/.whycode/skills/.system/`。

每个根任务冻结一次目录和显式选择的正文；正文只投影到请求尾部，不写成第二份长期消息。Skill 资源仍受根目录、大小、UTF-8、digest 和权限约束；Skill 只能指导现有能力，不能扩大工具、项目或审批边界。

### 11.2 Web

`WebSearch` 由已配置的固定搜索后端执行；`WebFetch` 和 `WebFind` 负责确定性抓取、正文转换、分页与字面查找。所有 URL、重定向、超时、响应大小和正文长度均有宿主与 Core 双重限制。模型最终结论应使用工具返回的来源链接，工具卡不把不可信网页正文当 Markdown 执行。

### 11.3 MCP

MCP 工具先以有界目录暴露，模型通过 `ToolSearch` 延迟发现并加载；实际工具仍走统一 schema、权限、取消和结果限制。项目临时信任属于当前会话，不随 Fork 转移。resources、prompts、sampling、elicitation 或 MCP Tasks 只有形成真实需求后才分别设计。

## 12. Renderer 架构与视觉基线

Renderer 代码位于 `apps/desktop/src/renderer/`。它只维护显示所需的短生命周期状态；会话、运行、任务和后台事实来自 Main 快照或已提交事件。

### 12.1 信息架构

- 左侧：新会话、置顶/最近会话、运行像素动画和未读终态。
- 中央：会话 Header、时间线、执行过程、Markdown 正文、会话定位轨和一体输入框。
- 右侧：环境信息、子代理和任务计划；打开详情侧栏时替换摘要区，不同时占用宽度。
- 设置：连接、模型、搜索、MCP、协商和其它全局配置。

### 12.2 字体与 Markdown

全局使用 DSH 对齐的系统 UI 字体栈；用户消息和模型正文共用可读的基础字号与行高，标题、列表、代码、表格和引用由语义层级派生，不能在组件内散落另一套字号。唯一 `MarkdownContent` 负责：

- GFM、CJK emphasis 和安全外链；
- 流式正文的轻量展示与定稿后的完整解析；
- KaTeX 数学统一接受 `$…$`、`$$…$$`、`\(…\)` 与 `\[…\]`；定稿规范化避开围栏代码、行内代码、转义字面量和未闭合定界符；
- 代码块、表格横向滚动和嵌套列表层级；
- 不改写模型原文语义，不建立针对某个模型的预处理分支。

### 12.3 交互与性能

- Radix 负责菜单、弹层和焦点行为；不要创建原生 select 或平行弹窗体系。
- 长驻信息面板与设置表单统一复用 Radix 菜单的中性表面、间距和分隔规范；长驻表单保持正确的页面语义，不伪装成会自动关闭的下拉菜单。
- BTW/BBTW 只在会话空闲且已有完整 Main 回复时出现在斜杠菜单；选中后输入框和对应用户气泡使用虚线，发送、退出模式或发送失败恢复遵守同一草稿事务。
- 工具卡片摘要由 Renderer 的单一格式化器按工具语义投影关键动作与目标；未知 MCP/Provider 工具只展示有界、脱敏的高优先级参数。
- 会话定位轨只在真实可见刻度上响应悬浮；滚轮只在轨道活跃时改变窗口，点击使用确定性定位事务。
- 长会话切换先恢复稳定滚动锚点再显示，避免表格、图片和异步字体导致偏移；重启默认到底部。
- 运行态只渲染有意义的持续动画，并尊重 `prefers-reduced-motion`；静态装饰不使用逐帧 JS。
- 排队消息保持单行主摘要，重新编辑、丢弃和立即发送使用右侧紧凑图标操作；长文本必须截断，附件与 Skill 仍在同一卡片内展示。
- Markdown、ViewEvent、滚动记忆、附件验证与会话列表缓存均有界；离开会话、步骤提交和组件卸载时释放短生命周期对象。

具体视觉红线见 `04-START-HERE.md` §5.2。

## 13. 工程约束与验证

1. 对稳定协议先改 Core 类型和契约测试，再改 Main/Renderer 消费者。
2. 不在 UI、IPC、Provider 与持久化层复制同一业务判断。
3. 所有异步资源都要有 sessionId 所有权、取消路径和终态；切换会话不能靠组件是否挂载决定后台生命周期。
4. 任何缓存必须可丢弃、有容量上限，且不能改变正确性。
5. 测试与改动风险匹配：至少运行受影响包测试；跨层协议、会话、Provider 或 UI 基线变更还需全仓 typecheck 和生产 build。
6. 验证报告区分自动化、离线适配器、真实端点和客户端人工验收，不能互相冒充。

项目仍处于开发阶段。当前待办、阻塞和尚未完成的验证只写入 `05-暂存区便签.md`；已经完成的变更从本文删除历史叙述，只保留仍成立的架构事实。
