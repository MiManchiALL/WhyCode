# WhyCode 技术栈与系统架构

> 本文档规定技术栈、目录结构、代码规范、接口与数据流约定。所有参与开发的模型必须遵守。

## 1. 技术栈（已决策，2026-07-04 与用户确认）

| 层 | 选择 | 决策理由（摘要） |
|---|---|---|
| 桌面框架 | **Electron**（electron-vite 构建） | TS core 可直接使用 Node 文件系统与进程能力；Codex/Claude Desktop/Cherry Studio 同选；Windows 为重点平台时 Tauri 优势最小 |
| 前端 | **React 19 + TypeScript + Vite** | 同类产品全用 React，AI 组件生态 React-first |
| UI | **Tailwind v4 + Radix Dialog/Dropdown/AlertDialog + Lucide React + 自有 CSS tokens** | Radix 只承担焦点管理、键盘语义和浮层定位，Lucide 提供统一图标；布局、低饱和贴纸语气和组件状态由 WhyCode 控制，不引入整套模板生成器 |
| 流式渲染 | **Streamdown + @streamdown/math + KaTeX** | Streamdown 负责流式 Markdown 与代码块；官方数学插件只在正文定稿后排版 TeX，时间线折叠与滚动锚定仍由 Renderer 自有纯投影负责 |
| 动画 | **CSS transition / keyframes** | 只用于侧栏、菜单、对话框和状态反馈，并统一尊重 `prefers-reduced-motion`；当前体量不引入 Motion |
| LLM 适配 | **Vercel AI SDK v7 + 自封装 Provider 层** | 内置厂商统一走受测适配器；特殊字段走 providerOptions 逃生舱；封装层隔离 AI SDK 升级风险 |
| Schema/校验 | **Zod v4 + MCP JSON Schema/AJV** | WhyCode 自有契约继续由 Zod 单源；外部 MCP schema 保持协议原貌并编译运行时校验器，二者共用一个执行入口 |
| Skill 元数据 | **yaml 2.9** | 解析开放 Agent Skills 的 YAML frontmatter 并严格拒绝重复 key；不自行维护 YAML 子集，业务字段、路径、预算和生命周期仍由 WhyCode 校验 |
| MCP 工具检索 | **本地加权 BM25 + stemmer** | 只索引名称、标题、说明和顶层参数元数据；英文 Porter 词干归一化由成熟小依赖完成，检索边界、权重、缓存和预算仍由 WhyCode 控制 |
| 图片处理 | **Sharp 0.35**（仅 Core 的模型衍生图） | 成熟覆盖 PNG/JPEG/WebP、EXIF 方向、缩放/质量控制和解码像素上限；原图不改写 |
| PDF 处理 | **PDF.js 6.1 + @napi-rs/canvas 1.0**（Electron Utility Process） | Provider 中立地提取文字并渲染页面；独立进程提供内存/超时/崩溃边界，不依赖用户安装 Poppler |
| Office 制品 | **docx 9.7 + PptxGenJS 4.0 + ExcelJS 4.4 + JSZip 3.10 + fast-xml-parser 5.10 + SES 2.2** | 成熟库承担 OOXML 创建/打包/解析，SES Compartment 去除构建脚本的环境权限，Utility Process 约束资源；WhyCode 负责模板源结构复制/血缘、深层校验、实际公式重算、原子发布、检查点与模型能力门控。渲染使用 LibreOffice headless 或 Windows 隐藏 Microsoft Office，再复用 PDF.js |
| 网页正文 | **LinkeDOM + Mozilla Readability + node-html-markdown + ipaddr.js**（Electron Main） | 不渲染/不执行脚本地解析 HTML、提取正文并转换 Markdown；成熟 IP 分类用于公开网络边界，避免自研 DOM、正文算法和 IPv6 网段判断 |
| 数据存储 | 会话 transcript：**JSONL**（append-only + parentUuid 链，含模型事实与用户可见事件）；配置：JSON 文件；API key：`safeStorage` 加密 | 单一事实源支撑安全恢复、模型压缩与完整界面重建 |
| 包管理 | pnpm（monorepo workspace） | |

不引入：LangChain / LangGraph / AutoGen（多 Agent 编排自建状态机，见 §5）、LiteLLM / OneAPI（桌面端不跑外部网关；但 Provider 层支持自定义 OpenAI 兼容 baseURL，用户自建网关可作为端点接入）。

## 2. 进程架构

```
┌─ Renderer（React，纯展示 + 交互）
│    ↕ 类型化 IPC（contextBridge，事件流 + 请求/响应两类通道）
├─ Electron Main（窗口、pty、文件系统、safeStorage、网页搜索/公开页面读取、Office 后台转换、宠物 IPC 端口）
│    ├─ PDF Utility Process（每次任务独立、384 MB heap、超时即终止）
│    ├─ Office Utility Process（每次检查/构建独立、384/512 MB heap、超时即终止）
│    ↕ CoreEvent / CoreCommand 协议（进程内函数调用，但保持协议边界）
└─ whycode-core（宿主无关 TS 包：Agent loop、工具、Provider、Orchestrator）
```

约定：
- **core 不 import Electron**。core 通过依赖注入拿到宿主能力（fs 已是 Node 标准，pty/审批回调/事件 sink 由宿主注入）。
- UI 是事件消费者：core 产出 `CoreEvent` 流（见 §6），Renderer 只渲染事件，不含业务逻辑。
- 该协议边界同时是未来宠物接入点：Vising（WPF）经 WebSocket/命名管道订阅同一事件流的子集（`agent-status` 等），并可注入 `user-message`（文件投递）。M1 只保证事件类型可序列化（JSON-safe），不实现传输层。

## 4. 代码风格与规范

- TypeScript strict；沿用仓库现有格式。当前未配置 ESLint/Prettier，代码提交前至少执行受影响测试、全仓 typecheck 与 `git diff --check`，不得把未执行的检查写成已通过。
- 命名：文件 kebab-case；类型/组件 PascalCase；工具名常量导出（禁止字符串散落，提示词引用工具名必须 import 常量）。
- 工具定义 fail-closed：不声明 `isReadOnly/kind/endsTurnOnSuccess` 时，默认按「非只读、execute、不终止回合」处理。`requiresStandaloneStep` 默认 false，仅建立计划身份或执行权边界的工具显式设为 true。
- 注释与文档用中文；标识符用英文。
- 禁止复制 Claude Code 源码片段；只借鉴设计，自行实现。
- git：main 稳定分支；每模块 `feature/<name>` 分支开发，合并后删除分支；不提交密钥、构建产物、scratch、Claude Code 源码（.gitignore 保证）。

## 5. 核心机制设计（参考来源见括号）

### 5.1 Agent loop（已实现，M2-a 定型；M5 分层长任务）
自持外层循环（`core/src/agent/session.ts`）：每步一次 `streamText`（`stepCountIs(1)`，工具由 AI SDK 在步内执行），消息数组由 AgentSession 维护，事件经宿主注入的 emit 回调吐出。步骤间是所有横切机制的挂载点：steering 排队消息注入、压缩检查、（M3）编排控制和（M5）任务计划事务。「本步是否有工具调用」为普通续轮信号；显式 `endsTurnOnSuccess` 的控制面工具成功后直接结束 turn，普通参数校验与执行错误在稳定提交后进入下一次模型调用，由模型继续修正或解释，不把工具错误本身升级为 turn 终止。没有工具调用且没有可交付答复的响应不构成稳定步骤：空白、空 `messages`，以及整条可见正文只有 `out:default_api:<工具>{...}` 上游内部工具协议泄漏时，Agent 都丢弃该未提交步骤并用原上下文重试一次；普通正文中引用同类片段不受影响。只有无结构化工具调用的步骤才进入这条重试，因此此前已提交的工具不会重放；协议文本也绝不被解析执行。第二次仍不可交付则携带 finish reason 进入可恢复错误，不能写入模型历史或伪报 `completed`。

循环边界按角色分层：普通 Main 与协商后的 Main 执行阶段不设固定总步数上限；M1/B/C 协议与讨论回合仍最多 40 步，耗尽返回 `max-turns`。计划内容持久存在不代表当前回合正在执行：interrupted 是 `TaskPlanState.resumeRequired=true` 的硬中断态，dormant 是存在 active plan 但当前 runLoop 未接合，engaged 是本轮计划工具稳定授予执行权，或回答未 interrupted 的计划绑定问题后。engaged 计划每连续 10 个已提交 assistant step 没有计划变更时收到一次中性进度提醒；urgent 丢弃的半步不计数。完整无工具最终正文会在同一步事务中自然结束计划，并与最终正文原子提交一次模型可见的 canonical `active_plan:null` 边界；后续普通 Turn 只沿用历史边界，不重复写入。连续 3 次完全相同的工具名、输入、结果和错误状态仍暂停并保留计划。模型传输连续 120 秒无流活动时丢弃当前未提交 step；本地工具和用户审批期间暂停计时，因此它不是任务或工具总时长上限。

用户硬停止后，AgentSession 把 `<whycode-turn-aborted>` 写入模型消息链并结束原 runLoop；若中断时计划已 engaged，同时把 `resumeRequired` 与原因原子写入 `TaskPlanState`。进程恢复依据 turn 中持久化的 engaged plan ID 判定，dormant 临时问答崩溃不会误标旧计划；共识失败/取消则回滚任务起点的 messages+TaskPlanState。新的顶层 Turn 在真实用户消息前写 interrupted/dormant 执行边界，模型请求始终携带完整活动消息历史，不再从最近中断处切片，也不再额外猜一个“中止前主题”。System 只包含稳定规则，动态计划状态进入内部消息和任务工具结果；整套任务工具与普通工具均按角色、项目、权限和能力稳定注册，状态合法性由控制器 fail-closed 校验。首个稳定 step 原子追加 consumed 标记；协议回合收到 abort 立即退出。finalization barrier 内已提交内容不回滚，停止请求会阻止自动交接并把排队文本还给输入框。

**Steering**：运行中/压缩中的用户消息入队（`message-queued`），在稳定步骤间作为真实 user 消息注入（`message-injected`），不伪装成 system reminder。engaged 且未硬停止时，技术纠正、约束、提醒和临时问题先处理后继续当前任务；用户明确要求暂缓时模型自然结束本 run，计划转为 dormant，不调用暂停工具也不改变生命周期。代码不按文本猜测意图，而给模型一个 steering 决策窗口：纯最终文本可结束并保留计划；若一步只调用 `UpdateTaskItem` 保存既有进度，窗口跨步保留到下一回复；读取、写入、命令及计划身份/执行权工具会消费窗口并继续实质处理，之后普通最终正文按统一协议结束计划。turn 结束仍有剩余消息时自动续跑为新 turn；硬中断时弹回输入框（`queue-restored`）。urgent 会立即取消并丢弃当前未提交 step，再注入消息。Renderer 主输入框统一为多行输入：`Enter` 发送或忙时排队，`Ctrl+Enter` 立即插话，`Shift+Enter` 只换行且优先级最高；输入法仍在组字时不提交。

### 5.2 Provider 层
- `providers/catalog.ts` 是厂商官方模型画像的单一事实源：稳定模型 ID、厂商模型 ID，以及 `supportsNativeTools / supportsImageInput / supportsOriginalImageDetail / reasoningExposure / reasoningEffort / structuredOutput / promptCaching / contextWindow / maxOutput`。`reasoningEffort` 逐型号记录官方允许的显式档位和厂商默认值，不是跨厂商伪造的公共子集。内置厂商同时明确维护 `anthropic-messages / openai-responses / openai-chat` 协议和默认 Base URL；`registry.ts` 只负责 AI SDK 适配器，不复制能力值。只有目录中的精确 ID 能进入运行时，不做别名、相似名称或未知型号兜底。
- “模型连接”只配置统一可用的内置厂商与 CLIProxyAPI 连接；“辅助模型”和“协商模型”只选择这些连接中当前可解析的精确 ID，不拥有第二套端点或密钥；网页搜索继续使用独立服务配置。内置厂商的 Base URL 可留空走官方端点，也可填写保持该厂商协议的透明中转。CLIProxyAPI 不接受手填模型名或协议；`cli-proxy-models.ts` 独立维护经官方内嵌/远程目录证明等价的候选路由，以及这些路由明确公布的最小能力约束。`cli-proxy-discovery.ts` 在启动、打开设置和保存时读取当前实例鉴权后的标准 `/models` 并求交集：`modelIds` 只保留用户选择，`modelRoutes` 保存当前实例公布的全部审核传输路由。成功目录响应是实例可用性的事实源，会清掉已经消失的选择；请求失败不改写上次配置。设置页只列实际公布路由，因而可展示尚未勾选的 Terra 一类可用型号，也不会让已消失的旧选择阻塞有效修改。只有 key、选择和实际路由都存在的 `cliproxyapi:<目录 ID>` 才进入顶部下拉框。Core 工厂默认使用厂商 API ID，CLI 连接只覆盖 wire model ID；运行时、设置页、模型列表和上下文管理共同使用“厂商画像 + 当前审核路由约束”的唯一有效画像。旧任意自定义连接、未知画像探测、模型名推理后缀和其它改名链路已删除；实例 `/models` 只确认账号可用性，不能动态创造身份或画像。
- `AgentSession` 在实例生命周期内持有唯一 `transportSessionId`：有 Journal 的会话直接使用其 sessionId，纯内存 Agent 使用实例级 UUID；模型切换和恢复不改变身份，Fork、Subagent 与协商 Agent 天然得到不同身份。Provider 注册表只提供通用的可选传输身份，具体连接适配器决定是否编码；当前只有 CLIProxyAPI 把它复制为每次请求的 `X-Session-ID`，Anthropic/OpenAI/Gemini 三种底层协议共用该规则，官方直连完全不透传。一次性辅助识图每次调用使用新身份。Header 不写入消息或持久化 schema，也不通过提示词塑造模型行为；CLIProxyAPI v7.2.138 会优先采用显式会话边界并停止从公共前置文本派生共享身份。
- 桌面设置只把 `hasKey` 和目录能力交给 Renderer，绝不回传密钥。Main 用 Electron `safeStorage` 分别加密内置厂商、CLIProxyAPI、Perplexity Search 与 Tavily Search 密钥，临时文件 + rename 原子保存；B/C 只持久化统一连接 `modelId`。配置 v9 在启动迁移时直接删除 v8 的 B/C 独立 `model/apiKey/baseURL`，不生成备份字段、不双读旧结构。启动迁移同时完成其它旧明文加密，并把 v3 自定义连接仅转换成 `retiredModelLabels` 历史显示名后从配置删除。高级用户在 JSON 显式写入的新 key 仍优先读取并在下次启动加密。网页搜索使用独立的 `webSearch.activeProvider/perplexity/tavily` 配置域；旧配置没有活动项时保持 Perplexity，活动密钥失效时只回退到另一已配置后端，不进入模型 Provider 配置或 Renderer 快照。
- 当前视觉目录包括 Anthropic Claude Sonnet 4.6、OpenAI GPT-5.5 / GPT-5.6 Sol、Terra、Luna，Google Gemini 3.1 Pro Preview / Gemini 3.7 Flash、智谱 GLM-5V-Turbo 与小米 MiMo V2.5；DeepSeek V4 Flash/Pro 保持纯文字。Gemini 3.6 与 GPT-5.2 已退役。内置 Base URL 中转按注册型号使用厂商画像；CLIProxyAPI 只有官方目录先证明等价且当前实例实际公布的路由才可合成有效画像。静态兼容目录当前审核 Claude Sonnet 4.6、Gemini 3.1/3.7、GPT-5.5 与 GPT-5.6 Sol/Terra/Luna；DeepSeek V4 没有 CLI 路由。厂商画像中 GPT-5.5/5.6 为 1,050,000/128,000，Gemini 为 1,048,576/65,536，Claude 为 1M/64K；CLI 路由则收窄为 Claude 200,000/64,000、GPT-5.6 372,000/128,000、GPT-5.5 272,000/128,000，Gemini 3.1 Antigravity 别名最大输出为 65,535，Gemini 3.7 使用 v7.2.132 内嵌目录登记的 `gemini-3.7-flash-high`。设置页展示、请求能力与 `autoCompactThreshold` 都读取当前连接的有效值，不能让官方大窗口推迟 CLI 路由压缩。GLM-5V-Turbo 与 GLM-4.7 均为 200K/128K，MiMo 为 1,048,576/131,072；DeepSeek V4 Flash/Pro 均为 1,000,000/384,000，约在 910,000 token 自动压缩。
- CLI 有效画像不是 `route ?? base` 的普通覆盖：数值取较小值；推理闭集与厂商档位取交集；明确 `false` 能关闭能力，路由 `true` 不能反向开启厂商画像尚未验证的能力；结构化输出只能降级；缺失字段只在同型号及透传语义经过审核后继承。`supported_parameters` 不代表输入模态，Codex client 的 `ultra` 带自动任务委派语义，也不属于 WhyCode 的通用 `reasoning.effort`。同一 wire ID 若可能由多个 OAuth Provider 提供且 `/models` 无法区分，静态约束取所有可能提供方的安全交集。应用不在启动时从可变远程目录生成画像，远程/内嵌目录只在模型更新审查时固定为随版本发布的代码事实。
- 推理强度的数据流固定为“会话选择 → 当前连接有效画像校验 → 实际客户端协议翻译”。内部 `default` 表示不覆盖厂商/连接默认；顶栏把它显示成当前连接记录的默认档位，并且只渲染真实档位，不再同时显示“默认（高）”和“高”。没有已验证可选档位的型号固定灰色“推理：默认”。显式档位与连接限定 `modelId` 一起写入同一 `model-change`、snapshot 和 metadata，重启可恢复，切换模型回到内部 default；路由更新后已不合法的历史选择归一为当前连接 default。Provider 只根据实际协议翻译：OpenAI Responses 使用 `reasoning.effort`，OpenAI Chat 兼容使用 `reasoning_effort`，Anthropic Messages 使用 adaptive thinking 与 `output_config.effort`；内置中转和 CLIProxyAPI 复用同一链路，不在 UI 或模型名拼后缀。已确认的 GPT 画像显式设置 SDK `forceReasoning`，避免 CLIProxyAPI 路由名不以 `gpt-5` 开头时被 SDK 按字符串误判为非推理模型。
- OpenAI Responses 函数工具在 `AgentSession` 的 Provider 边界统一显式发送 `strict=false`。WhyCode 的跨 Provider Zod/JSON Schema 保留真实的可选字段与默认值，而 Responses 当前省略 `strict` 会按 `true` 处理并要求生成所有属性；显式关闭后仍由统一运行时验证器在权限判定前 fail-closed，不增加 GPT、CLIProxyAPI 或具体工具的参数修补分支。OpenAI Chat、Anthropic Messages 及其它协议不注入该字段。
- OpenAI Responses 固定 `store=false`，因此规范消息链必须自己保持 function call/output 成对。只有 WhyCode 注册并由客户端实际执行的函数调用及结果属于本地工具事实；兼容网关擅自注入的原生服务端工具若被 SDK 标为 `providerExecuted`，其调用、供应商结果以及 SDK 为未注册工具合成的 `NoSuchTool` 结果必须在稳定提交和请求投影前按 `toolCallId` 整组移除。否则 SDK 下一次会跳过供应商调用、却把伪本地结果序列化为没有对应 `function_call` 的 `function_call_output`，服务端就会以 `No tool call found...` 拒绝整段历史。该协议级投影同时避免供应商图片 Base64 进入 JSONL；同一响应中的正常本地工具调用/结果继续原样提交。不得用 GPT/CLIProxyAPI 型号分支、继续重试、UI 隐藏、会话迁移或第二套历史修复替代这一配对不变量。
- 厂商官方精确档位：Claude Sonnet 4.6 为 low/medium/high/max（默认 high）；DeepSeek V4 Flash/Pro 为 high/max（默认 high）；Gemini 3.1 Pro Preview 为 low/medium/high（默认 high）；Gemini 3.7 Flash 为 low/medium/high（默认 medium）；GPT-5.6 Sol/Terra/Luna 为 none/low/medium/high/xhigh/max（默认 medium）；GPT-5.5 为 none/low/medium/high/xhigh（默认 medium）。CLIProxyAPI 中 Claude 档位不变；Gemini 3.1 规范/High/Low 路由默认分别为 high/high/low，Gemini 3.7 High 路由取官方档位交集 low/medium/high 并默认 high；GPT-5.6 只保留 low/medium/high/xhigh/max，Sol 默认 low、Terra/Luna 默认 medium；GPT-5.5 只保留 low/medium/high/xhigh（默认 medium）。MiMo V2.5、GLM-5V-Turbo 与 GLM-4.7 没有 WhyCode 可证明的离散档位，UI 固定禁用并灰显“推理：默认”。目录、Main 和 Provider 三层分别限制展示、命令与请求体，绕过 UI 的非法档位仍 fail-closed。
- 已知厂商差异（必须处理）：OpenAI GPT-5.5 与 GPT-5.6 全系使用 Responses API，默认不显式覆盖型号推理强度，但始终请求 `reasoning.summary=auto` 并固定 `store=false`。WhyCode 自己持久化完整历史，请求 `reasoning.encrypted_content` 并在后续工具步骤、普通轮次及重启恢复后重放完整 encrypted reasoning item；不得把 `rs_... / msg_...` 当成服务端已保存的 `item_reference`。Google 使用官方 OpenAI 兼容 Chat 协议；`extra_body.google.thinking_config.include_thoughts=true` 请求推理摘要，assistant tool call 的 `extra_content.google.thought_signature` 必须随稳定历史回传。Anthropic Claude Sonnet 4.6 固定使用 adaptive thinking，档位只调整 effort。DeepSeek V4 显式启用 thinking，只有 high/max 产生有效差异。智谱当前为工具兼容关闭 thinking；MiMo 用 `providerOptions.mimo.thinking.type=enabled` 开启 thinking，但官方不提供可调强度。OpenAI-compatible Provider 将流式 `reasoning_content` 映射为标准 reasoning part；该 part 与 assistant tool call 一起进入稳定 step 和 JSONL，恢复后必须按厂商契约还原。
- 统一 usage/成本统计按模型分桶累积。

### 5.3 工具系统（M2-b 定型；2026-07-11 三批增强；2026-07-19 Web P0；2026-07-25 MCP P0）
工具接口（`core/src/tools/tool.ts`）统一为 `name / description / prompt / inputSchema / isReadOnly / kind('read'|'edit'|'execute'|'control') / requiresStandaloneStep / endsTurnOnSuccess / initialApprovalReason / turnEndReasonOnSuccess / extractPaths / checkpointScope / renderDiff / execute`。内置工具继续使用 Zod 单源完成类型推导、运行时校验和 JSON Schema 派生；运行时 MCP 工具保留服务端原始 JSON Schema，用 MCP SDK 的 AJV 编译器生成验证器。二者都只经过 `validateToolInput` 这一条 fail-closed 输入边界，没有运行时验证器就拒绝执行。`kind` 与 `extractPaths` 供权限引擎判定；`control` 表示只改变会话/协议内部状态，不受只读档拦截、不触发资源检查点，但因有状态仍属于非只读调用。`checkpointScope` 只声明可完整证明的 `exact-files`，回答“哪些文件可以精确撤销”；未声明的写操作形成安全屏障。路径解析统一 `resolveAllowed`（项目目录+会话授权目录，执行时最后防线）。native function calling 优先；prompt-based fallback 按 capability flag 预留（暂缓实现）。

普通会话不存在 Core 级“纯聊天”工具装配分支：用户未选择项目时，Desktop 在首条消息前先把 `pending-managed` 物化为独占受管目录，再创建 AgentSession。普通 Main 始终注入 `# 环境 / # 工具使用 / # 任务计划` 并获得完整角色工具目录；权限档位不改变模型看到的工具，只在实际调用边界决定允许、询问或拒绝。讨论与协议角色仍按角色物理移除 Main 专属的网络、MCP、Skill、视觉、PDF、Office 和任务控制工具，但保留内置文件/命令工具，并由 discussion 权限强制项目只读、scratch 可写。

每个已建立会话还拥有独立的 `userData/scratch/{sessionId}/Main/`。它与 Local、managed 或 Worktree 的项目目录分离：项目目录保存交付物，非交付脚本、日志、下载/转换中间物等放入会话 scratch。稳定 System 在环境段只给出当前 Agent 的临时工作区，并用一条通用规则说明两类目录的职责；现有 `RunCommand` 说明只补足“复杂非交付脚本先写入该临时工作区再按文件执行”，其它工具不重复同一提示。权限边界把整个会话 scratch 根作为固定 `additionalDirs`，但仍服从当前权限档位；讨论阶段进一步把副作用收窄到本任务当前 Agent 子目录。

AI SDK 可能在同一步并行发出多个工具调用。所有调用先进入 AgentSession 的短审批尾链，在队首重新执行权限判定；因此同一工具的首次隐私审批不会并发覆盖 Renderer 的唯一审批卡，前一调用选择“会话记住”后，后一调用会读到新授权并直接通过。授权完成后 `isReadOnly=true` 的工具仍可并行，其余工具进入会话级副作用尾链。普通 Main 的 `edit`/`execute` 再由桌面宿主按 `WorkspaceBinding` 推导的有效工作目录进入跨 AgentSession FIFO，把审批、检查点 prepare、execute 与 finalize 放进同一临界区；检查点恢复使用同一队列。不同项目并行，同项目写入与回滚互斥；B/C 讨论继续受 scratch 权限边界约束，不借此放宽。

搜索与读取采用“快速主路径 + 安全回退”：`Glob/Grep` 从 PATH 的绝对目录解析 `rg`，不用项目 cwd 搜索可执行文件，执行时无 shell、可中止、20 秒超时并流式按行截断；无 rg 时由 `search/fallback.ts` 以 32 目录/16 文件批次有界并发遍历，最多扫描 20 万文件。三类目录/搜索工具支持 limit/offset，Grep 支持 content/files/count、glob、大小写、literal 和上下文。`ReadFile` 先探测 NUL，再用 stream+readline 获取指定行，限制超长单行，不再整文件读入内存。超长单行与网页正文共用 `unicodeSafePrefix`：限额仍按 JavaScript code unit 计数，但截断点若落在 UTF-16 surrogate pair 中间则退回一位，避免孤立代理项进入工具结果和后续模型请求。

网页搜索采用“统一 Core 契约 + Main 后端适配”而不是让模型直接绑定厂商：`core/tools/web-search` 只定义唯一 `WebSearch`、厂商无关请求/结果和宿主 `WebSearchHandler`；Electron Main 的单一分派边界在每次执行时读取当前设置，选择 Perplexity 或 Tavily 适配器，模型 schema 不出现后端名称或厂商字段。工具只在普通 Main 的 `mainTools` 中注册，默认受管工作区会话同样可用；讨论、M1/B/C 和协议回合沿用既有物理移除边界。即使未配置 key，普通 Main 的工具 schema 仍保持稳定，执行时返回当前后端的可操作设置提示；同一步的并行调用全部返回并提交错误卡，完整工具结果随后进入下一次模型调用，让模型解释配置问题、改用已有信息或自行判断后续行动。此前 WebSearch 独有的 `endsTurnOnError` 会在模型读取错误前强制暂停，现已从工具契约与 Agent 执行链整体删除。

`WebSearch.query` 默认接收一个最多 500 字符的查询，也可接收 2～4 个去重后的查询数组。工具提示要求把查询写成简洁搜索词，一个查询只表达一个检索目标；复杂调研只把互不重复、可独立作答且共享筛选条件的子问题批量提交，依赖前批结果的后续查询留到下一步再规划。`max_results` 为每个查询 1～10 条，Core 按查询数下调单查询上限，使一次工具结果总计不超过 20 条；recency 只允许 hour/day/week/month/year，来源域名白名单最多 10 个。Perplexity 将数组直接映射为一次 multi-query 请求，继续使用 `search_context_size=low`。Tavily `/search` 只接受字符串，因此按查询数并发 2～4 个请求；WhyCode 设置只提供 basic/advanced 两档并默认 basic，显式 `search_depth` 固定相关性和 credit 边界。请求开启 `auto_parameters` 但不指定 `topic`，让 Tavily 自动选择 general/news/finance；显式 depth、max_results、时间、域名和关闭 answer/raw content/images 的字段继续覆盖自动决策，所以不会产生第二份服务端答案或正文膨胀。Tavily 的 `time_range` 最细只到 day，故 hour 在适配边界降为 day。

两家适配器共用一个 Main HTTP 边界，分别固定发往 `https://api.perplexity.ai/search` 与 `https://api.tavily.com/search`；通过注入的 Electron `net.fetch` 使用 Chromium 网络栈并继承系统代理、PAC 与代理认证。每次工具调用共用 20 秒 AbortSignal、禁止重定向和总计 2 MB 流式响应上限；Tavily 批量请求按查询数平分响应预算。普通单查询失败不取消已经并发的其它查询：至少一个请求完成时返回成功来源及有界失败清单，全部失败时才抛出工具错误；用户取消和统一超时仍会中止整批。非成功状态先取消 body，不读取或回传服务端正文，也不做可能重复计费的隐藏重试。Tavily 在适配器内部按有限 `score` 降序排列，缺失 score 的结果稳定置后；score 只作为同批相对次序，不使用 `>0.5/0.7` 等跨查询硬阈值。两家响应随后都只投影到 Core 的标题、无凭据 HTTP(S) URL、摘要和可用日期；Core 按去除 fragment、排序查询参数后的 URL 身份去重，保留后端排序最靠前的条目，再统一限长并格式化为 `[Sx] [标题](URL)`、部分失败说明及“不可信外部资料”边界。首次调用仍明确告知搜索词将发往已配置的外部服务。

`WebSearch` 的固定服务端点不接收用户 URL，因此自身不引入任意主机网络权限或 SSRF 分支；Search API 摘要仍不能冒充已读取全文。官方请求/响应字段以 [Perplexity Search API](https://docs.perplexity.ai/api-reference/search-post)、[Tavily Search API](https://docs.tavily.com/documentation/api-reference/endpoint/search) 与 [Tavily Search Best Practices](https://docs.tavily.com/documentation/best-practices/best-practices-search) 为准。advanced 只有用户在设置中明确选择才会使用 2 credits；默认 basic 继续保持 1 credit。未来只有真实场景证明需要时才考虑自动后端回退或多后端聚合；当前不让单次模型调用隐式启用另一个后端或产生两套并行结果。

完整网页读取另建厂商无关的 Core 契约：`WebFetch {url,offset?,limit?}` 的 `url` 必填，`offset/limit` 只用于 HTML/文本且默认从第 1 行返回最多 100 行。该工具只读取无需登录或服务身份即可公开访问的网页；用户只给出普通 HTTP(S) URL 且没有明确要求私有、登录或账号数据时，模型先用 `WebFetch` 尝试公开读取。公开读取失败，或用户已经明确需要授权、登录态或私有数据时，再用 `ToolSearch` 查找对应 MCP 工具；需要先发现来源而不是读取已知 URL 时使用 `WebSearch`。结果是判别联合：文本页返回标题、请求/最终 URL、内容类型、稳定行号、总行数和源截断状态；远程 PDF 返回请求/最终 URL、来源链接及已保存的规范 `PdfAttachment`，不提供 WebFetch 行分页。`WebFind {url,pattern,context,max_results}` 只在同一 AgentSession 的已完成文本正文缓存中做不区分大小写的字面查找，PDF 后续统一使用 `ReadPdf`。三者只注入普通 Main，默认受管工作区会话同样可用，M1/B/C、讨论和协议回合物理移除。`WebFetch` 首次调用沿用 `initialApprovalReason` 告知目标请求可能暴露公网 IP，可单次批准或会话记住；`WebFind` 不联网，因此不另设审批。WebFetch 未取消的失败结果在既有脱敏错误后追加“若已配置对应的 MCP 服务，可尝试 ToolSearch”，由模型自行判断是否采用；用户取消只返回取消事实。所有错误仍作为普通工具结果回流当前主模型，没有正文摘要模型或第二套 Agent 调用。

Electron Main 的任意 URL 传输使用 Chromium 网络栈的 `net.request`，继续继承系统代理/PAC，但不使用 `net.fetch({redirect:'manual'})`：真实 Electron 中后者遇到重定向会直接拒绝，无法给安全层逐跳判断。薄适配器只把 `redirect/response` 事件变成流式 Response；请求对象保留一个覆盖完整生命周期的错误监听，Electron 在 `response/end/close` 后迟到的 `ERR_CONNECTION_CLOSED` 因而被当前请求消费，不再成为 Main 未捕获异常弹窗，读取期间的错误仍由 body 流返回。URL、重定向和正文规则仍集中在单一网络层。每一跳只接受无凭据 HTTP/HTTPS，HTTPS 不降级到 HTTP，并在请求前通过同一 Chromium DNS 缓存校验全部 A/AAAA 结果；localhost、单标签/内网后缀、私网、链路本地、CGNAT、保留/文档/组播、IPv4 映射/NAT64/6to4 和已知云平台服务地址均拒绝。请求固定 GET、`credentials=omit`、不使用会话 Cookie、无 referrer、无缓存，统一 20 秒超时、最多 5 次重定向；HTML/文本解压后最多 5 MB，远程 PDF 复用既有 50 MB 上限，非成功响应正文不进入错误消息。

成功响应接受 HTML/XHTML、纯文本、Markdown 与 PDF，按响应头、BOM 或 HTML meta 确定文本字符集。网络下载留在 Main；HTML/文本通过一次性 `web-page-worker` Utility Process 执行 LinkeDOM 清洗、Mozilla Readability 正文提取与 node-html-markdown 转换，V8 heap 限 256 MB、20 秒，超时/取消/退出立即杀进程，Main 对 IPC 来源、URL、内容类型、标题、行长和总量重新校验。整页文本最多缓存 250k 字符、单行最多 4096 字符；每次 `WebFetch` 最多 100 行且正文不超过 9k 字符，明确给出下一 offset。每会话只保留最近 6 页、15 分钟的文本内存 LRU，不跨会话或重启持久化；这份缓存是 `WebFind` 稳定行号与不重复联网所必需的唯一状态，不建立 ref_id 或第二套页面事实源。远程 PDF 不进入 HTML worker、文本缓存或 WebFind，也不再经过一条 Web 专属文字提取路径；下载字节直接复用现有 PDF 附件的 staging、SHA-256、完整打开校验、commit/rollback 事务，保存到当前会话 `attachments` 后返回 ID。后续视觉与非视觉读取都走既有 `ReadPdf`，共享 50 MB/1000 页及 PDF Utility Process 边界。

搜索结果提供 `[Sx]` Markdown 来源；HTML/文本的每个 `WebFetch` 分页结果、`WebFind` 匹配都提供同一最终 URL 的可点击来源与 `Lx-Ly` 证据范围，远程 PDF 的初次结果提供最终来源与附件元数据，后续证据范围由 `ReadPdf` 的页段承担。工具提示要求最终答复汇总“来源”。Renderer 仍只渲染模型文本，Electron 对新窗口与页面导航统一拦截，只把无凭据 HTTP(S) URL 交给系统浏览器，文件、脚本和带账号密码的地址全部拒绝。这是现有字符串工具结果中的确定性引用格式，不新增引用数据库、后处理模型或第二份页面身份。

路线取舍：Claude Code 当前 WebFetch 在 HTML 转 Markdown 后还会调用小模型回答抓取提示，WebSearch 则依靠服务端搜索工具产生 Sources；Codex 的公开 app-server 契约把 `search/open_page/find_in_page` 作为托管 Web Search 动作，并不提供可直接复用的本地 HTML worker。WhyCode 保持用户已确认的 Codex 式稳定行号/分页/页内查找，用自身 Utility Process 隔离不可信 HTML；远程 PDF 则像用户附件一样先建立稳定会话身份，再交给统一 `ReadPdf` 分页读取。引用与附件提示都由代码生成，仍只有主模型一次推理。未来深入方向（非当前承诺）：需要 JavaScript 渲染、登录态、导航等待、DOM 定位或点击输入时再单独设计隔离浏览器与按来源授权；当前静态读取不增加隐藏浏览器、跨会话页面缓存、第二模型压缩或 B/C 网页能力。

MCP 采用“内置工具常驻、外部工具延迟加载”。Electron 启动时在全局 `~/.whycode/mcp.json` 缺失时创建文件，并通过同一个原子配置变更函数补齐缺失的 Context7 与 GitHub 内置项；已有同名条目完整保留，用户关闭内置项应修改 `enabled`，不能靠删除制造每次启动都不同的默认状态。两个内置项都默认启用且不在启动时预连：Context7 官方端点可匿名使用；GitHub 使用官方 `/mcp/readonly` 路由并同时固定 `X-MCP-Readonly: true`，以传输路径和 Header 双重约束读取工具，但官方仍要求所有操作认证。WhyCode 为内置项维护最小、可信的来源能力摘要，因此首个模型步骤无需预连就能知道 GitHub 可读取仓库/文件/Issue/PR 及认证后私有资源，Context7 可查询当前库文档；这只影响能力路由，不复制工具目录或认证状态。未认证 GitHub 在创建会话快照时从有效服务器集合移除并留下可操作诊断，因此不会让 `ToolSearch` 反复撞 401，也不会把“默认启用”伪装成“匿名可用”。项目可提供 `<project>/.whycode/mcp.json`，同名服务器整项覆盖全局，禁用或字段错误都不会回退。配置是 AgentSession 创建时的一次性快照，最多 32 个有效服务器；相对 stdio cwd 分别以全局配置目录或项目目录解析，`${ENV_NAME}` 只允许出现在显式 stdio env 与 HTTP Header 值中。模型、Renderer、工具结果和错误日志永远不接收 command/args/cwd、URL/Header 或环境变量值；项目配置可能启动进程或连接外部服务，因此非全自动档第一次 `ToolSearch` 必须让用户显式信任当前配置摘要；显式全自动档与其它工具一样直接进入执行边界，不产生审批卡。批准后的配置身份进入同一会话 MCP 状态，运行体卸载再恢复时若身份未变不重复审批。

`core/src/mcp/` 以 `McpConnectionManager` 协调目录、`McpServerConnection` 管理单服务器协议生命周期。P0 只支持 stdio 与 Streamable HTTP；HTTP 由 Electron `net.fetch` 注入并禁止凭据与重定向，stdio 只继承 SDK 安全环境白名单再叠加显式 env，并持续排空 stderr。连接最多 4 个并发。首次 `ToolSearch` prepare 全部当前有效且已获信服务器，取得分页目录和 `initialize.instructions`；已经 ready 的连接复用现有目录，重复检索不再强制发送 `tools/list`。恢复会话只重连最新工具状态实际引用的服务器，不为只需显示说明的其它服务器建立传输；再次 ToolSearch 才连接余下服务器并重建全目录。协议初始化说明会规范换行、拒绝危险控制字符并按 2 KiB UTF-8 上限保存；连接关闭只清除传输实例，稳定步骤会把所有连接成功服务器的有界说明放入内部会话状态，总计最多 8 KiB。ToolSearch 提示以“不可信外部元数据”展示当前仍启用配置对应的说明，不把 scope、idle/ready 或连接错误等易变运行态放进定义，因而 AgentSession 重建后可以恢复相同提示。`tools/list` 最多 100 页、单服务器 2,000 个、总计 10,000 个工具，单个输入/输出 schema 最多 256 KiB、单服务器规范化目录最多 2 MiB。目录发布是原子的；刷新失败保留 last-good 元数据但状态 fail-closed，不能继续绑定；`tools/list_changed` 到达时立即增加 revision 并令当前步骤旧绑定失效，同时触发规范目录刷新，刷新期间的新步骤不得获得半新半旧目录。实际调用前再次核对服务器 revision、稳定工具 ID 和包含配置/schema/说明的描述符哈希，改变后要求重新检索。

`ToolSearch {query,max_results=5}` 是非独占的本地控制工具，最多返回 8 个结果。其静态描述与 WebFetch 使用同一条路由边界：普通已知 URL 先公开读取，失败或明确需要已配置服务的登录身份、授权能力或私有数据时再检索 MCP；这不改变 MCP 状态、工具数组生成时机或缓存键。它可与 `WebSearch`、`WebFetch` 及其他非独占工具在同一个模型步骤并行调用，两类结果仍按现有步骤事务一起稳定提交；但一次模型 API 请求的工具定义在生成开始前已经固定，所以本次检索新命中的 MCP schema 不能倒灌进仍在生成的同一响应，只能从紧接着的下一模型步骤以 `Mcp__<server>__<tool>__<hash>` 形式作为真正具名 function tool 出现。这是已有 Agent 工具结果循环的自然下一步，不增加摘要模型或额外业务调用。

检索结果明确是按相关性截取的 top-N 候选，不代表完整工具目录；候选不适用或零命中时，模型应先用更具体、贴近英文工具元数据的动作、对象或参数词再次检索，再决定是否改用网页工具。`query` 的固定参数说明用“读取仓库代码 → `GitHub file contents get read`”示范如何把自然语言目标改写为能力词；示例不绑定某个工具 ID，也不参与路由或排序。目录匹配使用确定性的紧凑加权 BM25：服务器名和原始工具名、标题、说明、顶层参数名及其说明按不同权重进入索引，不递归索引任意深层 schema 值；英文做 camelCase 拆分、Porter 词干和通用动作同义归一，中文等 CJK 文本保留单字与双字 token。目录描述符未变化时复用同一个派生索引，`tools/list_changed` 或描述符变化后才重建；不调用 embedding、搜索服务或第二模型，不设置跨主题固定分数阈值，也不加入 GitHub URL、私有仓库或 404 特判。不存在通用 `CallMcpTool` 分发器。

新检索结果按相关性优先占用最多 64 个工具、总计 256 KiB 的模型定义预算，空间不足时先淘汰较旧引用。工具引用、服务器说明与可选的项目配置信任指纹共同写成版本化内部 system 状态，并与产生它的 assistant/tool 消息在现有 JSONL step 原子提交；所有普通模型请求和摘要源都物理过滤该状态。完整压缩不再丢弃它，也不让摘要模型总结，而是由宿主把压缩前最新状态精确重建到压缩后消息链。状态中的连接身份摘要只包含传输目标、命令参数、cwd 及 env/Header 名称，不包含其值、安全存储凭据或凭据派生摘要；项目信任指纹只对当前项目服务器名称与上述无密钥路由身份稳定排序后求摘要。配置删除、禁用或路由身份变化在新 AgentSession 的下一稳定步骤统一清除旧工具、说明与失效信任，并在再次检索项目服务器前重新审批；认证值轮换不会把同一端点误判成另一套目录。只要 MCP 配置和目录没有变化，切换会话本身不会改变该对话下一请求的 System、ToolSearch 提示或已加载工具数组；实际 ToolSearch 命中新工具造成的工具数组变化是明确且不可避免的缓存边界。

所有真实 MCP 工具无论服务器 annotations 如何都按 `kind=execute / isReadOnly=false` 进入既有参数验证、首次外部执行审批、会话副作用串行、不可回滚屏障、取消、进度、错误回流、附件和步骤提交链；工具名中的描述符哈希也使“会话记住”不能跨目录版本误授权。服务器返回的工具 description 与 `initialize.instructions` 始终标为不可信元数据，只能帮助理解能力，不能覆盖 System、项目或用户指令；初始化说明只出现在 ToolSearch 来源上下文，不复制进检索结果。结果只投影 text、structured content、文本资源和资源链接，移除 `_meta`；格式化过程最多检查 256 个 content item，并对结构深度、节点、集合项与字符串逐层限长，最终模型文字总计 64 KiB，不能先构造无界中间文本再末端截断。所有外部字符串在同一输出边界识别可解析 URI，URL userinfo 以及 token、access token、API key、credential、signature、OAuth code/state 等凭据型 query/fragment 值统一替换为固定占位；普通参数、路径和正文不改写。文本先按既有 64 KiB 预算截取再扫描，结构化字符串仍先受 8 KiB 单值与总结构预算约束，不因脱敏重新引入无界处理。PNG/JPEG/WebP 最多 4 张并复用会话图片事务，音频与二进制资源明确报告不支持。AgentSession 空闲卸载、恢复候选失败、删除目标会话和退出应用都会关闭客户端、传输与 stdio 子进程；删除事实源前等待关闭完成。

Core 与 Desktop 使用同一精确依赖 `@modelcontextprotocol/sdk@1.29.0`：它承担初始化协商、stdio/Streamable HTTP 传输、分页、通知、取消、超时、协议 schema 和 OAuth 客户端编排；自行实现 JSON-RPC、传输或 OAuth 发现/换令牌会复制安全敏感基础设施。SDK 当前尚未吸收的安全修复由 `pnpm-workspace.yaml` 精确覆盖到 `@hono/node-server@2.0.11`、`fast-uri@3.1.5`、`hono@4.12.34` 与 `ip-address@10.3.1`，上游升级后必须删除失去作用的覆盖，`pnpm audit --prod` 持续归零。当前仍不支持 legacy SSE、resources/prompts、sampling、elicitation、MCP Tasks 或自动安装任意服务器；这些只有出现真实需求并完成各自生命周期与 UI 设计后才扩展。协议依据：[MCP 2025-11-25 规范](https://modelcontextprotocol.io/specification/2025-11-25)、[MCP Authorization](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization)、[官方 TypeScript SDK](https://github.com/modelcontextprotocol/typescript-sdk)。

桌面“连接设置”是 `mcp.json` 的受限管理视图，不是第二份结构配置：Main 每次打开/刷新时重读全局与当前项目配置，Renderer 只看到名称、作用域、传输类型、启用/覆盖、内置身份、认证是否完成、当前会话状态、工具数量和脱敏诊断；启停与简化新增都原子写回原文件。绿色“推荐预设”已经删除，Context7/GitHub 直接作为中性的内置默认项出现。普通表单只承载名称、作用域、传输，以及 HTTP URL 或 stdio command/逐行 args/可选 cwd；env、额外 Header、超时等低频字段继续在高级文件中维护。当前 AgentSession 使用创建时固化的连接管理器，结构或认证修改明确等到该运行体重建后生效，避免热换服务器破坏工具 revision、审批和步骤事务。项目配置首次实际检索仍走显式信任边界；同一会话恢复出的信任指纹只在配置身份完全相同时复用，身份变化会 fail-closed 重新审批。缺失项目文件只生成空模板，不自动引入全局默认项。

全局 Streamable HTTP 共用一条认证主通道。`mcp.json` 只保存连接结构与可移植的环境变量引用；界面填写的 Header/PAT 由 Electron `safeStorage` 加密保存在应用托管配置中，并按服务器名称与 `{transport,url}` SHA-256 指纹绑定，URL 变化即 fail-closed。Context7 只用内置元数据把官方 `CONTEXT7_API_KEY` 显示成可选 API Key；GitHub PAT 输入则统一归一为 `Authorization: Bearer …`，默认只读 Header 继续留在结构配置中。Renderer 只看到已配置的 Header 名称。项目配置不写本机密钥库，继续用 `${ENV_NAME}`，也绝不继承同名全局 OAuth 会话。

通用 OAuth 控制器只服务全局 Streamable HTTP，并复用 SDK 执行 RFC 9728 受保护资源发现、授权服务器元数据发现、PKCE、授权码交换和令牌刷新；支持动态客户端注册的普通服务器可直接使用。浏览器回调固定为 `http://127.0.0.1:47168/mcp/oauth/callback`，每次使用 256-bit 随机 state、五分钟超时和全局单飞；MCP 资源、发现、动态注册、换令牌及浏览器授权地址都只允许 HTTPS 或 loopback HTTP，OAuth fetch 同时禁用凭据继承、缓存与重定向，防止恶意元数据把授权码、客户端凭据或令牌降级发送到远程明文 HTTP。动态注册信息、预注册客户端信息、access/refresh token 作为一个严格校验的 payload 整体加密，并与名称+URL 指纹绑定；单项损坏 fail-closed，不拖垮其它连接。PAT 与 OAuth 不允许并存，登录等待不占 Agent 运行锁；为保护同一配置事实源，期间只拒绝连接修改和会话删除，不冻结聊天输入、模型控件、会话新建/恢复或工作目录切换。退出只删除本机认证状态，当前已固化会话仍按既有“新会话生效”契约收尾。

GitHub 官方远程 MCP 不允许匿名访问，也不支持动态客户端注册；每个第三方宿主必须预注册独立 GitHub App 或 OAuth App。WhyCode 因而提供两条真实路径：用户现在即可保存 fine-grained PAT；发行版若通过 `WHYCODE_GITHUB_OAUTH_CLIENT_ID` 与 `WHYCODE_GITHUB_OAUTH_CLIENT_SECRET` 注入专用客户端，则同一通用 OAuth 控制器开放一键登录，并固定用 `client_secret_post`。桌面客户端的 secret 无法对本机用户真正保密，发布方必须使用专用 App、最小权限并接受 GitHub 的宿主集成边界，不能借用其它产品的 client ID/secret。默认 GitHub 只开放官方默认 toolset 的只读变体；即使以后开放写工具，也必须另做显式权限与审批设计。Playwright 仍等待固定运行时、隔离 profile、允许来源和页面授权。依据：[GitHub MCP Server](https://github.com/github/github-mcp-server)、[GitHub Host Integration Guide](https://github.com/github/github-mcp-server/blob/main/docs/host-integration.md)、[GitHub Policies & Governance](https://github.com/github/github-mcp-server/blob/main/docs/policies-and-governance.md)、[Context7 客户端配置](https://context7.com/docs/resources/all-clients)、[Context7 API Key](https://context7.com/docs/api-guide)、[Claude Code MCP](https://code.claude.com/docs/en/mcp)、[Codex MCP](https://developers.openai.com/codex/mcp/)、[Playwright MCP](https://github.com/microsoft/playwright-mcp)。

编码写工具保持单一结构化入口：`EditFile` 接受 1～50 个跨单文件或多文件的精确替换，每项都针对调用开始时的原始文件快照；默认 `oldText` 必须唯一，`replaceAll` 才允许全量非重叠替换，重叠、嵌套和顺序依赖在预检阶段拒绝。全部文件成立后才写入，写入异常会补偿本次已尝试文件。`DeleteFile` 一次接受 1～50 个普通文件，解析去重并全量预检后才删除；`MoveFile` 只移动单个普通文件，不覆盖现有目标并处理跨卷复制补偿。三个专用工具都走 edit 权限、会话副作用串行和 `exact-files` 检查点；新建或整文件重写仍使用 `WriteFile`。

`AskUserQuestion` 是普通 Main 的终止型控制工具，也是未完成任务的硬等待点：只有当前目标尚未完成、用户回答是继续完成该目标的必要条件时才能调用；问题必须实质改变下一步、不可自行查明且没有安全合理默认值。模型调用和持久事件都只接受根级 `{questions:[1..6]}` 批次，每题含一个短标题、一个问题和 2～4 个选项；缺少批次数组或携带旧单题顶层字段都会校验失败。Renderer 自动补自由输入，以回车或按钮逐题前进，最后一题才提交整批答案；成功产生一个 `user-question`，以 `waiting-user` 结束 turn 并保留活动计划。问题批次、assistant/tool 消息、TaskPlanState 与模型专用答案绑定在同一个稳定 step 原子提交，恢复后继续显示；任意新用户消息都会清除旧卡片。只有界面问题卡生成的精确完整回答、问题属于已接合 active plan 且状态未 interrupted 时才重新接合；硬中断必须先 Resume。普通输入始终按新的回合意图处理。任务已可交付时正常 completed，可选问题和后续方向只进最终文本；不得弹卡询问是否满意、是否继续。M1/B/C、协议回合以及完整协商任务期间不注册该工具。

`RunCommand` 负责不接受 stdin 的短前台命令：所有平台都关闭子进程 stdin；Windows 直接以 `-NoLogo -NoProfile -NonInteractive -EncodedCommand` 启动 PowerShell 5.1，避免无人可答的确认提示占满 120 秒，并显式透传原生命令退出码。中止和超时会清理完整进程树：Windows 使用系统树终止，POSIX 在独立进程组上先 TERM 后 KILL；Renderer 在收到 idle/error 前保持“停止中”并禁用重复提交。长命令由宿主级 `CommandSessionManager` 管理并给普通 Main 注入五个会话工具：Start/List/GetOutput/WriteInput/Stop。`StartCommand` 的默认 `detach=false` 用于有限的安装、构建和测试：工具持续等待终态、通过 `tool-progress` 回传增量输出，最终把末尾最多 64 KiB 的 Unicode 安全结果交给同一模型任务继续；用户停止当前 turn 时同步终止进程树。只有开发服务器、watch 或跨回合 stdin 任务显式 `detach=true` 并立即返回 taskId。工具返回前调用 `armTerminalNotification`：若进程已经终止，当前工具结果直接交付终态且不武装；仍在运行才记录仅存内存的可选 engaged plan ID，避免“工具返回 + 完成通知”双投递。任务先写稳 completed/failed manifest，再同步回调宿主；用户停止与应用退出不回调，超时按 failed 回调。通知只含 taskId、状态、退出码、命令/目录和有界输出元数据，完整日志仍由模型按需调用 `GetCommandOutput`，不复制 8 MiB 日志进上下文或 Renderer。

桌面 Main 用 `BackgroundTaskWakeQueue` 复刻 Claude Code 的 `run_in_background → Promise 完成 → task-notification → 新 query` 主链，但复用 WhyCode 已有运行时边界而不复制其实现：通知以 `(sessionId,taskId)` 去重，事件驱动地等待恢复租约、目标运行体、八任务全局名额和该运行体既有 FIFO 路由闸门；运行体 idle/error、用户输入路由、连接写入结束或恢复租约释放时再次 nudge，不使用 Sleep、轮询或第二份任务状态。未加载但可恢复的会话在后台构造并登记 `DesktopSessionRuntime`，不改变当前选中会话；删除目标会话会先丢弃待交付项。`AgentSession.handleTaskNotification` 把 `<task-notification>` 作为不产生用户气泡的内部 user 消息：Main 忙时在下一稳定 step 与真实用户消息同一原子提交边界注入，真实用户消息保持 FIFO 优先；Main 空闲时开启隐藏 turn 并沿用 `work-started/work-finished`、JSONL 和正常模型流。只有通知携带的 plan ID 仍等于当前 active plan 且未 interrupted 时，才复用既有 task continuation 接合执行；旧、已替换或 interrupted 计划只把结果交给模型，不恢复执行权。已武装同计划通知在 running 以及“终态已写稳、通知尚未发出”的窄窗口都算待 continuation：模型中途停止时保留计划，终态续轮的最终正文再自然结束。提问卡等待期间，通知继续保留在宿主队列，不越过 `AskUserQuestion`。应用退出信号可打断通知对前序输入闸门的等待；交付失败保留队列项等待下一事件重试，并由所属运行体显示可恢复错误，不污染当前对话。

任务仍按 sessionId 隔离，日志和 manifest 写入 `userData/command-tasks/{sessionId}`；显式脱离任务在切换会话后保留运行，删除会话先停任务，应用退出终止全部进程树。正常重启恢复日志/终态，但不重放此前未交付的内存完成通知；异常 running 标为 interrupted，不按 PID 重连。输出最多保留 8 MiB，读取使用 byte offset+最长 30 秒等待，stdin 支持 EOF；终态每会话保留最近 16 项。Manager 从同一任务事实投影全部 `StartCommand` 的有修订号 `BackgroundTaskState`，只包含类型、截断命令、状态、起止时间、短失败原因及当前是否会自动续轮；默认等待和显式脱离的长任务都进入 Header，只有已武装终态通知的运行项显示续轮铃铛。Main 以整表 IPC 推送，RuntimeSnapshot 提供恢复基线，Renderer 最多缓存 8 个非当前会话的最新整表以处理切换竞态，不另建任务注册表。M1/B/C 与协议回合物理移除后台工具。前后台命令都不扫描工作区、不建立文件检查点，并形成 none 边界；跨边界只允许恢复专用工具跟踪且未被后改的文件，不能同时截断对话。本轮没有修改会话 schema，也没有增加旧对话兼容分支。

### 5.4 上下文管理（已实现，M2-d 定型；`core/src/context/`）
- 用户自定义 System 不进入含密钥密文的应用托管 `~/.whycode/config.json`，也不进入 Renderer 设置。Electron Main 在同目录缺失时一次生成独立 `system-prompt.json`（严格 `mode:off|append|replace` + `file`）和空白 `SYSTEM.md`，之后不覆盖；它是自定义 System 配置的唯一事实源。仅在新 journal 创建前读取配置，off 不读取正文，append/replace 再解析相对或绝对路径并执行 UTF-8 与 32 KiB 校验，把严格 `{mode,content}` 交给 Core；当前 journal 已存在时绝不重读。`buildSystemPrompt` 在请求边界按 append/replace 组合固定快照；只给 Main，独立 B/C 保持自身 System。
- 项目指令由 `core/src/instructions/project.ts` 确定性发现：全局只读取 `~/.whycode/AGENTS.md`；项目从当前目录向上寻找最近 `.git` 文件或目录作为根，无 Git 时只使用当前工作目录。随后按根→当前目录逐层选择文件；每个目录先尝试 `AGENTS.override.md`，存在时不再读取同目录 `AGENTS.md`。最终顺序是全局→项目根→子目录，后出现的深层规则优先；直接用户要求仍高于这些持久规则。内容总预算为 32 KiB，超限时优先保留更深层内容并显式标记截断，UTF-8 字符不会被切坏。
- 合并文本带内容 SHA-256，包装成唯一 `<whycode-project-instructions>` 内部 user 消息。AgentSession 在新 turn 起点以及后续每个模型请求边界惰性读取，不使用 watcher、轮询定时器或缓存；未变化不写新事件，变化后下一次模型请求立即使用新版本。System、工具 schema 和普通历史前缀仍保持稳定；文件变化本来就是明确的合法前缀重建边界。
- 计量：`AgentSession` 只维护一个上下文压力函数，自动压缩和 live UI 都直接读取它。有最近 API usage 时使用该次 `input+output` 基线，加上未被覆盖的新消息增量；宿主在响应后追加的 tool result、页面图和控制标记不能误算进基线。没有基线或历史被改写时，才以 System、工具目录和全部消息确定性粗估（CJK /1.7、其余 /4）。消息块顶层及工具结果载荷上的 `providerOptions` 属于协议签名、加密推理载荷等元数据，不按序列化字符计量，其真实影响由后续 Provider usage 覆盖；工具参数内部同名业务字段仍按正文计算。图片固定估算 3,000 token，绝不按 Base64 字符数计量。阈值 = `窗口 − min(输出上限,20k) − max(13k, 窗口7%)`；每次模型请求前检查。
- 上下文用量 UI 不建立 Renderer tokenizer：`usedTokens` 就是上述唯一压力值，不再把 Provider 基线与本地分项相加或取较大值。解释分项复用真实请求的 `buildSystemPrompt` 和 AI SDK 工具 JSON Schema，并按当前稳定消息投影估算；单个异常 schema 只降级为名称/说明估算，不能阻断请求。分项只解释近似构成，不要求相加等于 Provider 锚定总量。`autoCompactThreshold` 随同一个 live 事件下发；Main 模型切换时旧基线立即清空，turn 冻结期间不把旧模型窗口显示成新模型窗口。
- 分级压缩：自动与手动入口都先执行同一 microcompact——白名单工具（读/搜/命令/写）的旧结果替换为占位，保留最近 5 个且幂等冻结；自动压缩若已降回阈值内便停止，手动压缩继续按需尝试完整压缩。任何自动微清理只要改写了活动消息，即使完整摘要未发生或失败，也立即提交统一 `compact` snapshot，避免内存请求历史与重启/Fork 恢复历史分叉。完整压缩从末尾按约 20k token 选择逐字保留区，不再要求固定文本消息数量或回退到完整 user turn；切点允许位于 user/assistant，命中 tool result 时向前扩到其 assistant tool call，保证调用与结果配对，未消费中断、问题卡和尾部输入批次仍逐字保护。若保留区已包含真实用户输入，只生成被逐出完整历史的九节摘要；若仍处于同一过长 turn，则另以独立请求生成 Pi 式“原始请求/早期进展/后续所需上下文”前缀摘要。重复压缩只基于当前活动上下文增量更新两类摘要，不回读已丢弃原文；历史摘要不声明当前工作或下一步，最新状态只以逐字尾部、canonical TaskPlanState 与应用上下文为准。压缩后继续重注入最近 5 个读过的文件（50k/单文件 5k）。
- 未来深入方向（不属于当前实现承诺）：只有真实长会话暴露摘要质量或预算估算偏差时，才基于 transcript 调整提示或估算常量；不预加 tokenizer、摘要模型设置、Provider 特判或第三类摘要状态。
- 熔断：连续 3 次失败停止自动尝试并只提示一次可恢复错误，成功清零；不能像旧实现一样静默停用。手动压缩（`compactNow`）不看阈值，期间消息排队、完成后接续。压缩后旧对话回滚锚点失效（仅文件回滚可用）。
- 尚未消费的回合中断标记和计划问题绑定标记属于压缩保护边界：摘要只能处理其前缀，标记及之后的新消息逐字保留；摘要提示词不得把“已中断”请求重新写成待办、当前工作或下一步。
- 项目指令不进入摘要源：摘要模型只把当前精确版本作为控制上下文执行，提示词明确禁止复述、改写或归纳；压缩完成后 AgentSession 再读一次文件系统，并把当时最新原文直接放回索引 0。即使文件在摘要生成期间变化，持久快照也只保存压缩结束时的新版本。
- 全量压缩按“内部 compact summary（历史摘要 + 可选 turn 前缀摘要）→ 约 20k 逐字安全尾部 → 文件与 canonical TaskPlanState 应用上下文”重建；尾部若有尚未处理的后台通知、真实 user 或 steering 批次，应用上下文放在整批之前。TaskPlanState `version>0` 时重注入当前状态，包括已结束计划的 `active_plan:null`；`version=0` 的纯对话不制造空状态。只有同一 engaged 自动压缩才附带绑定 `turnId + engagedPlanId` 的 continuation；interrupted/dormant/手动压缩没有 continuation，摘要文本也不能授予执行权。快照原子保存 messages+TaskPlanState，但压缩本身不增加 state version。
- 内置 System、会话起点固化的自定义 System 与整套任务工具 schema 在会话内保持字节稳定，任务 ID、版本、进度、执行边界和提醒只走 `<system-reminder>` 或工具结果。正常状态变化只追加消息；micro/full compact、模型/Provider、项目或协商模式变化才是合法前缀重建边界，避免普通轮次击穿 Anthropic 前缀缓存及 OpenAI/DeepSeek 自动缓存。

### 5.5 多 Agent 协商（已实现，M3 定型；`core/src/consensus/`，协议见 multi-agent-decision-protocol.md）
- **Orchestrator**（orchestrator.ts + full-consensus.ts）= 纯 TS 控制面（非 LLM）：M1 锁定 protocol_mode → main_only 直接放行 / quick_review 一轮快评 / full_consensus 三轮（独立初判 → B1/C1 评 M1 → M2+交叉投票计票 → session_score 兜底）→ 执行包一次性注入 Main。计票/兜底为纯函数（passesRound1/countRound2Votes/round3Winner），离线断言 15 例。
- **模式升级**（协议 §1.1，控制面正则只升不降）：用户显式要求讨论/共识（含“三agent / 3 个模型 / 三方评审”等写法）或硬性风险词（数据迁移/删库/生产环境/支付）→ 在 M1 请求前锁定 full_consensus，并用收窄后的协议 schema 拒绝模型降级，避免工具卡模式与实际流程不一致。
- **B/C** = 受限 AgentSession（peer-agent.ts）：与 Main 使用同一全局/项目指令发现规则，但仍服从讨论档只读项目与 scratch 写边界；每个协商任务使用 `userData/scratch/{sessionId}/consensus/{taskId}/{Main|B|C}/`，任务内跨轮保留会话，任务结束丢弃只留 memory_summary（memory.ts，从协议输出直接提取零 LLM 调用，**不持久化 scratch 临时路径**）。协商产物随会话 scratch 保留到删除会话，供恢复、后台唤醒和 Fork 使用；应用启动只清理没有任何会话事实的孤儿 session 目录，不再全量清空。下任务首轮注入记忆 + 任务脉络摘要（最近 6 条，含 main_only 任务，补"刚才那个"类指代）。
- **协议输出** = 合成工具（protocol-tool.ts，借鉴 Claude Code StructuredOutput）：Zod schema 按轮次动态生成借 tool-calling 约束格式，工具层校验协议规则（target 存在/reason 非空/reject 必带 suggested_change/mustVote 恰一票），不合规回错误让模型自动重试；回合结束未提交注入提醒 ×2 后判 invalid；invalid → 降级 Main 终判（永不卡死）。
- **终止语义与通用任务**（2026-07-10 修正；2026-08-09 工作区统一）：`SubmitProtocolOutput` 成功即终止协议 turn，不再请求模型生成工具后总结；正式协议回合的普通文本不进入主聊天/Peer 卡片，但 Main 的 provider reasoning 仍正常显示。进入 B/C 评审时，候选事件携带任务方案、证据和风险供 UI 默认展开；`main_only` 只显示实质摘要并由执行回合交付完整答案。WhyCode 允许非编程任务；未显式选择项目的会话先物化独占受管目录，Main/B/C 不再存在 projectless 工具装配分支，讨论角色统一由项目只读与 scratch 写入权限约束。
- **模型角色（用户定案 2026-07-04；2026-08-07 连接收口）**：整个应用只有三个模型位——**Main 永远 = 顶栏当前模型**（普通对话、简单问题、协商发起与执行都是它，上下文全程连续，中途开关协商不断档）；B/C 仅在协商时加入。设置页从当前已配置且可解析的统一模型连接中分别选择 B/C，config.json `consensusAgents{B,C}` 只保存 `modelId`；运行时统一经 `resolveModelConnection` 取得同一个模型画像、协议、端点和凭据。两项都有效才可开启；删除或失效的连接会清理对应引用并关闭协商可用态，不回退到别的模型或独立连接。
- 与早期设想的差异（有意为之）：B/C 不创建 worktree（用户项目未必是 Git、B/C 不产出待合并代码）→ 按需复制进 scratch；Main 是否使用显式 Worktree 由会话工作区选择决定，但不改变 B/C 的读项目、写 scratch 边界。B/C 过程不写独立 transcript → 走 peer-event 包装进主事件流（UI 折叠卡片）。

### 5.6 持久化资源检查点（2026-07-10 重构；`core/src/checkpoints/`）

- **事实源与生命周期**：`sessions/{sessionId}/checkpoints/manifests/` 保存版本化 before/after 资源清单，`blobs/` 保存精确文件内容；两者完全归属该会话，不使用项目级共享仓库。删除会话随事实源目录一并删除目标检查点，不触碰同项目其它会话或项目文件；应用启动清理旧版本遗留且已退出事实源的共享命令快照目录。
- **覆盖契约**：WriteFile/EditFile/DeleteFile/MoveFile 声明 `exact-files`，直接捕获普通文件或 missing 状态，不受 `.gitignore`/排除表限制，额外授权路径同样覆盖；移动同时覆盖源与目标。RunCommand/StartCommand 及其它未声明精确范围的写操作不建立回滚点，只形成 `none` 边界。跨边界的“仅文件”恢复仍可处理明确路径并执行 after 冲突检测；“文件+对话”会被拒绝，命令副作用保留。之后的新精确检查点可独立恢复。
- **诚实 UI**：每个完整精确检查点仍保存在 `ToolCall.hasCheckpoint` 与 manifest 事实中；Renderer 依据既有 `turn-start` 边界，只把每轮最早的有效检查点投影为“回滚本轮”，同轮后续工具不重复显示入口。入口仍提供“仅文件 / 文件+对话”，命令卡和 partial 覆盖都不显示；检查点失效后由同一投影自然消失，实时与重放共用 reducer。该收口不修改 CoreEvent、ViewEvent、JSONL 或恢复引擎。RunCommand 成功但没有 stdout 时显示“命令成功，无标准输出”；需要交互的前台命令快速返回非交互错误，不再让空输出看起来像卡住。
- **冲突与事务**：恢复目标会连同本会话更晚的有效精确 manifest 逆序撤销。写入前只捕获 manifest 中的明确路径并与最后一个 after 比对，用户或其他会话后改即拒绝；随后逆序应用并校验最终状态。资源、会话 rollback 新根、manifest 失效三者属于同一补偿事务；失败会恢复文件和原对话。Renderer 把正在回滚的 toolUseId 提升为全局交互锁并纳入 runtime snapshot，完成/失败事件均清除 pending；回滚不可取消，因此界面显示专用文案而不提供无效的停止按钮。
- **对话边界**：SessionJournal 持久化活动父链上的 turn 起点；“文件+对话”从目标 turn 第一个检查点恢复，压缩前或不在当前父链的 turn 仍只允许文件回滚。rollback 新根保留新根内更早 turn 的边界，重启后可继续回滚。
- **未来深化（非当前排期）**：Local 跨会话工作区级写/恢复 FIFO 与显式 Worktree 隔离均已完成；后续只有出现真实交付需求时再增加 handoff/合并冲突预览、孤儿资源可视化与存储配额/GC。检查点 diff/浏览继续按真实需求推进，不复制 Git 的提交或合并职责。

### 5.7 权限模型（已实现，M2-b 定型 + M3 讨论档；`core/src/permissions/`）
判定链顺序不可换：Windows 可疑路径拒绝 → **普通 Main 的显式全自动直接放行** → **普通 Main 只读档硬拒绝 edit/execute** → 讨论档项目/scratch 硬边界 → 聚合敏感路径与全部越界路径 → 角色、会话记忆和默认档位策略。只读拒绝发生在首次隐私/外部信任审批之前，因此项目内外的写入、命令、`WriteCommandInput` 与实际 MCP 工具都没有授权入口；项目外 read 仍按路径审批。讨论档只能读和在显式 scratch 边界内修改/执行，未声明路径的 edit/execute 也 fail-closed。显式全自动继续零弹窗，但 Windows 可疑路径和 discussion scratch 边界都不能被放宽；被放行调用的精确外部路径只注入该次工具上下文，不扩大后续工具权限。普通会话创建 AgentSession 时必有真实工作目录，权限引擎不再承担“无项目能力”分支。

工具执行边界为项目根和每个 `additionalDirs` 同时保留词法根与真实根：请求路径必须位于某个原始允许根内，其最深现存祖先解析后的真实路径也必须位于某个允许根的真实边界内。这样显式授权的符号链接或 Windows 目录联接可以按原路径使用，但不会顺带授权其真实目标的直接路径；允许根内部再次经链接逃逸时，即使后代尚未创建也会被拒绝。真实路径无法可靠解析时 fail-closed。

普通 Main 的会话 scratch 根在 AgentSession 创建时一次加入固定路径边界，与用户审批后追加的目录共用 `additionalDirs`，但不是临时审批记忆：运行体卸载、恢复或后台唤醒后仍从 `sessionId` 派生同一路径。只读档仍拒绝其中的 edit/execute，默认档仍按工具类型审批，自动编辑/全自动仍沿用原档位语义；只有“是否越出允许根”不再因 scratch 位于项目外而产生误导性的 add-dir 审批。

首次隐私/外部信任与常规权限共用 `checkToolAuthorization`：硬拒绝优先；同一次调用同时涉及默认写权限、首次外部执行、敏感路径或项目外路径时合并为一张卡，展示完整原因和精确输入。一次模型步骤中的多个 ask 调用由 `StepToolApprovalBatcher` 在各自独立判定后合并成一张精确清单；批准或拒绝只覆盖清单中的调用，异构记忆建议不提供“本会话记住”，后续模型步骤重新判定。批准后以及真正进入副作用队列前都按当前档位重查不可审批的硬拒绝，避免等待期间切入只读后继续执行。

四档权限选择属于应用偏好：Main 先把新档位应用到当前运行体和新会话默认值，再异步写入 `~/.whycode/config.json`，消除 UI 已显示只读但旧审批仍可执行的窗口；保存失败会明确提示“当前会话已生效、重启可能恢复旧偏好”。切入只读会拒绝并清空待审批，切入全自动会通过并清空待审批，默认/自动编辑保留用户正在处理的决定。具体工具、路径或隐私审批不持久化；“本会话记住”仍只在对应 `DesktopSessionRuntime` 内存中生效。

### 5.8 会话持久化（已实现，M4 定型；`core/src/session/`）
- **Fork 完成边界**：`turn-end(status=completed)` 只表示模型 turn 已稳定提交；可 Fork 的完整工作还必须有随后持久化且指向同一 turn 的 `work-finished(outcome=completed, forkTurnId)`，并且该 turn 的最后一个模型 step 是不含工具调用的非空 assistant 最终正文。Renderer 只在这个最终正文的最后一个 block 展示分支图标；`/` 的“在新对话中继续”只在会话空闲时出现，并选择当前时间线中最新的同类边界。运行中、停止、等待用户、错误、未提交输出、纯工具完成以及同一步文本+工具输出均不暴露入口。
- **精确上下文复制**：Core 以选定边界为终点重建当前 JSONL 活动链，复制当时真正进入模型的 messages、压缩快照、任务状态、MCP 状态、冻结 Skill 与交付事实，不发起模型摘要，也不把界面文字重新包装成新请求。边界之后未交付的 queued/restored 草稿不进入子会话；若历史草稿已经在边界前被消费，只保留维持事实链所需的原身份并清除 pending 资格。
- **独立会话与有限血缘**：新会话拥有新的 session 身份以及独立 JSONL、附件字节和检查点清单；复制前缀的 entry UUID 与模型上下文中的稳定附件 ID 保持不变，只把所属 session 改为新会话，避免破坏历史事实链与引用。源会话不删、不改。`forkOrigin` 只保存稳定 family、源 session/turn、序号、基础标题与创建时间，用于 `标题（2）/（3）`、来源提示和诊断，不参与 Agent、任务计划、后台任务或授权的 owner 判定。
- **运行时隔离**：Fork 创建全新的 `DesktopSessionRuntime` 并立即选中。源会话已经运行的后台命令及其完成唤醒继续按原 sessionId 投递，不复制、不阻塞 Fork；会话内审批记忆重新开始，持久 MCP 状态可复制，但项目配置的临时信任在所有消息与快照容器中统一清除并于子会话重新判断。来源会话的完整 scratch 树同时复制到新 sessionId，后台进程仍只写来源目录；新 System 提供来源根到当前根的相对路径映射，历史消息不改写，也不会继续访问来源目录。
- **工作区与资源生命周期**：Local 仍引用用户目录。Worktree 使用 manifest v2 的 `sessionIds[]` 显式引用计数，只有显式 Fork 可以附加第二个 session；普通恢复若发现已有其它会话引用则 fail-closed，删除最后一个引用才清理工作树。非项目 managed 会话保持单会话所有权：Fork 先把来源目录复制到新的受管 UUID 目录，再把新 `session-start` 与检查点中的工作区内绝对路径切到目标快照；之后父子修改和删除互不影响。附件、检查点、会话事实源与 managed 快照都在失败时回滚，不能留下半成品或改变源会话。
- **存储模型**：`userData/sessions/{sessionId}/transcript.jsonl` 是唯一结构化事实源；记录带 schemaVersion、UUID、parentUuid、时间戳并经 Zod 校验。当前 schema v11 沿用既有 Skill 冻结快照、图片交付事实、必填 `WorkspaceBinding = none | local | managed | worktree`、`forkOrigin` 与 `work-finished.forkTurnId`，并以单一活动 `TaskPlanState` 表示计划；TaskItem 只接受 `pending|in_progress|completed`，计划终态只接受 `completed|ended`。根输入、steering、queued/restored/delivered、重启、中止后编辑与 Fork 都读取同一交付事实，不从当前配置反推历史路由。输入仍可保存最多 8 个完整 `ActivatedSkill`，压缩快照仍保留 `activeTurnEngagedPlanId`、完整 `TaskPlanState` 与待处理输入；图片与 PDF 原字节统一放在 `attachments/`，JSONL 只保存经校验的元数据和内部引用。v10 及更早开发会话不迁移，只保留 unavailable/delete-only 入口；不增加默认值、双读或旧任务/工作区/图片路由分支。`metadata.json` 只做可重建列表缓存，transcript 已 flush 后若缓存刷新失败会删除旧缓存，由列表/open 从 JSONL 重建。
- **自定义 System 快照**：`session-start.customSystemPrompt` 是可选的严格 `{mode,content}`，在首个模型请求前与会话起点一次写稳；没有字段自然表示仅用内置 System。JSONL append-only 永久保留该起点，即使活动 parent 链由 compact/rollback/recovery snapshot 换根，恢复仍从原始 start 读取同一份快照，因此压缩记录不复制字段、不引入版本事件或兼容状态。删除会话时它随 transcript 一并删除。
- **项目指令版本**：schema v4 追加 `project-instructions` 事件；每次实际内容变化写一条带 SHA-256 的完整消息，删除全部指令文件时写 null tombstone。JSONL 原始事件 append-only 保留历史版本供审计，但活动链重放、AgentSession messages、turn 起点和活动共识基线共用唯一替换函数，所以实际模型输入始终只有最新一条且固定在索引 0。首个 turn 的指令变化与 `turn-start → messages` 在同一次 flush 中提交，不插断根输入交付判定；后续变化在模型请求前 fail-closed 写稳。snapshot 只保存规范化后的当前版本，不复制第二份运行时状态。
- **双投影、单一事实源**：活动模型上下文从 parentUuid 活动链重建；用户可见时间线从全部 `view-events` 记录按写入顺序重放。模型压缩只换活动模型根，不删除旧界面；文件+对话回滚由可见时间线中的 `checkpoint-restored` 事件重放截断。没有第二份 Renderer 快照文件。
- **提交边界**：图片先在 `.image-import-*` 私有目录完成有界读取、魔数/尺寸预检、像素级完整解码和 SHA-256，再通过 rename 提交原图；任一失败回滚整批，启动/open 还会清理 staging 和事实源未引用的文件。文件选择交付绝对路径；无路径剪贴板截图只在一次性 JSON-safe IPC 命令里携带有长度上限的 Base64，落盘后立即丢弃传输副本。每条用户输入在交给 Agent 前以稳定 UUID 写入 `user-input`：根输入用 `startsTurn=true`，运行中输入进入 pending queue；根输入只有进入完整 `turn-start → messages` 或 `consensus-task-start` 才算已交付，`turn-start.rootInputId` 精确确认被 ViewEvent 等记录隔开的根输入，steering 的 delivery ID 则必须与实际模型消息放在同一 `messages`/共识起点中原子确认。退回草稿先写 `user-input-restored`，重提时新 `user-input` 原子消费旧 ID；任何关键 delivery/step/恢复写盘失败都 fail-closed，模型和 UI 不得越过事实源。每个稳定 step 的 assistant/tool 消息、问题绑定、engaged plan ID、可选 TaskPlanState，以及该 step 由 `ViewImage`/`CaptureScreenshot` 新导入的附件元数据放在同一条 `messages` envelope；中止/异常回收未提交图片。图片在活动历史、回滚起点和快照里始终只保持引用；首次读取、进程重启或 transcript/附件集合/源文件磁盘身份变化时，对全部历史附件重新执行完整解码、摘要和结构校验，只有同一进程内已经完整验证且身份未变的相邻 open 才复用该结论。只有原生视觉 Main 请求或 `AnalyzeImage` 的独立辅助请求边界才水合本次所选字节。尾行半截时整步丢弃；`step-committed/step-discarded` 同时约束 JSONL/ViewTimeline 与 Renderer 实时投影：实时 reducer 在首个 step-scoped 事件保存稳定快照，提交时固化、丢弃时恢复。用户硬停止时先发 `step-output-retained`，ViewTimeline 与同一个 reducer 只写稳/恢复当前 step 已展示的正文，推理、工具、问题卡与任务状态仍由紧随其后的 discard 撤销；urgent、异常和不可交付响应继续全量丢弃。稳定 ViewEvent 重放不进入实时事务。turn 终点记录 stopReason；JSONL append 按会话串行并 flush。压缩、文件+对话回滚和崩溃恢复追加 parentUuid=null 的新根快照，不改写旧事实。
- **损坏处理**：只容忍最后一行 JSON 被截断；被容忍的坏尾会先物理截断并同步，完整 JSON 末行缺换行会先补分隔符，再允许后续 append。中间坏行、完整但 schema 非法的尾行、重复 UUID、断裂/循环父链、混入其他 sessionId、非法活动根均拒绝恢复。会话列表只对未打开的历史项从 transcript 重建；`DesktopSessionRepository` 把全部已打开 Journal 的实时 metadata 一次传入 Core，删除标记仍优先，但活动项绝不调用 `open()`。这是所有权边界而非 UI 兜底：`open()` 会执行崩溃尾行修复、附件完整校验和 staging/孤儿清理，只能用于没有内存所有者的会话，不能与后台附件提交并发。合法 UUID 目录即使因旧 schema 或损坏无法打开，也用匹配同一 sessionId 的 metadata 降级成 `resumable=false` 摘要，仅供展示与删除；非 UUID 目录继续忽略。
- **安全恢复**：未闭合 turn、活动共识或尚未交付的根输入标记 interrupted，但不重放任何工具/审批；恢复新根保留根输入一次并追加 `process-interruption`。尚未 delivery-ack 的 steering 在恢复快照中从 queued 原子变为 restored，不自动注入模型；已确认送达但即时事件缺失时，重放器只在原交付位置补一条可见消息。停止、共识失败或不能安全接续时同样先持久化 restored，再按原消息边界退回草稿。turn 级 engaged plan ID 只用于判断崩溃是否应让匹配 active plan 写入 `resumeRequired`；dormant 计划保持原状态。共识任务起点锚定原始请求、任务前 messages+TaskPlanState 及此前有效 turn ID，失败/取消回到安全基线。只有绑定同一 turn/plan 的压缩 continuation 能让当前 runLoop 在自动压缩后延续。问题 step 已稳定提交但 turn-end 前崩溃时恢复为 `waiting-user`，但 interrupted 闸门仍优先；文件+对话回滚到提问点也恢复问题卡与 TaskPlanState。
- **恢复与选择生命周期**：Main 用 `SessionRuntimeRegistry` 把当前选中运行体与仍在后台执行的运行体分开。恢复磁盘会话前仍同步取得带目标 sessionId 的全局选择租约；`prepareResume()` 完整验证 Journal/附件并构造候选 `DesktopSessionRuntime`，成功后才一次登记并选中，失败不改变原选择。若同一 sessionId 已有运行体，选择只切换指针，不重建或中断 Agent。若历史 `modelId` 已退役，仍建立只含 Journal 的运行体并展示完整时间线，不回退模型或改写 JSONL；用户明确切换后才构造 AgentSession。新建、恢复、删除当前会话和切目录的 IPC 成功结果直接携带同一边界 `RuntimeSnapshot`，不再让 Renderer 在选择完成后另发第二次快照请求。快速双击和选择期间的旧运行体命令由 Renderer 同步事务锁阻止。

  `RuntimeSnapshot` 同时公开 runtimeId、sessionId、稳定可见事件、当前未提交 step、queued/restored 输入、审批、连续工作起点 `workStartedAt` 和事件游标。`ViewTimeline.snapshotAt()` 先排空已提交写入，再按真实捕获顺序合并 Main/B/C 瞬时 step，并在同一个同步边界读取全局事件序号；Renderer 只重放该游标之后的事件，避免快照与实时流之间缺口或重复。后台事件携带 runtimeId/sessionId，不能改写当前界面，只触发历史状态刷新；切回时先应用快照，再按序消费快照边界后的有界缓冲。Renderer 热重载也复用同一路径，切换、恢复或重连均不向真实时间线追加合成提示。非选中运行体变为空闲后保留 30 分钟再关闭 AgentSession/MCP/WebFetch 并释放 Journal 内存，重新选中会取消卸载；切走时仍在运行的对话从真正转为空闲时开始计时。脱离命令完成通知可以在不选中目标会话的情况下复用或后台恢复其运行体并开启新工作；完成后的 idle 事件继续从零开始同一 30 分钟卸载计时，不另设永久后台运行体。运行中、审批中或附件准备中的运行体保留，应用退出统一中止并等待清理。会话列表的附件校验结果仍只以进程内磁盘身份签名缓存，签名变化即失效。

- **连续工作计时与最新根编辑**：计时由 `DesktopSessionRuntime` 在根输入被权威接受时只启动一次，排队 steering 与自动续 turn 不重置；live-only `work-started` 和快照起点驱动 Renderer 每秒派生显示，不把 tick 写入协议或 JSONL。进入 idle/error 或交付异常时先发持久化 `work-finished(durationMs,outcome)`；正常结束固定显示“已处理 Xm Ys”，只有用户发起的 abort 写 `outcome=stopped` 并显示“你在 Xm Ys 后停止了”，应用关闭不伪装成用户停止。会话空闲且没有待处理输入时，时间线中最新根用户消息可原位编辑，无论旧任务是正常完成还是中途停止；运行中、旧根消息和非根 steering 不开放编辑。Main 复用普通输入 reservation，先排空 ViewTimeline，再让 Journal 在一次 flush 中追加 `rollback` 新根和带 `replacesTurnId` 的新 `user-input`；旧物理分支保留审计，活动 messages/TaskPlanState/turn 锚点、协商累计状态、Skill 与附件回到目标任务首个 turn 前，新根以稳定 input ID 交付。实时 `user-message-edited` 与重放从 `replacesTurnId` 派生的同一事件都走一个 reducer：截断旧任务输出、在原 block 位置替换根消息并让新 `turn-start` 复用该锚点，不建立独立“已编辑消息”存储；完整交互约束见 §5.14。

  连续工作的折叠只使用现有 Renderer 投影，不增加 CoreEvent、IPC、会话字段、迁移或平行时间线。流式 `text-delta` 先保持 pending；Core 消费完整个模型步骤并发出 `step-committed` 后，Renderer 检查该步事实：出现工具则正文归入 activity，没有工具的纯文本步骤归为 final 并收起此前过程。这个判断正是“纯文本返回即最终回答”，但权威结果只能在完整流结束后得到；同一个 assistant step 可以先发文字、随后再发工具，不能在首个文字增量到达时把“尚未看到工具”当成“不会再有工具”。历史重放在 `work-finished` 边界使用同一稳定终态分类。

  `work-duration.outcome=completed|stopped` 继续共用同一个工作区结构和时长开关。只有当前工作存在已提交的 `phase=final` 正文才默认收起；问题卡等待、纯工具完成、无最终正文错误和执行中停止都保持展开。用户在最终正文阶段停止时保留已展示正文并冻结停止瞬间的收起状态，手动展开同样不被终态反向覆盖；推理、工具和其它未提交状态继续撤销。摘要出现后输入区上方同一计时隐藏，工具卡仍用原 block ID 二次展开。`step-output-retained → step-discarded` 的既有事务顺序不变。

  会话切换仍以 ViewEvent 重放为消息和默认展开的唯一事实源；Renderer 另外按稳定会话身份保留本进程内的展示偏好，只把用户手动开合以覆盖值叠加到重放结果，不冻结整个默认集合，因此离开期间新增的工作仍遵循上述统一规则。滚动恢复同时区分贴底与向上阅读：阅读态保存工作段、正文块及其顶层 Markdown 内容身份和内容内偏移；切回时在 `useLayoutEffect` 中临时物化目标及其之前的已完成 `content-visibility` 段，并仅在目标后的估算内容不足一屏时继续物化到可承载目标位置为止，以真实累计段高在首次绘制前完成一次定位。目标前后段写入实测固有高度后立即恢复离屏优化；锚点所在段则由同一次恢复事务保持真实渲染，直到它离开滚动视口或会话被切走才释放，避免 Chromium 在首次绘制前重新采用占位内容。没有可用锚点才回退到有界 `scrollTop`，不使用内容类型特判、跨帧二次跳转、隐藏整页或整条时间线物化。贴底态观察时间线内容尺寸，Markdown、公式或离屏段从估算高度变为真实高度时继续定位到底部，因此应用重启后的所有会话统一从底部开始。展示缓存以 LRU 严格限制为最近 32 个会话，每个会话最多 256 个显式开合覆盖；被淘汰或应用重启时自然回到上述底部和投影默认值。展示偏好不进入 Core、IPC、JSONL 或会话 schema，删除会话时随草稿缓存一并清理。

  未来深入方向（非当前承诺）：如果以后仍要求“最终正文首字到达即收起”且不允许误判，前提是全部受支持模型协议提供可在首字前验证、并能排除随后工具调用的原生语义边界。当前不新增控制工具，也不退回首段/措辞特征、定时器、强制 `tool_choice` 或 Provider 分支。

- **并行所有权与共享宿主资源**：每个 `DesktopSessionRuntime` 独占 WorkspaceBinding、Journal、AgentSession、Coordinator、MCP 状态、WebFetch 页面缓存、模型/推理、审批、路由闸门、附件事务、状态和可见时间线；命令、事件、快照、模型列表与 PDF 打开均以 runtimeId 路由。权限引擎仍在每个运行体内持有并执行当前档位，但应用级权限偏好是全局事实：设置时先同步更新 Registry 中全部已加载运行体，再持久化为新建/恢复运行体的首选档位，任何一个对话切档都会立即反映到其它对话；会话审批记忆仍不共享。最多 8 个 Agent 同时工作；Registry 在任何异步输入准备前通过目标运行体既有的 FIFO 路由闸门原子预留工作名额，避免多个并发 IPC 同时观察到空位并超限。预留者到达队首后再按真实执行态判定 root/steering，因此前一条输入准备失败时不会把后一条误当作插话；达到上限只拒绝新的根任务，不阻断已忙会话的 steering。宿主管理的 `CommandSessionManager` 继续按 sessionId 隔离长进程并跨 AgentSession 存活。全局连接设置在任一运行体忙碌时 fail-closed，避免一半请求使用新配置；MCP 结构或认证修改等到运行体重建才生效。

  Local 模式中，同一真实项目路径的 `edit`/`execute` 工具和检查点恢复进入一个宿主 FIFO；权限判定、同一步审批聚合与用户等待发生在该副作用锁之外，不会因一个审批卡阻塞同项目其它会话。精确批准后，FIFO 覆盖最新硬边界重查、检查点准备、执行与 finalize；等待或排队期间取消都绝不执行副作用。路径先取 realpath，Windows 再大小写归一；不同项目互不阻塞。截图使用独立全局队列，防止多个会话的宿主窗口排除事务交错。只读工具仍可并发。只有显式 `detach=true` 后继续存活的长驻进程不受工具调用期 FIFO 约束，因此 Local 仍是共享目录/共享进程语义，不能描述成进程级沙箱；默认等待的有限 `StartCommand` 始终属于当前工具临界区。

  会话 schema v11 继续以判别联合 `WorkspaceBinding = none | local | managed | worktree` 作为已建立会话的唯一工作区事实，并保留既有每条图片输入 `native|auxiliary` 交付事实；`DesktopSessionRuntime` 不保存第二份可变 projectDir，恢复也不按当前模型能力重算图片路由。首条消息前，运行时快照可以携带不属于 schema、没有执行目录的 `pending-managed` 或 `pending-worktree`。`managed` 固化 runtime UUID、受管子目录与创建时间，并由单 session manifest 表达独占所有权；Worktree 固化受管 ID、原仓库、受管根、仓库内相对工作目录、精确 base commit/ref 与创建时间，由 manifest v2 的 `sessionIds[]` 表达显式 Fork 引用。Agent prompt、项目指令、Skill 项目目录、MCP 项目配置、权限基准、文件工具、前后台命令、宿主写队列、附件与检查点统一使用物化后的真实目录。v10 及更早开发会话不迁移、不补默认值，仍只以 unavailable/delete-only 形式存在。

  `WorktreeManager` 只接受 Git 仓库且已有 commit 的显式请求。检查阶段一次读取当前 HEAD、当前符号分支和按名称稳定排序的 `refs/heads/*`，形成唯一 `WorkspaceCandidate.worktreeBases`：当前分支置顶，其余本地分支排序；源目录本身处于 detached HEAD 时，以 `{ref:null, commit:HEAD}` 置顶并继续列出本地分支。Renderer 只提交用户选中的必填 `baseRef + expectedBaseCommit`，不保留旧的“默认使用当前 HEAD”请求格式。Main 在选择阶段重新检查一次请求，只生成无执行目录的瞬时 `pending-worktree`；首条消息进入已有 `ensureSession` 单飞事务后，再次列出引用并只校验所选项，目标分支删除或 commit 改变即中止，而无关的当前分支变化不影响该基线。Worktree 此时才固定创建到 `~/.whycode/worktrees/<repository fingerprint>/<runtime UUID>`，始终以所选精确 commit 执行 `git worktree add --detach`，绑定同时固化所选 ref/commit，因此不会占用原分支。本地 tracked/untracked 改动默认不复制。可选 `.worktreeinclude` 只接受仓库根中逐行声明的字面相对路径：每项必须被 Git 忽略，拒绝绝对路径、导航段、盘符、尾随点/空格、通配符、符号链接、特殊文件和目标覆盖，并限制为 10,000 个文件/512 MiB；路径拼接不用可被后续盘符重置的 resolve 语义。实际创建前先原子占用空目标目录；任一步失败时移除 Git 登记、受管目录和临时清单，回滚本身失败则保留已写入的所有权清单并明确上报，不伪装创建失败已清干净。

  Worktree 所有权清单单独保存，完整绑定、`sessionIds[]` 引用集合、活动运行时租约及 Git `worktree list` 登记共同决定可恢复/可删除身份。恢复会先验证规范路径、实际 Git 根、原仓库登记和执行子目录，再取得租约；`session-start` 已写而清单尚未关联的窄崩溃窗口只允许空引用清单由同一会话补认领，已存在其它引用时 fail-closed。清单缺失而目录仍在时，即使用户请求丢弃也不递归删除；原仓库已丢失时默认保留，只有显式丢弃才按已验证受管根删除。每次递归删除前重新对受管根做 lstat/realpath 与普通目录检查，路径被符号链接或 Windows 目录联接替换时保留现场。Windows 状态与非强制清理命令通过进程内 `-c core.fileMode=false` 忽略 NTFS 无法表达的 executable bit，不改写原仓库配置，仍保留内容、未跟踪文件和非 Windows 平台的真实模式变化。只有工作区干净、HEAD 仍在基线或已有分支引用且未建立 session 的空白草稿会在运行体释放时自动清理；启动扫描也只回收清单未认领且不被任何当前会话事实引用的干净草稿，会话引用优先保护窄崩溃恢复窗口；删掉某仓库最后一个受管 Worktree 后，只对仍位于受管根且确认为空的 16 位仓库指纹目录执行非递归删除，有其它 Worktree、竞态新建或异常路径时都保留。未提交变化和未建分支的 detached 提交都默认保留。已建立会话默认持续保留。

  `ManagedWorkspaceManager` 负责非项目默认会话的 app-owned 目录。可见根仍是规范化的 `Documents/WhyCode Workspace`（失败回退 `userData/workspace`），每个草稿规划 `root/<runtime UUID>`，但选择阶段不创建；首条消息在 `ensureSession` 单飞内先排他写入根外 `~/.whycode/managed-workspaces/<UUID>.json`，再创建普通目录，Journal 写稳后把唯一 sessionId 原子关联到同一清单。Fork 会校验来源所有权，把来源目录中的普通文件与目录复制到新建但尚未绑定的目标；符号链接、目录联接和特殊文件会终止并清理整个目标，避免新会话继续共享外部资源。新会话事实写稳后才认领目标，失败则同时回收会话目录与目标；恢复仍核对 ID、路径、创建时间、唯一 sessionId 和普通目录身份。启动时先完成会话列表扫描和孤儿清理，再创建首个运行体，避免清理与新会话物化竞态。删除已知绑定直接按绑定+清单核对；只有会话摘要不可读时才按 sessionId 扫描清单，若存在损坏记录则停止删除而不是删掉事实源后静默遗留目录。

  `SessionScratchManager` 负责所有工作区模式共用的 app-owned 临时目录。目录固定为 `userData/scratch/{sessionId}`，普通 Main 使用 `Main/`，协商使用 `consensus/{taskId}/{Main|B|C}/`；路径完全由 sessionId 派生，不进入会话 schema 或第二份 manifest。新会话在 Journal 创建后建立目录，恢复与后台唤醒幂等补齐，turn 结束和运行体卸载都不删除。Fork 使用与 managed 快照相同的普通目录复制器，拒绝链接和特殊文件；目标 scratch、工作区、附件、检查点及会话事实中任一失败都会进入同一回滚。应用启动以会话列表中的全部事实（包括 delete-only 项）为保留集合，只删除没有对应事实的 scratch 子目录；显式删除会话则在事实源前定向删除该 sessionId，绝不触碰其它会话或用户项目。

  Worktree 分支创建先占用该运行体既有输入 FIFO，再复查 Agent 与后台命令，并复用宿主项目写队列，避免与消息启动或工具写入竞态。交付面板只做状态、变更列表、tracked diff、打开目录和从 detached HEAD 创建分支；不自动 commit、merge 或覆盖本地分支。HEAD 偏离基线但尚未建立分支时，面板明确要求先建分支；显式丢弃仍允许清理，但确认文案会说明该提交将失去 Worktree 引用。删除 Worktree 会话时顺序为持久 delete-only 标记 → 停止命令/释放 Agent 与租约 → 删除受管 Worktree/清理 Git 登记 → 删除会话事实源；删除 managed 会话在同一事实源前清理其独占目录，Local 会话仍绝不触碰用户目录。B/C 继续使用项目外 scratch，不为协商创建 Worktree。设计取舍参考 [Codex Git worktrees](https://learn.chatgpt.com/docs/environments/git-worktrees.md) 与 [Claude Code worktrees](https://code.claude.com/docs/en/worktrees)；Codex 会把所选当前分支的未提交改动应用到新 Worktree，WhyCode 按既定产品决策不采用该行为。

- **宿主/UI**：Electron 只允许一个主实例持有 `userData`，第二次启动只聚焦现有窗口。点击“＋新会话”进入 `pending-managed` 默认草稿，但界面只显示“选择项目”，不暴露尚未物化的默认子目录；用户也可不选择项目直接发送。首条消息前选择非 Git 目录直接创建 Local 草稿；选择 Git 目录也先创建 Local 草稿，并在输入框上沿提供相邻的启动模式与基线分支两个 Radix 锚点菜单：模式可切 Local/新 Worktree，基线可先独立选定本地分支的精确提交，不打开居中对话框。项目/模式/基线信息只在第一条用户消息前显示；消息开始后只在标题旁显示可打开的实际工作目录。首条消息物化 Worktree 期间，Renderer 保留本次用户输入并显示单一、真实的创建过渡，不伪造无法从宿主确认的子步骤；Main 的命令响应再把真实绑定和执行路径原子同步给 Renderer，失败则恢复输入。之后标题目录只负责打开当前目录，不允许改变已建立会话的工作区。恢复历史严格使用 metadata 的 WorkspaceBinding，不调用进程级 `chdir`。Renderer 不按本地 busy 乐观追加正式消息；每个运行体自己的 FIFO 路由闸门在“同步判定 root/steering → 写稳输入 → 交给 Session/Coordinator”中权威分类，IPC 在 Agent 同步接收后即可确认。确认后即可切走，任务继续运行。附件准备只锁目标运行体到消息完成持久化；正文与附件不可拆分。无路径图片只在草稿内存持有并用对象 URL 预览；已持久会话的未发送草稿按 sessionId 暂存，删除同步清理；没有历史入口的空白草稿在新选择快照成功后立即释放，未发送的 managed/Worktree 选择都没有磁盘资源。持久图片只通过受限 `whycode-attachment:` 协议读取已加载运行体的当前会话文件，PDF 历史卡也必须携带对应 runtimeId。历史会话删除仍全局单飞但不冻结其它运行体；目标运行中时必须先停止。API key 与四档权限偏好只存在 `~/.whycode/config.json`，其中密钥使用系统安全密文且 Renderer不可读取；权限偏好在全部已加载、新建与恢复运行体间共享，具体审批记忆、运行态和 Peer 全量会话不落盘；输入队列事实、资源检查点、附件、活动计划和待回答问题持久化。
- **删除生命周期**：显式删除先校验 UUID，并用排他创建 + flush 在会话根的 `.deleting/{sessionId}` 写外置 marker；它不随目标目录的部分递归删除消失，并优先于 live metadata，使当前进程或重启后的列表都返回 `resumable=false`，`open()` 直接拒绝。随后停止并移除该会话的后台命令与日志、定向删除 `scratch/{sessionId}`，再按外置所有权记录删除 Worktree 或 managed 默认目录，最后递归删除 `sessions/{sessionId}`（含 transcript、metadata、临时文件和会话级 checkpoints）；只有全部成功才清 marker。Main 的作用域化删除租约始终阻止第二个删除；若目标是当前运行体，先从 Registry 原子移除并返回新的默认空白草稿快照，当前输入、会话切换和项目选择锁到结果落地。若目标是历史 sessionId，则只排斥该目标的重复恢复/操作：其它会话可继续恢复或新建，项目选择与当前输入、附件、模型切换和 Agent 运行保持可用，较大的 Worktree 清理不会冻结整个应用。目标仍在工作时必须先停止，不能删除运行中的事实源。删除目标的界面锁作用域先用 Renderer 当前会话快照消除点击竞态，再以 Main 当前 `sessionId` 校准；历史列表的 `isCurrent` 只用于展示。切换到其它会话时，新快照只描述新当前会话，不能覆盖 Renderer 正在跟踪的历史删除目标。确认始终留在 Renderer DOM，不得使用 `window.confirm/alert/prompt`。中途失败只允许重试级联，不再恢复部分清理的会话；所有权记录损坏时事实源保持 delete-only，避免界面删除成功却遗留目录。Local 用户目录永不属于 app-owned 删除范围；同一项目的其它会话数据全部保留。

### 5.9 Main 长任务控制（已实现，M5；`core/src/tasks/`）

- **作用域**：仅普通 Main 与协商后的 Main 执行阶段持有正式计划；M1/B/C 不注册任务工具，继续按协议完成有界分析。简单问答和一步操作不应创建计划。
- **状态契约**：`TaskPlanState = {version, activePlan, resumeRequired, interruptionReason}`。单会话至多一个完整活动计划，不保存历史计划。计划由 3～7 个宏观、结果导向的 `outcome` 建立，最后一项是唯一 verification；TaskItem 状态只允许 `pending|in_progress|completed`，同一时刻至多一项 `in_progress`，completed 必须带不可改写的 evidence。
- **控制工具**：普通 Main 始终获得完整且顺序稳定的 `CreateTaskPlan / ResumeTaskPlan / UpdateTaskItem / CloseTaskPlan`，不按 none/interrupted/dormant/engaged 改变注册集合。Create 前先定向扫描关键文件，只写宏观结果。Update 原子添加、删除、修改、重排当前或未来项，并可同时设置 `in_progress|completed`；全部变化先应用到副本并整体校验。状态 setter 通用幂等，纯结构 no-op 保持 `no_state_change`，非法跳转 fail-closed。Close 无参数，只用于显式放弃或切换独立目标。
- **步骤事务**：计划控制器在每个模型 step 开始时暂存状态；完整 step 与会话消息、TaskPlanState、计划事件一起提交，urgent、取消或异常整体丢弃。Create、Resume、Close 标记 `requiresStandaloneStep`。切换独立目标先 Close，在后续稳定 step 扫描新目标再 Create；不提供 Replace、历史归档或同一步 Close→Create。
- **执行上下文**：none 无 active；interrupted 是硬中断留下的 `resumeRequired`；engaged 是当前 runLoop 已由稳定计划工具或绑定问题答案授予执行权；dormant 是其余 active 状态。新的顶层请求不继承 engagement，interrupted/dormant 不自动续跑。
- **自然结束与等待**：engaged run 的完整无工具最终正文在同一步事务中自动结束计划；全部里程碑完成时终态为 `completed`，否则为 `ended`，两者都清空 active。用户 Stop、AskUserQuestion、明确自然语言暂缓或已登记后台终态唤醒仍在等待时保留计划；后台通知回到同一逻辑任务后，再由最终正文自然结束。
- **渐进执行与恢复**：模型先用 Update 将选定项显式置为 `in_progress`，再读取代码、确认细节并实施；完成或删除当前项不自动启动下一项。即时详细步骤不写入计划。engaged 计划连续 10 个完整 assistant step 无变更才注入进度提醒；不再以无工具提前收尾触发反向提醒。压缩、重启、回滚和共识事务携带完整 TaskPlanState，只有有效 continuation 延续 engagement。
- **展示**：Renderer 只保留当前活动计划或最新终态快照，计划卡只显示进度、单行 outcome、状态图标和 verification 标识；不重复显示计划目标，也不显示阻塞原因、验收小字、终态总结或历史卡。
- **未来深化（非当前排期）**：提交事件级证据引用、语义无进展检测、显式 UI 恢复、用户调整当前计划和更长的多 Provider 压力测试；通用 subagent 接入时再增加 owner 与证据合并。

### 5.10 图片模块（P0 已完成客户端验收并合并；`core/src/attachments/`）

- **输入与附件事务**：单条用户输入最多 10 张，普通视觉工具与 MCP 单步骤结果最多 4 张；支持按魔数识别的静态 PNG/JPEG/WebP；不信任扩展名，动态/多帧和 GIF 不开放。会话原图最多 20 MB、单边最多 8,192 且总像素不超过 2,000 万；文件头只做廉价预检，Sharp 在 30 秒上限和 AbortSignal 下强制完整解码，再生成 SHA-256 做批内去重与长期内容身份。用户选择、粘贴、拖放和恢复附件使用 10 张输入 schema，工具采集使用 4 张结果 schema；两者复用同一底层导入验证与事务边界；新字节先 staging，全部成功才 commit，失败 rollback，启动/open 清理半事务与无引用文件。原图永不改写。
- **细节级别、区域与缓存**：`high` 默认执行 `autoOrient()`、Lanczos3 缩放、ICC 保留和分级编码，最长边 2,048、最多 3.75 MB；透明 PNG 优先 PNG/WebP，非透明 PNG 优先 PNG/JPEG，JPEG/WebP 保持同族并逐级降质/缩边。`original` 表示不降低像素分辨率，未裁剪且无需纠正方向时直接发送原字节，否则以原尺寸重编码，仍受 20 MB 上限；只对真实验通且显式标记 `supportsOriginalImageDetail` 的模型开放。`ViewImage.region` 使用 autoOrient 后源图整数像素坐标，结果返回所选区域与模型像素到源图的比例/偏移。v1 引用兼容默认 high，v2 引用记录变换；v3 缓存名绑定源与变换摘要，读出也完整解码，损坏/过界删除重建，并发写使用临时文件 + rename，每会话按 mtime 淘汰到 64 MiB，旧缓存与过期临时文件会清理。缓存不能替代权威原图。
- **模型消息与视觉工具**：`ViewImage` 把项目内或经授权的图片复制进会话；`CaptureScreenshot` 由宿主返回屏幕字节；`RenderOffice` 把后台栅格化页面导入同一附件事务。Agent 把工具文字和图片统一写进原 `toolCallId` 的规范 tool result，附件元数据、assistant/tool 消息和 step-scoped `image-viewed` 同步提交，失败或未提交 step 回收原图/缓存。JSONL 中的嵌套图片仍是版本化稳定引用，视觉请求边界才水合 Base64；普通后续轮次不会主动删除历史工具像素，只有既有微清理/完整压缩负责真正退出上下文。Anthropic Messages 与 OpenAI Responses 保留原生多模态工具结果；OpenAI Chat 的 tool role 只能承载文本，因此 provider 仅在请求副本中保留文字 tool message，并在整组连续工具结果之后追加一条不写回历史的内部多模态 user 消息，逐组显式携带原 `tool_call_id`。并行结果不会被 user 消息从中截断。JSONL、ViewEvent、CoreEvent、压缩尾部和 Renderer 保留状态都不含图片字节。
- **工作中补图与协商边界**：具备 `native` 或 `auxiliary` 有效图片路由的 Main，其根图片、普通 steering 和 urgent steering 共用文本+附件消息；普通按 FIFO 在稳定 step 间 delivery-ack 后注入，urgent 只丢弃当前未提交 step。停止/异常将队列连同原交付方式持久退回草稿，进程崩溃把未 ack 输入恢复为草稿，已 ack 输入不重复。协商开启时图片仍只给 Main：空闲直接跳过 B/C，B/C 阶段普通补图延后到 Main 执行包之后的独立输入，urgent 先终止并回滚半截共识。图片字节不进入 B/C 或协议提示。
- **辅助识图路由（v8 引入，当前 v11 沿用）**：设置页候选只取当前已配置、可精确解析且有效画像 `supportsImageInput=true` 的连接；失效选择在配置提交边界清空，不按名称、厂商或列表顺序猜替补。原生视觉 Main 使用 `native` user message 并在请求边界水合像素；非视觉 Main 只有在辅助选择有效时才能导入图片，使用 `auxiliary` user message 保存正文、显示名、稳定附件 ID 与不含字节的版本化标记。`AnalyzeImage` 只注册给非视觉普通 Main，B/C、discussion、协议回合与视觉 Main 均物理移除；Main 的工具参数必须把完整对话中的省略、代词、区域、颜色、OCR、比较和输出要求改写成独立视觉问题。Main 宿主只把本次选中的附件像素和该问题交给辅助模型，不发送主会话历史、项目目录、工具集或 Renderer 密钥；辅助输出作为普通 tool result 进入现有步骤事务，并带稳定 ID 标记供活动上下文再次调用。切到视觉 Main 后，该模型可原生读取之后的 native 图片，但既有 auxiliary 消息仍保持文字引用和已落盘观察，不自动批量补发旧像素；切回非视觉时也不重复水合。该能力只覆盖会话图片读取，不授予 `ViewImage`、`CaptureScreenshot`、`RenderOffice` 或视觉 PDF 路径。
- **桌面截图与复验**：Core 的 `CaptureScreenshot` 只定义宿主中立回调；Electron 用 `desktopCapturer/screen/nativeImage` 实现主/指定屏幕、当前/标题窗口和相对所选显示器的 DIP 区域截图，换算到真实源像素后仍执行统一 7,680 单边、2,000 万像素、20 MB 限制。单个外部应用或网页优先使用 `target=window + window_title` 绑定独立窗口源，本地 HTML 可从 `<title>` 取得标题；`screen/region` 仅用于整屏或跨窗口观察。工具参数以 `target` 为权威边界：若兼容端点把 JSON Schema 的其它可选字段一并补齐，Core 在执行前丢弃与目标无关的 `display_id/window_title/region`，但 `target=region` 缺少有效坐标仍然失败；这是确定性的输入规范化，不是重试计数或模型特判。Windows 采集整屏/区域时在截图事务内用 `setContentProtection(true)`（`WDA_EXCLUDEFROMCAPTURE`）排除 WhyCode，并在 `finally` 恢复原状态，不隐藏界面或改变焦点；其它平台仅在 WhyCode 当前位于前台时短暂隐藏并在失败/取消后恢复。工具在视觉普通 Main 中注册，默认受管工作区会话同样可用，讨论/协议回合移除；只读/默认/自动编辑档首次调用说明桌面隐私并走 `allow-tool` 会话记忆，显式全自动档不弹首次提示。截图独占一个模型 step，稳定提示要求视觉改动必须“先截图基线 → 修改 → 再截图验证”，没有新截图不得宣称视觉验收。
- **能力边界与未来深化**：目录按厂商官方画像为 Claude Sonnet 4.6、GPT-5.5/5.6、Gemini 3.1/3.7、GLM-5V-Turbo 与 MiMo V2.5 开放视觉；官方端点和同厂商协议中转使用该画像，CLIProxyAPI 只对“审核候选 ∩ 实例已公布路由”再叠加路由约束，视觉必须同时获得厂商画像与路由审核支持，不能用动态图片挑战或模型自述开启。MiMo/GLM 官方接入、CLIProxyAPI GPT 与本机 Gemini 3.1 Chat 路由有真实记录；单次 Gemini 3.1 烟测只证明路由/协议，不替代图片和完整 Agent 客户端验收。即使 Codex client 元数据声明 original，当前 GPT 厂商画像未完成 WhyCode original 验收，合成后也不会反向开启；只有 MiMo 的 original 经过真实小字烟测。DeepSeek 与 GLM-4.7 保持非视觉。视觉历史切回非视觉模型时，有有效辅助选择便降级为带稳定附件 ID 的 `AnalyzeImage` 提示，没有辅助选择才是不可见占位；规范历史与附件不变。辅助路径产生的历史本来就是文字引用与观察结果，之后切到视觉模型也不会自动批量水合旧像素。设计参考 Claude Code 的原始输入+执行期转换/排队语义及截图时排除宿主窗口，也参考 Codex 的能力门控、`high/original`、局部读取、目标浏览器绑定、截图复验和工具结果语义绑定，按 WhyCode 多 Provider/JSONL 事务重新实现。当前桌面截图不承诺 DOM、导航就绪或点击控制，这些属于后续浏览器/Computer Use 模块。

### 5.11 PDF 模块（P0 与 JPEG-only 视觉深化已完成客户端验收并合并 `main`；`core/src/pdf/`、`tools/read-pdf/`）

- **输入与事务**：单条最多 4 个 PDF，单个原文件 50 MB、单条总计 100 MB、文档最多 1000 页；扩展名和 MIME 只用于 UI 初筛，Main 复制后由 PDF.js 完整打开。路径与 restored ID 可混合，图片/PDF 共用一次消息准备事务；新文件先进入 `.pdf-import-*`，有界流式复制同时计算 SHA-256，全部检查成功才 rename，失败回收整批。空文件、损坏、加密、重复、大小/页数越界均拒绝；JSONL/ViewEvent 只保存 ID、显示名、摘要、字节数和页数，不保存路径、正文或 Base64。恢复时重新核对会话归属、摘要、字节数和解析结果，统一清理图片/PDF staging 与孤儿文件。
- **处理隔离**：Core 只依赖 `PdfProcessor` 端口；Electron 每次 inspect/read 在独立 Utility Process 中加载 PDF.js，V8 heap 限 384 MB，检查/文字 30 秒、视觉分页 120 秒，超时/取消/异常立即终止进程。输入先限制为 50 MB，PDF.js 关闭 worker fetch/系统图像解码，CMap、WASM、ICC 与标准字体资源均指向打包依赖；视觉页按 Claude Code 的分页参数等价渲染为白底 100 DPI JPEG（质量 75），同时保留最长边约 2048、最多 2000 万像素、单页 20 MB 与单批 32 MB 的安全上限。子进程响应重新校验页码、数量、文字长度、尺寸和 `.jpg` 严格输出路径，再交回 Core。
- **视觉请求单通道**：持久 user 消息始终只含轻量 PDF 引用。对有效视觉模型，每次请求副本从活动历史中最近的权威引用开始选择单份不超过 10 页、总计不超过 10 页的小 PDF，在原 user 消息处附加逐页 JPEG 页面图，无需模型先调用工具，也不并行发送宿主提取正文；页面图编码后总预算 16 MB。该选择按最近引用和总页数预算确定，而不是靠删除旧附件；大 PDF 或预算外 PDF 只保留稳定引用并等待 `ReadPdf`。派生页面图不生成聊天缩略图。派生缓存以源 PDF SHA-256、页码、页面图摘要和 manifest-last 原子提交校验，JSONL 不保存 Base64；失败则保留引用并提示调用 `ReadPdf`。
- **按需读取**：普通 Main 动态注册 `ReadPdf`；模型侧统一使用扁平的 `sourceType/sourceValue/startPage/pageCount` 契约，不按 Provider 特判，也不暴露 `mode`。视觉模型固定走页面图路径，默认及单次最多 20 页、页面图总计最多 32 MB；工具文字结果描述页段、安全边界与下一页游标，页面 JPEG 则绑定同一 `toolCallId` 的规范工具结果，并在 provider 边界按协议原生序列化或作 OpenAI Chat 兼容投影。非视觉模型固定走文字路径，默认 5/最多 20 页、总计 60k。会话 PDF 的同一页面图带稳定来源元数据并复用已有文件；路径来源因文件可变不跨调用猜测复用。PDF 专用 20 图上限只用于工具结果，`ReadPdf` 不发出 `image-viewed`，Renderer 因而不展示派生页图；显式 `ViewImage`、`CaptureScreenshot`、`RenderOffice` 的可见事件与用户图片仍保持 4 图边界。讨论 Agent、协议回合与 B/C 物理移除工具；含 PDF 的协商输入记录 `pdf-input` 并只交给 Main。
- **生命周期与上下文**：每次处理会在已加载字节上重新核对导入时 SHA-256，同长度替换也不能越过内容身份。工作中普通/urgent 补发、delivery ack、停止/崩溃草稿恢复、回滚和混合图片输入沿用现有消息事务；WebFetch 导入的 PDF 也在包含该工具结果的同一稳定 step 中登记并持久化，失败或中止同时回收未提交文件，恢复后从同一 JSONL 事实源重建可读附件。它带 `origin=web`，无论页数都不在视觉请求中自动展开，模型必须显式调用 `ReadPdf`，避免一次 URL 抓取意外注入整份 PDF。压缩在 20k 引用预算内重注入最近 PDF，回滚/重启只信应用生成的 user 引用块。`ReadPdf` 页面图随其规范工具结果跨普通轮次保留；微清理替换该工具结果时会让同一 `toolCallId` 的文字与页面图原子退出上下文，完整压缩则按既有摘要边界处理。图片按 3,000 token 固定估算而不按 Base64 长度计费，provider usage 基线不吞掉宿主随后追加的工具结果/页面图。历史卡仍通过受限 IPC 使用系统阅读器打开。
- **依赖与未来深化（非当前承诺）**：PDF.js 提供成熟解析/文字提取，`@napi-rs/canvas` 提供 PDF.js 所需 Node Canvas；现有 Electron/Sharp 不具备 PDF 页面解释与字体渲染，自研解析器风险更高，系统 Poppler 又无法保证安装和版本，因此新增这两个精确锁版本依赖。方案借鉴 Claude Code/Codex 的轻引用、按需分页和本地工具思路，但保持多 Provider 一致。后续仅在真实需求出现时评估 OCR（让文字模型读扫描件）、全文 SearchPdf、内置阅读器/页跳转、批注、Provider 原生 PDF 快路径及 B/C 有界读取；密码交互当前明确不做。

### 5.12 Office 制品 P1（已完成客户端验收并合并；`core/src/office/`、`tools/*-office*/`、`desktop/main/office/`）

- **能力而非模型白名单**：普通 Main 的 `mainTools` 始终注入 `BuildOfficeArtifact` 与 `InspectOffice`，因此非视觉模型也能生成、修改和结构检查 DOCX/PPTX/XLSX。`RenderOffice` 由 `AgentSession.buildToolSet` 在“有项目 + 持久会话 + 普通 Main + 当前模型支持图片”时动态装配；模型切换后自然重新计算工具集合。discussion、M1/B/C 与协议回合没有 Office 工具，不调用第二模型补视觉。
- **构建与权限边界**：模型先用 WriteFile 保存求值结果为构建函数的脚本，随后 `BuildOfficeArtifact` 以 execute 权限和 `exact-files` 输出检查点进入同项目宿主 FIFO；普通脚本文件末尾分号合法，不再用额外括号改写源码语法。Main 把脚本和最多 32 个显式 asset 固定读取到私有 staging，再启动一次性 512 MB Office Utility Process。进程内先执行 SES `lockdown`，脚本在独立 Compartment 中只得到格式、浅冻结/能力膜收窄的 `docx/PptxGenJS/ExcelJS/JSZip/fastXml/OfficeTemplate`、不可变 assets 与 report；Node 全局、Function 构造器逃逸、import/require、文件/进程/网络和库的路径型读写方法都不可达。asset 同时提供原样 `Uint8Array` bytes、base64/dataUri 与按需严格 UTF-8 解码的只读 text；JSON 等文本资料不依赖隔离区缺失的 Buffer/TextDecoder，也不能用 `Uint8Array.toString()` 误解码。能力膜深解包普通数据时对 `Uint8Array` 原样传递，避免把模板 bytes 展开成数字键对象，因此 ExcelJS 可直接执行文档公开的 `workbook.xlsx.load(assets.template.bytes)`。接口或构建错误必须继续修正同一 builder，不能退回 RunCommand/WriteFile 手写、打包或覆盖最终 OOXML。SES 是环境权限边界，Utility Process 仍独立负责 180 秒、heap 与崩溃/取消边界，二者不混称。staging 的所有权覆盖构建、最终模板比较、可选 XLSX 重算、最终检查和原子发布；这些异步步骤全部 settle 后 `finally` 才删除目录，不能直接返回未等待的 finalizer Promise。
- **深层 OOXML 校验**：源文件最多 100 MB；ZIP 中央目录先拒绝加密、ZIP64、多磁盘、重复/绝对/导航路径、非 UTF-8 名称、未知压缩算法、宏部件、单部件/总解压越界和扩展名伪装。随后解压并验证全部 `.xml/.rels`，核对 Content Types、关系 owner/target 与根 officeDocument。格式层继续核对 DOCX 书签/批注范围、修订元数据、脚注/尾注、编号和样式引用，PPTX slide/shape ID 与 chart axis，XLSX 工作表名/ID、style index、表和各种 A1 range。被关系引用的缺失部件等完整性错误拒绝文件；未被关系使用的冗余 ContentType Override、页面几何、标题跳级、缺替代文字、PPT 对象越界/明显文本重叠、XLSX 文本裁切和 drawing anchor 等确定性问题作为 warning 返回。
- **对象化 InspectOffice**：单一工具通过 `view` 提供 `content/objects/styles/relationships/validation/template/formula-trace`，而不是按格式复制工具。DOCX 对象覆盖 paragraph/table/drawing/section/header/footer/comments/notes/revisions/fields，物理段落 locator 不再与“仅非空内容序号”混用，style/template 还返回具体对齐、间距、缩进、字体、字号、颜色；PPTX 由单一嵌套 shape 扫描器覆盖稳定 ID/name/type/bounds/text/placeholder、group/父组、notes 与 master/layout/theme，媒体资源再按 slide relationship 解析 target/type/SHA-256/bytes/active-use-count/crop，objects 与 template 共用该索引；XLSX 覆盖 cell/type/style/formula/value、defined name、table/drawing/chart/comment/merge/filter/pane/validation/conditional formatting，template 视图在 XLSX 上明确拒绝而不是静默退回 content。`startUnit` 是视图结构单元索引而非 XLSX 行号，后续分页只使用返回的 `nextUnit`；XLSX 的 `sheetName/range` 只在 content、objects、formula-trace 生效，styles、relationships、validation 必须省略，PPTX 的 `slideNumber` 只在 content、objects、template 生效。所有结果保留稳定 OOXML locator、每次最多 50 单元和 60k 文字预算。公式追踪解析普通、共享公式的相对平移及定义名称，最多 200 个依赖节点；XLSX 解析另设单表 100,000、整簿 200,000 个非空单元格、200,000 个共享字符串与 20,000 个定义名称的确定性上限，超限 fail-closed。深层 XLSX 校验只统计 `cellXfs` 直接子级的 `xf`，并按 SpreadsheetML 顺序校验已知工作表节点。
- **显式模板模式、媒体处置与血缘**：`BuildOfficeArtifact` 必须选择 `create|template`；template 必须有 `templateAssetKey`，create 反向禁止该字段。Main 在执行 builder 前先检查暂存模板并确认格式，最终文件（XLSX 为实际重算后的最终文件）在独立 Utility Process 再与模板比较。模板能力只开放两种单计划对象：`OfficeTemplate.docx({template,textEdits,rangeEdits})` 与 `OfficeTemplate.pptx({template,slides})`，两者直接返回 OOXML bytes，不存在把 bytes 直接传给函数或再调用 `slide/replaceShapeText` 的可变对象接口。DOCX 复制原包，按物理段落 locator 替换文字或用源段落克隆范围；PPTX 复制选定 source slide 及 notes，保持原 master→layout→slide 关系，可重复源页、重写页码字段缓存。每个输出页的所有 slide-level 图片/图表/关系图/嵌入对象/媒体必须恰好由一个媒体动作覆盖：`image` 直接指向 picture shape，`delete` 可指向 shape/group 并清理该页未再引用的关系，`keep` 只接受 `brand|decoration`；媒体动作携带 `mediaRole+reason`，同页 shape ID 不可重复。共享图片关系在替换时先拆成克隆页自己的关系，避免误改同页其它 picture。Word 样式/编号/设置/页眉页脚/媒体、PPT master/layout/theme/media、XLSX styles/theme/chart/drawing/pivot 的共享模板部件仍逐字节保护；PPTX frame 血缘由“与源页完全同构”收敛为“同 layout 源页对象序列的有序非空子集”，允许删除源内容对象，同时拒绝新增、重排、空白重建和只抄配色。模板原件仍留在用户路径，输出检查点只覆盖目标文件；没有旧字段别名或第二条编辑路径。
- **XLSX 实际重算**：ExcelJS 只负责构建。若检查发现公式，Main 优先启动本轮专属隐藏 Excel，关闭宏、事件、alerts 和链接更新，执行 `CalculateFullRebuild` 并等待 `CalculationState=xlDone` 后另存 XLSX；Windows Excel 不可用时使用隔离 LibreOffice profile 打开另存。重算文件再进入 384 MB Utility Process 完整检查；公式数量变化、任何未保存计算值或任何公式错误值都 fail-closed，不发布原始缓存版本。外部工作簿链接会以确定性 warning 进入 InspectOffice；含公式构建检测到该 warning 时在启动重算器前停止，因为禁用链接更新后不能证明来源数据已刷新。成功结果记录 `microsoft-excel|libreoffice`、公式数和最终 SHA。
- **无窗口视觉链**：`RenderOffice` 不调用 `CaptureScreenshot`、不启动系统查看器，也不改变前台焦点。Electron 先检查同一 OOXML，再在临时目录中优先调用带独立 profile 的 LibreOffice `--headless --invisible`；Windows 无 LibreOffice 时用 `cscript //B` 的 VBScript late binding 创建本轮 Word/PowerPoint/Excel 实例。只有 WMI 确认新进程带 `/Automation` 或 `-Embedding` 后才修改应用属性和打开文件；随后设置 `Visible/WithWindow=false`，强制禁用宏、alerts、events 和链接更新，以只读方式导出 PDF。late binding 避免第三方办公套件遗留 TypeLib 注册破坏 .NET COM interop；取消、120 秒超时、失败以及正常完成都会按 PID、进程名和自动化命令行三重校验定向清理本轮实例并等待退出，不附着或结束已有 Office。`pages` 让 `PdfProcessor` 每批输出最多 4 张 JPEG；`overview` 在同一次 Office→PDF 转换内按 PDF 视觉上限分批渲染最多 50 页，再用现有 Sharp 生成一张有页码的有界总览图。两者都沿原工具调用作为 `image-viewed` 附件稳定提交，临时 Office/PDF/页面/总览目录在导入后回收。
- **ViewImage 取舍**：`ViewImage` 仍是读取任意项目栅格图、局部裁剪和像素映射的一等工具；它只复制/解码文件并把图像交给模型，本来就不会启动外部应用。Office 页面渲染具有格式解释、分页、转换后端和全页遍历语义，单独建 `RenderOffice` 比删除或扩张 `ViewImage` 更清晰。非视觉模型完成生成与全部 `InspectOffice` 后必须写“结构检查通过，未执行视觉复核”，不得调用桌面截图冒充版面验收。
- **Skill 交付闸门**：三项 Office Skill 按只读问答、从零创建、已有文件/模板修改和仅验收四种模式路由。任何创建或修改先读取 builder API 与质量清单；PPTX 模板任务另读按需 `template-following.md`。共同流程是“研究/内容模型 → 数值化设计或源槽映射 → 单一 builder 迭代 → 结构复核 → 可用时整套总览与全页细查”。PPTX 规划先看源文件 overview，盘点叙事角色、构图轮廓、视觉密度、编辑槽和媒体槽；输出页必须映射同类 sourceSlide，输入资料中的相关视觉先物化为显式 asset，禁止错用封面/章节/结束页或反复选纯文字源页绕过媒体。最终先用 overview 对照源文件和成品的整套节奏，再用媒体 hash/target/reuse 与 pages 核对全部细节；BuildOfficeArtifact 的“模板继承”只证明 OOXML 血缘。XLSX 对关键结果再做 formula-trace 和业务独立复算。实质修改使旧证据失效。
- **Codex/Claude PPTX 对齐依据**：Codex 当前 presentations/template-following 工作流要求先建立 template frame map，再把继承对象逐项标成 keep/rewrite/replace/delete，并把新来源图像装入继承框；Anthropic 官方 PPTX Skill 明确“template slots 不等于 source items”，源主题图片与其配套文字/group 应整体替换或删除，最终按内容计划和全页渲染复核。真实 WLB-LLM/Suika builder 的 27 个输出页全部一对一复制源页，26 页含图但零 image/delete 编辑，活动媒体全部来自模板，证明原缺口属于 WhyCode 契约而非某个模型。当前实现只吸收两家共有且可在本地验证的约束，不复制其私有 runtime，也不增加 Provider 特判。
- **依赖与当前边界**：六个库均精确锁版本并使用各自成熟职责；SES 为 Apache-2.0，其余 Office 库按各自开源许可使用；`exceljs` 的 `uuid` 传递依赖继续最窄覆盖到修复版 11.1.1。P1 不改会话 schema，不做 Office composer 附件或聊天内制品预览；项目/已授权路径是文件事实源。没有 Excel/LibreOffice 时，无公式 XLSX 仍可生成，含公式构建明确失败而不伪造重算；视觉渲染也返回 renderer-unavailable。Visio、实时 Office 控制、自带跨平台办公运行时、第二视觉评审模型和 Codex 私有 artifact-tool 均不在本轮。

### 5.13 Agent Skills P0（客户端已验收并随 Office P1 合并；`core/src/skills/`、`tools/skill/`）

- **发现与身份**：依次扫描当前执行目录→最近 Git 根各层 `.agents/skills`、`$HOME/.whycode/skills` 的普通子目录，最后扫描应用托管的 `$HOME/.whycode/skills/.system`；三类 scope 分别是 `project/user/system`。用户扫描不进入任何隐藏目录，因此 `.system` 只由显式 system 根发现；旧全局 `$HOME/.agents/skills` 不再扫描。不同根按规范绝对路径去重，同名项不覆盖。每个 `SKILL.md` 的 ID 是规范绝对路径 SHA-256，内容另有 digest；UI 和模型工具都使用精确 ID，Renderer 提交 locator，Main 在写入输入前重新解析。
- **内置资产生命周期**：参考 Codex 把 embedded system skills 物化为带指纹的磁盘缓存、Claude Code 把常用流程随 CLI 注册的做法，WhyCode 内置 `code-review/debug/documents/presentations/simplify/skill-creator/spreadsheets/verify`。Office 三项只编排 WhyCode 一等 Office 工具；主文件保留任务模式与强制交付顺序，`references/builder-api.md` 和格式专属 `references/quality-checklist.md` 按需渐进读取，不复制 Codex/Claude Code Skill 源码或私有工具调用。源码内嵌资产在启动时写入 `$HOME/.whycode/skills/.system.installing`，完整落盘和 marker 写入后才替换 `.system`；指纹相同直接复用，目标或暂存路径不是普通目录/被符号链接替换时 fail-closed。整个 `.system` 是可重建的应用托管缓存，版本变化会整目录替换；初始化器只写托管的 `.system`，不会改动同级用户 Skill，项目 Skill 仍独立留在 `.agents/skills`。资产与用户项走同一解析、目录、冻结快照和 `Skill` 资源读取链路，没有第二套内存注册表。
- **通用内置工作流**：五个非 Office Skill 只吸收 Codex/Claude Code 可由 WhyCode 当前工具与权限完整执行的共同做法：精确触发描述、基于真实 merge base 的缺陷审查、先证据后结论、根因而非症状、保持行为的去重、指令优先的渐进披露和直接行为验收。`system-assets.ts` 仍是唯一源码事实源；不增加其它宿主的 `allowed-tools/context` 等扩展字段、动态命令注入、专用子代理或 Provider 分支。物化测试同时锁定五项仅含 `name/description` 的 frontmatter 和各自关键工作流，内容变化自然更新既有发布指纹。
- **解析与有界缓存**：`yaml@2.9.x` 只承担完整 YAML 语法及重复 key 检查；WhyCode 强制 `name/description`、目录名一致、合法 Unicode、UTF-8 和 256 KiB 文档上限，JSONL/IPC 恢复也按 UTF-8 字节复核而不是只数 JavaScript 字符，并重算正文 digest/path ID、包根、目录名和 frontmatter 元数据，任一不一致即把记录视为损坏。扫描深度 6、每根最多 2,000 个目录/20,000 个条目；解析 LRU 同时受 20,000 项和 32 MiB 限制，并按文件身份、`mtimeNs+ctimeNs+size` 复用。每个根任务仍重新枚举，新增/删除在下一任务可见；冻结正文总量另限 32 MiB，并按当前目录→仓库根→用户级→内置的发现优先级稳定截断，缓存不是第二事实源。根、包目录、`SKILL.md` 与资源路径均拒绝符号链接/目录联接，包内文本资源最多 512 KiB，并用打开后 stat 的固定长度读取防止大小竞态。目录 description 被规范为单行且所有结构字段经过 XML 转义，正文仍保持原字节语义。
- **显式与隐式激活**：当前行输入起点的 `/query` 打开统一功能与 Skill 面板，避免把 URL、Unix 路径或正文中的 `/` 误识别；功能置前，Skill 按名称前缀→名称包含→描述包含稳定排序，最多选择 8 个并显示 scope/path 区分同名项。空正文但选择了 Skill 时发送固定最小任务文本。普通 Main 每个根任务还得到不超过模型上下文 2%（无画像时 8,000 字符）的 `<available_skills>` 元数据目录，以及只读 `Skill {skillId,resourcePath?}`。省略资源路径返回该任务冻结的 `SKILL.md`；读取主文成功后正文提升为活动上下文，包内参考文件结果只保留到当前根任务。
- **生命周期与持久化**：显式根输入、运行中 steering、共识期间暂存输入、普通/urgent 队列都携带完整 `ActivatedSkill`；共识只在最终 Main 执行包交付，M1/B/C 不读取。当前 schema v11 沿用既有完整快照结构写入 `user-input` 和 pending snapshot，Renderer 事件只展示摘要；开发期 v10 及更早会话不迁移。恢复草稿按 input ID 复用 JSONL 正文，即使源文件变化或删除也不重读。编辑最新普通根时从它对应的首个 `turn-start.rootInputId` 找回原冻结快照；排队根从起始 messages 的 `deliveredInputIds` 聚合，共识最终执行再沿当前事务起点补入原始根输入，重启前后语义一致。根任务结束清空活动状态；下一根任务重新枚举，不继承正文或资源结果。
- **缓存与压缩红线**：System 完全不变。目录提醒只在项目指令之后插入请求缓存前缀，未变化目录的 revision、顺序和字节稳定；活动正文只追加到当次请求尾部，不能把每任务变化推到长历史之前。Skill 工具正文在请求投影中替换为稳定过期占位，摘要模型只看到无正文投影；压缩完成后从当前任务内存快照重新注入。usage token 基线保存上次 Skill 投影差值，后续以“当前差值−基线差值”校正，避免工具正文冻结与活动正文提升产生漏算/双算；仅 Skill 注入已达到自动压缩阈值时直接结束任务，不发送超限模型请求。
- **权限和角色**：Skill 只提供指令与只读包资源，不扩张任何权限；其中建议的脚本仍由既有命令工具执行并走当前权限、审批、项目边界与检查点规则。discussion、M1、B/C 和协议回合物理移除目录与工具。pending managed/Worktree 没有真实执行目录，选择阶段只列用户级与内置 Skill；首条消息物化后，普通根任务目录才基于真实目录增加项目级项。Subagent 可按自己的固定工具画像使用 Skill，但仍只读取该次激活实际发现的目录，不能以 Skill 或 Agent 定义扩张父会话权限。

### 5.14 Renderer 应用壳层（2026-08-06～07 开发与客户端验收完成；`apps/desktop/src/renderer/`）

> **前端唯一事实源**：Renderer 的信息架构、复用参数与视觉实现只在本节维护；需求文档和暂存便签只记录状态并链接到这里。强制开发红线见文档四 §5.2。

- **职责边界**：壳层只组合 Main 已提供的会话列表、运行时快照、Workspace、任务计划、连接设置和既有命令；没有复制 Core 状态、改写 JSONL/会话 schema 或重定义授权语义。全局权限偏好同步应用到 Registry 内全部运行体；最后选择的 Main 模型复用现有 `defaultModel` 作为新会话与重启首选，模型和权限的配置更新共用一条串行读改写链。`AgentSession` 在每个 turn 起点冻结 model、provider config 与 reasoning effort，使运行中调整只作用下一 turn，当前工具循环不会混用协议、能力或上下文窗口。上下文用量作为 live `context-usage` 进入同一 runtime snapshot，Renderer 只展示 Core 投影，不保存或重新估算；实时事件与恢复历史继续共用 `conversation-state`/`conversation-sections` 的纯投影。
- **信息架构**：`AppSidebar` 持久承载新会话、可折叠“置顶”、按活动时间排列的“最近”和设置，不再维护独立“进行中”分组。首条根输入写稳后发出的 `work-started` 立即刷新标题与列表；后台唤醒在持久化 `turn-start` 后确认新的活动时间，未置顶会话因此可靠上浮，置顶会话则按用户操作顺序固定且新置顶追加在组末。每行始终预留等宽状态位：前后台运行统一使用来自 DeepSeek Harness 视觉基线的 8 像素绿色 CSS 追逐动画，非当前会话结束后改为静态绿色未读点，打开会话即确认；侧栏收起时由同一未读集合汇总到会话图标，应用重启不恢复瞬时未读。运行与未读事实由 Main 的 `SessionRuntimeRegistry` 投影，不建立 Renderer 轮询或计时状态；置顶顺序独立原子保存在 `userData/session-sidebar.json`，不进入会话 JSONL/schema。`TaskHeader` 左侧显示会话标题、可点击实际目录和 Workspace 状态，右侧仅在当前会话存在 `StartCommand` 长任务时显示可点击计数入口，不放压缩菜单或任务栏开关；侧栏开关的可访问名称统一描述“侧边栏”，不绑定当前展示的子代理内容。入口用绿色脉冲点反馈运行态；面板按“运行中最早启动优先、终态最新结束优先”排列命令摘要、状态和耗时，自动续轮任务只增加铃铛图标，完成/失败/停止/中断均保留到宿主既有终态上限且不提供日志详情。中央只保留时间线；`TaskInspector` 常驻右侧，将“环境信息、子代理、任务计划”按固定顺序合并到一个复用 `wc-menu-content` 的 Radix 菜单表面，以灰线分区并用灰色小标题和同尺寸图标标识；没有 Worktree、子代理或计划时仍保留对应空标题。Worktree 内容只在环境区显示状态、变更、建分支和提交/推送入口；状态刷新由当前会话的工具完成、后台任务/子代理状态、任务结束及窗口重新聚焦共同驱动，短时合并重复信号，不轮询也不保留手动刷新。子代理区只在有记录时显示运行/结束摘要并进入独立面板；任务计划区不重复目标，只显示进度、单行结果里程碑、状态图标和 verification 标识，不显示阻塞原因、验收小字、状态说明、关闭总结或历史计划，也不提供手动展开/收起，进行中步骤统一使用浅绿色呼吸点。首条用户消息前，`wc-composer` 对未选项目只显示“选择项目”；选择 Git 项目后，在项目标签旁显示两个独立锚点菜单：启动模式选择 Local/Worktree，基线菜单选择精确分支提交，均使用圆角 Radix 浮层而不是居中对话框；消息开始后清空这条上下文。唯一原生目录选择器显式绑定当前主窗口为 owner，保持系统模态层与宿主点击提醒，不能被 WhyCode 主窗口覆盖。空会话尚无用户消息时，Slash 功能目录不提供 `/压缩`；首条用户消息存在后才按既有运行态决定其可用/禁用。附件、权限、协商、模型、推理和发送通常位于输入框底栏；等待 `AskUserQuestion` 时，同一个 Composer 原位切换为问题表单并暂时隐藏普通输入与底栏，回答后恢复原草稿和控件。任务运行时模型与推理控件保持可操作，变更从下一 turn 生效。审批卡仍位于输入框正上方。旧 `AppHeader`、弹出式 `SessionPanel`、居中的 Workspace 启动框和独立附件按钮同步删除。
- **交互与视觉**：全局 tokens 只使用中性纸白、灰、低饱和 sage/sand/blue/rose 和单一危险色。任务/环境、审批及设置中的相邻配置区域使用四种非对称手绘纸贴；同一个纸张伪元素同时承担低饱和填色、`2.5px` 单笔 `#1e1e1e` 边框和不规则椭圆圆角，使颜色与轮廓天然共用边界，不能把独立填色层和描边层叠在一起，也不能用多根细线模拟粗笔。四种纸形直接复用既定的四组椭圆圆角和 `-1.5deg / 1.2deg / 1.8deg / -1.2deg` 静态倾角，不再派生近似轮廓；弹窗纸贴必须归零倾角。阴影统一使用灰色偏移层与轻柔远层阴影。支持 hover 的精细指针悬停 `wc-paper-card` 时，容器以 `200ms ease` 相对上移 `4px`，纸张伪元素从各自静态倾角回正、放大 `1.02`，灰色偏移阴影同步由 `4px 5px` 加深为 `6px 8px`；正文从不参与 transform，避免悬停起止时字体被合成层重采样。鼠标仍在纸贴上或其 Radix Portal 菜单打开期间保持同一悬停姿态；Renderer 用单一事件委托保留最近一次真实纸贴命中，原生 IME 短暂接管命中时不闪退，菜单关闭且指针已离开或首次点击卡外时立即平稳复位，不以残留焦点维持悬停。该动效由全局纸贴原语提供，排除弹窗且不在组件内复制，不使用常驻 `will-change`。主聊天输入框和提问界面不使用纸贴，统一采用菜单圆角、细边框和柔和阴影。正文、光标、菜单和弹窗布局保持清晰；禁止 SVG turbulence、CSS filter、Canvas、逐帧 JS，以及在工具卡、普通正文、菜单或弹窗上套用纸贴悬停动效。工具调用卡继续使用既有样式，正文与主时间线不做重装饰。用户 PDF 作为带文件图标的独立胶囊排列，图片作为独立 96 px 缩略图带，文字保留单独气泡。
- **纸贴、菜单与字体复用参数**：普通纸贴统一使用 `22px` 内边距；每张旋转纸贴必须放入 `wc-paper-frame` 外接框，由外接框吸收旋转和偏移阴影造成的越界，相邻外接框以及外接框与标题/说明文字之间使用固定 `20px` 间距，禁止直接拿旋转元素的未变换布局框计算间隔。超宽单列纸贴使用 soft frame 与约 `±0.35deg` 倾角，避免宽度放大视觉斜率。纸贴只用于仍有明确纸张语义的设置和审批，不用于环境、计划、提问、工具卡或普通正文；右侧环境/子代理/计划共用静态 `wc-menu-content` 表面和 `wc-menu-item` 交互，不创建三张独立卡。三块顶层区域用稍强的 `1px` 灰线和额外留白分组；环境区内部的状态、变更、建分支与提交入口仍使用更淡且更内收的细线，不能让内部行误读成第四个顶层区域。提问表单直接复用 `wc-composer` 外壳与 `wc-menu-item` 条目视觉，不创建第二张卡、Portal 或 DropdownMenu 关闭生命周期；宽屏两列，窄屏单列，选项编号和长文案都必须安全换行。全局采用 DeepSeek Harness 的系统字体栈，代码字体栈不得以裸 `monospace` 收尾；`body` 与 Tailwind 公共 token 只提供 `14/22`、`13/20`、`12/18`、`11/14px` 四档界面文字，组件不得再声明 9～13.5px 的近似层级。用户消息、原位编辑与 Worktree 准备态首条消息共用 `wc-user-message-copy` 的 `16/24px`；模型 Markdown 共用 `wc-conversation-copy` 的 `16/28px`；主输入同样使用 `16/24px`。模型 Markdown 的一级至三级标题为 `24/34`、`22/32`、`20/30px`，四至六级标题为 `16/28px`；表格为 `15/25px`，行内代码为 `14/22px`，代码块为 `13/22px`，标题内代码继承标题。根块、首尾、标题、列表项和分隔线的纵向节奏由同一 CSS 边界统一，Streamdown 自带字号和间距不得泄漏成偶然跳变。所有枚举/下拉/锚点选择共用 Radix 浮层基线：约 `15px` 圆角、`1px` 微边框、无投影阴影，纸白表面使用 `80%` 不透明度与仅在浮层存在时生效的轻量背景模糊；应用与设置页的侧栏、主面板壳层边界复用同一圆角 token，设置页进入和返回使用对称的轻量淡入淡出。设置与输入框内的触发器复用同一边框和悬浮状态，禁止原生 `select` 或为锚点选择弹出居中模态框。以上 token 只在 `styles.css` 定义一次，组件通过 `wc-type-control/caption/tiny`、`wc-paper-frame`、`wc-paper-section`、`wc-paper-pad/compact-pad`、`wc-paper-grid/stack`、`wc-menu-content`、`wc-select/context-trigger` 与 `wc-shell-panel` 复用。
- **响应式边界**：窄窗口优先自动隐藏右侧任务栏，保留用户主动展开的左侧会话栏；输入框以容器宽度而非整屏宽度判定紧凑态，空间不足时权限与协商只保留图标，模型名称始终可见，用户输入字号不变。该适配只改变 Renderer 布局，不改变任务计划、Workspace 或权限事实。
- **上下文圆环**：已建立 Main 会话且 Core 有有效窗口估算时，模型控件与发送按钮之间显示 16 px 圆环；悬停/键盘聚焦给出“上下文已用 N%”，点击在输入框上方展示约计总量、模型窗口、System/工具/对话消息三项构成及自动压缩阈值。若最终无工具正文提交后才越过阈值，当前没有待发送模型请求，也就没有溢出风险；圆环明确显示“下次模型请求前自动压缩”，下一次用户输入或同 turn 工具续步进入统一请求前检查，不在 idle 状态额外调用摘要模型。圆环与明细条对 0～100% 封顶，模型切换尚未完成重建时隐藏；面板支持再次点击、点外部和 Escape 关闭。组件不引入新依赖、持续动画或第二套上下文状态。
- **时间线细节**：恢复历史时不再显示短暂的“正在验证附件并恢复对话”占位；现有加载状态在内部完成。根消息提交至首个可见模型事件、以及工具结束至下一可见事件的空窗期，由 Renderer 从现有 `AgentStatus + Block[] + workStartedAt` 纯派生显示 Heart Wave 与“正在思考”；运行中工具、流式思考/正文、审批等待和停止过程不重复显示。曲线按指定公式一次生成 481 点路径，以 `loop=3s` 的单段连续 SVG 描边沿路径流动，不再堆叠离散粒子；`pulse=5.6s` 只做同公式幅度的 CSS 呼吸。动画服从 `prefers-reduced-motion`，不增加 Canvas、逐帧 JS、Core/IPC/JSONL 状态或计时轮询。回滚和压缩等发生在下一条用户消息之前的独立 notice 先切为 standalone section，再建立下一轮 completed/active work section，因而通知位于用户气泡上方，不进入其“已处理”折叠过程。
- **会话定位轨**：宽窗口在中央时间线左侧固定保留 `4.75rem` 槽位，其中靠外的 `2.75rem` 是横向指针/滚轮热区；纵向命中只接受实际落在最近锚点 `12px` 按钮高度内的坐标，不能把整条轨道强制钳制到首末锚点。正文与 Composer 保持引入右侧平衡前的既有左边界，仅把右边界内收 `2.75rem`，按可见热区而非整条左槽做视觉平衡，不增加会改变 Flex 中心的右侧占位节点。每条用户输入投影为一个稳定锚点。相邻刻度使用轻微长短/粗细差，上下两端淡出，指针附近按连续二次曲线形成波峰。波峰只改变长度，所有非命中刻度保持统一灰色，只有精确命中的单个锚点变黑；指针离轨或纵向不在任一锚点上时波峰、预览与颜色选中均为空。普通指针移动实时切换有界纯文本标题与完成回答摘要；活动轮次不截取尚未稳定的正文。只有指针位于轨道热区且真实命中一个可见锚点时，轨道才接管滚轮并平移刻度窗口；期间冻结滚动前的绝对波峰与语义预览，停止后波形回到当前指针，但预览必须等待下一次真实指针移动才切换。点击或滚动轨道后，该会话内的手动刻度窗口保持不变，正文区域的滚轮只推进正文阅读位置，不能再反向驱动轨道窗口居中；切换会话自然重建该瞬时状态。点击锚点与会话位置恢复共用同一完成段物化、实测固有高度和 `content-visibility` 保活事务：先释放上一次保活，物化目标及其之前的完成段，再从目标段起按当前布局逐段确认真实内容已覆盖待定位视口；这一步不以可能仍包含旧宽度固有高度的全局 `scrollHeight` 提前退出。随后只设置一次 `scrollTop`，其余段写回实测固有高度并恢复离屏优化，目标工作段保持真实布局直到离开视口或会话切换。这样侧栏宽度造成的正文重排不会让用户输入漂入回答正文；不能增加平滑动画、内容类型特判、延时重试或二次补偿滚动。轨道最多渲染 42 个刻度加一格 overscan；当前阅读段以工作段 DOM 锚点二分定位，仅在命中段内识别少量用户插话。每个条目只持有截断后的 72/150 字符纯文本，活动 token/tool 增量由时间线比较边界挡住；指针和滚轮事件最多每动画帧提交一次，没有常驻动画循环、Markdown 预渲染或跨会话缓存。视口宽度不超过 `1280px` 时定位轨与右侧视觉内收一起取消，既有侧栏、任务栏、Composer 与滚动位置记忆不变。
- **长时间线性能与 Renderer 恢复**：`conversation-state` 对未变化 Block 保持对象身份，这是 Renderer 的渲染契约；`ConversationView` 和块级视图以该身份为边界，只让当前脏尾、活动工具或确实改变的交互状态重渲染。Renderer 对正文、推理、同一工具进度及同一讨论 Agent 正文这四类高频追加流使用同一 `ConversationEventBuffer`：严格相邻片段复用 Core 的唯一合并规则，最多等待一个动画帧后一次提交，时间采用最后一个有效事件时间；非相邻待提交项另有 128 项硬上限，后台窗口暂停动画帧也不会无限积累。任意步骤提交/丢弃、工具起止、完成、停止或其它语义边界都会连同此前片段立即保序提交，会话快照替换则取消旧 Runtime 尚未显示的帧。这样避免一个 token 触发一次 React 状态复制、section 投影与 Markdown 更新，同时不改变停止保留、步骤事务、折叠或恢复语义。未提交的活动正文与已确认的活动最终正文使用 streaming 模式并延后完整数学排版，稳定内容再切回 static；Streamdown 已按顶层 Markdown 块保持稳定渲染，已完成工作段再使用 Chromium 原生 `content-visibility:auto` 与固有高度占位跳过离屏布局/绘制，不另建时间线缓存、自研 Markdown 切分或滚动虚拟器。Electron Main 监听 `render-process-gone` 并记录退出原因；异常退出只安排一次短延迟 reload，必须等 `did-finish-load` 后才重新布防，避免崩溃重载循环，界面继续从既有 Core runtime snapshot/JSONL 投影恢复。该设计吸收 Claude Code 的脏子树/视口跳过和 Codex App 的稳定 turn/单次恢复原则，但不复制其私有实现，也不增加 IPC、JSONL 或会话 schema 状态。
- **会话列表、切换与删除响应**：会话删除继续以根目录外的 durable marker 和单飞 lease 为唯一事务边界；删除当前会话时只在 marker 写稳并提交替代草稿前冻结切换，随后 lease 收窄为仅锁定目标 sessionId，命令、Subagent、scratch、显式 Worktree、managed 目录及会话事实源在 Main 后台按所有权顺序清理。Renderer 用独立 `completed|failed` 删除状态收口目标行；失败保留 delete-only 事实和重试入口，不能重新恢复目标，也不能扩大到 Local 用户目录。会话列表不再为每次刷新打开所有历史 transcript：已加载 Journal 直接提供实时 metadata，未加载项只读取包含 transcript `dev/ino/size/mtime/ctime` 身份且与当前文件精确一致的派生缓存；缓存缺失或失配才完整重建，正式恢复仍执行全部 transcript 与附件校验。列表请求在 Renderer single-flight 合并，切换成功后复用返回的唯一 runtime snapshot，只并行刷新小型模型目录。可见 `tool-progress/tool-end` 在 Core、持久 ViewEvent 与 IPC 投影共用 64 KiB 尾部上限，完整模型上下文和命令日志仍由原事实源持有。`work-finished` 先结束工作段，权威 `agent-status: idle|error` 再校正侧栏运行态；最终正文从 streaming 切 static 时先提交状态与轻量正文，完整 Markdown/TeX 在空闲阶段用低优先级更新，历史静态正文首次打开仍直接渲染。
- **Markdown 数学公式**：所有模型与恢复历史共用唯一 `MarkdownContent` 和精确锁定的 Streamdown 官方 `@streamdown/math`，由其成熟的 remark-math、rehype-katex 与 KaTeX 链路处理 `$...$`、`$$...$$`；显式启用单美元行内公式，代码围栏仍由 Markdown 语法优先保护。当前可变正文不加载数学插件，避免流式半截公式反复重排；步骤提交后已不可变的过程正文可排版，最终正文只在工作正常 `completed` 后排版，`stopped` 保持原始 TeX，防止未闭合公式静态解析为空。真实 transcript 已证明模型常见的 `$$内容$$` 与 `$$\\begin{aligned}` 行首写法不满足 remark-math 的块级围栏语法：定稿路径因此先做一次幂等的分隔符规范化，只把行首 0–3 空格内、同行或跨行闭合的双美元块改成独立开闭行；段落内部双美元、反引号或波浪线代码围栏保持原样，之后仍只由官方数学插件解析。插件对象保持稳定身份并进入块级渲染缓存比较；KaTeX 样式和字体由生产构建打包，块级长公式仅在自身范围横向滚动。横向滚动需要纵向裁剪，KaTeX 数学盒又不计入中文回退字体的少量墨迹外沿，因此滚动区以等量缩减默认外边距的方式加入上下安全内边距，既不截断分式中文，也不改变公式整体纵向节奏。该能力不改 System、Provider、Core/IPC/JSONL 或会话 schema，也不复制 deepseek-harness 的定制 TeX 解析器，不增加模型特判或旧内容兼容路径。
- **消息动作、来源与最新根重发**：用户气泡悬停统一显示发送时间和复制；只有时间线中最后一条用户消息、且它已获得根任务首个 turn 身份并处于空闲时，才额外显示编辑。编辑框在原位发送，Core 原子追加 rollback snapshot 与替换 `user-input`，活动 messages、TaskPlanState、Skill/附件投递和协商累计状态恢复到旧任务首个 turn 起点；旧分支继续留在 append-only JSONL 审计中，但 `user-message-edited` 会让 Renderer 原位替换根消息并截去其后输出。协商重跑必须复用同一个新 input ID，禁止再生成第二条根输入。运行中只显示时间/复制；完整 `completed` 回答悬停显示完成时间、复制和分支图标，图标只锚定该回答自己的持久 Fork 边界；停止、半截输出、纯工具完成和同一步文本+工具均不冒充完整回答。Slash 的“在新对话中继续”复用最新同类边界；进入子会话后，只有非空 `forkOrigin.sourceTurnId` 与复制终点的 `work-finished.forkTurnId` 精确匹配，才在该终点下方显示一次“从聊天中继续”分隔线，两个缺失 ID 不构成匹配。实时事件用宿主 `occurredAt`，恢复事件用既有 JSONL entry `timestamp` 生成同序 `viewEventTimestamps`；它们只属于 Main/Renderer 投影，不写入 ViewEvent/JSONL schema。Markdown 表格保留原位滚动和复制等控件，但关闭无收益的 fullscreen 入口。网页引用按**最终交付物**判断：只有调研、搜索、资料汇总或事实比较需要在关键结论句末写 `[来源](实际URL)`，并把去重后的纯链接列表放在回答末尾 `### 来源`；正文每个引用 URL 必须在末尾列表原样出现一次。联网若只是执行、修改代码或生成产物前的中间查证，则不输出正文引用和来源列表。Web 工具共用一条 `web-source` 契约，并在不可信网页结果之后再次提醒，不按模型或供应商分支。Renderer 共用单一 `MarkdownContent`：普通链接保持原样，严格的纯外链列表从 HAST 提取标题与 URL 后渲染为左对齐、紧密换行的自然宽度胶囊流；item 与胶囊同步限制为最大 `22rem`，避免长标题的未截断固有宽度留下不可见占位。正文 `[来源](URL)` 始终是回答内导航，不触发外部打开；它在所属工作段内跨 Markdown block 精确定位相同 URL 的胶囊，滚动并高亮 3 秒。类型图标固定 `0.82rem`；点击胶囊只打开锚定在原位的 Radix 菜单，完整标题、域名、打开来源与复制链接均在菜单内，只有“打开来源”会触发外部导航。前端不重排普通模型正文，也不为旧回答合成缺失来源。Streamdown 的二次链接遮罩关闭，所有外部打开仍以 Main 的无凭据 HTTP(S) 校验为唯一安全边界。
- **设置与 Worktree 动作**：连接设置是侧栏进入的全屏分类页；“模型连接”只维护统一连接，“辅助模型”和“协商模型”分别用相同圆角 Radix 菜单选择满足能力要求的连接 ID，后两者没有 key/Base URL 表单。原有保存/加密/刷新逻辑不变。所有枚举选择共用圆角 Radix 菜单；MCP 卡片、认证子区和诊断区统一使用 `min-width: 0`、安全内边距及长字符串换行，不能溢出手绘纸贴。Renderer 的 Worktree IPC 只支持读取状态和创建 Git 分支；状态读取由会话事实事件与窗口聚焦触发并丢弃过期响应，界面不暴露手动刷新入口。“提交或推送”明确把审查/提交/按需推送请求放入输入框，由用户确认后仍走正常 Agent、权限和工具链；不伪造直接 Git 按钮或新增第二条执行通道。
- **Markdown CJK 强调语法**：所有模型、实时流和恢复历史继续共用唯一 `MarkdownContent` 与 Streamdown 解析链。精确锁定的官方 `@streamdown/cjk` 在 streaming/static 两条路径都替换强调、斜体与删除线的分隔符语法，使中文引号、括号、全角标点及中英文相邻边界按 CJK 规则配对；代码、链接和其它 Markdown 节点仍由同一 AST 边界保护。插件配置保持稳定对象身份并进入既有块缓存比较；实现不预处理或改写原文，不增加正则修补、第二套 Markdown 解析器、System/模型约束、Provider 分支、Core/IPC/JSONL/schema 或旧内容兼容路径。
- **Markdown 元素覆盖与文档元数据**：`MarkdownContent` 覆盖 Streamdown 元素时必须通过统一适配层保留上游 class、`data-streamdown` 和未完成节点语义；普通无序列表与链接不得因来源展示丢失圆点、缩进或可识别样式。普通列表以 `wc-markdown-list` 为唯一视觉钩子，按嵌套层级统一使用实心圆、空心圆、方块，三级以后保持方块；只有 HAST 严格判定为每项恰好一个外链的列表进入来源胶囊。完整定稿正文把 `remark-frontmatter` 追加到 Streamdown 导出的完整 `defaultRemarkPlugins` 值列表，不能用单一自定义数组替换 GFM 与代码元数据插件；这样开头 YAML 元数据不会被误解为 Setext 标题，规范表格仍保持原生渲染。可变正文继续使用上游 streaming 默认插件，不在半截文档上启用 frontmatter 扩展。正文中的普通分隔线、表格、代码、公式、CJK 插件和来源行为仍由同一解析链处理，不增加原文正则改写、第二解析器或内容/模型/Provider 特判。

- **用户消息原位编辑视觉**：最新根消息进入编辑态时继续复用 `wc-user-message-bubble`，透明无边框的 textarea 与取消/发送操作属于同一个灰色气泡；焦点反馈只作用于气泡外边界，不再嵌套第二张白色输入卡。输入区不提供手动拉伸柄，内容高度从原 `4rem` 自动增长至 `2.5×`，超过 `10rem` 后固定高度并启用内部纵向滚动。编辑资格、提交、取消、键盘与重发协议均沿用既有实现，不增加 Renderer 状态或协议字段。

### 5.15 通用 Subagent（代码完成，待客户端验收；`core/src/subagents/`、`desktop/main/subagent-*`）

- **所有权与持久化**：普通 Main 的 `Subagent` 只负责创建稳定子代理 ID，`SendSubagentMessage` 只继续同一父会话拥有且已结束的 ID；父工具行保持普通工具展示，不把子代理伪装成用户会话。每个子代理在 `sessions/{parentSessionId}/subagents/{subagentId}/` 下保存严格 manifest 和独立 append-only `transcript.jsonl`，内容只包含委派输入、子代理自身过程与输出；临时文件位于 `scratch/{parentSessionId}/subagents/{subagentId}/`。最终交付仍写父会话项目/交付目录。子代理与父 transcript 不并列成可恢复用户会话，也不进入用户会话列表。
- **激活与并发**：每次启动或继续都从磁盘冷建一个 `AgentSession`，不设置固定模型步骤上限，由完整最终正文、循环保护、模型输出边界、错误或取消结束后立即释放；同一稳定 ID 可由后续工具再次冷恢复，但同一 ID 不能并发激活。每个父会话最多同时保留 8 个“准备中或运行中”激活，准备阶段也先占位，防止并发调用越过上限；该配额独立于 `SessionRuntimeRegistry` 的 8 个用户会话运行名额，不设置隐蔽的全局子代理上限。子代理作为父运行体的 external work 保持父 Journal 与状态存活，但不会被统计为另一个用户会话。
- **定义与工具画像**：内置 `explore` 仅有文件/网页/图片/Skill 只读工具，`reviewer` 在其上增加 `RunCommand`，`general` 再增加专用文件写入、删除和移动；三者都有独立计划工具。用户定义来自 `$HOME/.whycode/agents/*.md`，项目定义来自 `<project>/.whycode/agents/*.md`，严格 frontmatter 为 `name/description/profile/tools?`，文件名必须等于小写连字符 name。单文件 64 KiB、每根 128 项/2 MiB，拒绝符号链接、无效 UTF-8、YAML alias、未知画像和未审计工具；`tools` 只能从固定子代理白名单增加能力。创建时冻结定义、模型、推理档位和权限快照，源文件后改只影响新 ID。
- **调度与提示职责**：Main 只把边界明确、可独立并行或需要大量调查的工作委派出去，互不依赖的委派同一步启动；启动后继续完成不依赖且不重叠的父任务工作，没有此类工作时才等待终态。委派必须自包含目标、已知事实、范围、禁区、交付证据和验收边界；子代理直接交付结论、证据、验证与风险，父代理负责必要核验、综合和最终用户答复，不能在依赖结果到达前猜测或宣布完成。
- **权限与角色隔离**：子代理继承父会话当前 permission mode、已批准目录和会话级允许规则，再加入自己的 scratch；定义只能通过固定画像收窄或从审计白名单选择物理工具，不能扩大父权限。审批仍走父会话既有统一入口，写副作用继续进入同项目宿主 FIFO 与检查点链。首版物理移除 `AskUserQuestion`、Subagent 嵌套、Fork/主会话控制、后台命令、MCP、Office 与截图；切换会话不停止，父 Stop/删除/退出会取消准备中和运行中的子代理，拒绝其待审批并等待卸载。Fork 只保留来源 transcript 中已提交的父工具事实，不继承子代理 owner、控制权或活动运行体。
- **终态与计划**：运行时而非模型生成每次 activation 的 `completed|error|aborted|limit|refusal` settlement，持久化为 pending 后向父会话注入有界 `<subagent-settlement>` 内部消息；父步骤写稳后才标 delivered，模型忘记汇报、空输出或异常也不会丢终态。父计划只在与委派时同一 engaged plan 的激活或待投递 settlement 存在时沿用后台 continuation 语义，通知续轮自然结束后再按既有规则收尾。子代理使用完全独立的 TaskPlanState，不能修改父计划。
- **Renderer 与开销**：`TaskInspector` 在计划卡下展示非纸贴的子代理摘要卡，运行态和终态按同一有界状态投影；Header 入口打开约 380 px 右侧栏，列表按运行/终态分组，点击子代理后才读取并订阅其只读实时 transcript。关闭面板保留当前选择，`X` 清空选择，`+` 仅为预留入口；切换父会话清空跨 owner 选择。Main/Renderer 常驻只保留有界摘要和最多 8 个非当前父会话快照，完整事件不复制进 Header 或主会话，只有当前选中的子 transcript 进入 Renderer。

## 6. CoreEvent 协议（接口与数据流约定）

**单一事实源：`packages/core/src/events.ts`**（含完整注释），本节只列清单，改协议必须同步该文件与此清单。全部 JSON-safe、只增不改语义。

- core → 宿主事件：`turn-start / step-committed / step-output-retained / step-discarded / final-response-started / text-delta / thinking-delta / thinking-end / tool-start / tool-progress / tool-end / image-viewed（ViewImage/CaptureScreenshot/RenderOffice 的 toolUseId+图片元数据）/ approval-request（单项为 reason+diff+suggestion；同一步批量时另带精确 items[]）/ user-question / turn-end / work-started（live-only）/ work-finished（durationMs + completed|stopped，可恢复）/ context-usage（live-only，当前 Main 用量或 null）/ agent-status（宠物接口消费）/ error`；宿主即时显示根输入使用 live-only `user-message-accepted（带可选稳定 inputId、图片/PDF 与 Skill 摘要）`；最新根重发实时投影使用 `user-message-edited（previousTurnId+inputId+text+taskPlan）`，持久化重放从 JSONL 编辑关系派生；steering：`message-queued / message-injected（均可带附件、Skill 摘要与 startsTurn）/ queue-restored（保留原消息 items）`；检查点：`checkpoint-created / checkpoint-restored（可携带恢复后的 taskPlan/question）/ checkpoint-disabled`；任务计划：`task-plan-updated / task-plan-restored`；压缩：`context-compacted`；附件协商降级：`consensus-skipped(reason=image-input|pdf-input)`
- 宿主 → core 命令：`user-message（urgent、attachments、pdfAttachments、restoredInputIds、Skill locator 可选；图片支持 path/inline/stored，PDF 只支持 path/stored；stored 与恢复 Skill 都只能和事实源中选定的 restored 输入身份匹配；正文与附件都可 root/普通 steering/urgent steering）/ edit-user-message（turnId+text）/ approval-response（approved+remember）/ abort / set-model / set-permission-mode / restore-checkpoint / compact`
- M3 增补协商事件（`negotiation-round / candidate / vote / decision`）；candidate 除摘要外可携带完整方案、证据和风险，scratch 路径不进入 UI 事件。结构对齐协议文档 §7。
- 会话可见事件白名单与 Zod 契约在 `core/src/session/view-events.ts`；审批、运行态、live-only `work-started`、`context-usage` 和 `user-message-accepted` 不进入 ViewEvent。输入队列不是第二份 UI 快照，而由 `user-input / user-input-restored / deliveredInputIds / turn-start.rootInputId / snapshot.pendingUserInputs` 事实重建；根消息由 `user-input.startsTurn` 重建，delivery-ack steering 在原交付位置补成可见消息，防止崩溃窗口丢显示或重复。编辑后的根输入通过 `user-input.replacesTurnId` 和其直接父 `rollback` 快照派生 `user-message-edited`，不另存同义 ViewEvent；首个可见 turn、无后续用户输入和空闲状态分别由 Core 持久边界与宿主运行闸门验证。稳定控制事件 `consensus-skipped / work-finished` 立即写入，`image-viewed / checkpoint-created / task-plan-updated / user-question` 随所属稳定 step 提交；`checkpoint-restored` 携带失效工具 ID 以及文件+对话回滚后的计划/问题绑定。任何新增可恢复 UI 事件都必须同步更新该契约与重建测试。
- **Renderer 侧约束**：运行时值只能从浏览器安全子路径（当前包括 `@whycode/core/events`、`/permissions`、`/pdf-limits`、`/image-limits`）导入；根入口只可 `import type`，否则会把 Node 内置模块拖进渲染端（白屏事故 #2）。`/pdf` 含 Zod schema，不作为 Renderer 常量入口。
