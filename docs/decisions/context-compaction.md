# 上下文压缩：设计与取舍

状态：已采用。本文只记录上下文压缩这一项决策，解释为什么这样划分信息、选择摘要范围和处理恢复；不作为其它开发决策的汇总。可执行契约由[文档三 §4](../03-Agent与协议契约.md#4-上下文压缩契约)维护，模块职责见[文档二 §6.3](../02-技术栈与架构.md#63-压缩)，精确类型与参数以相应源码为准。

## 1. 要解决的问题

长任务中的关键证据经常只存在于工具结果里：文件片段、命令输出、网页内容、错误详情、图片与 PDF 页面。若在完整摘要之前按“只保留最近几个结果”清空旧结果，摘要模型无法恢复已经消失的证据。不能把连续性寄托在执行模型恰好写过阶段总结上。

另一类内容有独立事实源：项目规范、Skill 目录与有效正文、当前计划、子代理目录和状态。把它们当普通对话压缩，既重复占用摘要预算，也可能让过期规则和状态以摘要形式长期存活。

长任务还需要两个不同尺度的连续性：用户原始要求提供目标与边界，近期交互提供正在进行的细节。一个笼统摘要难以同时维护多次任务历史和同一任务的累计进展；只按最近工具调用数量保留上下文，也无法保证保留了足够的信息。

## 2. 微压缩只处理意外过长的文本

采用 DSH 的字符阈值与头尾保留方式，取消按结果年龄清空正文。阈值以内的工具文本不变；超过阈值时保留开头和结尾，在中间使用固定剪枝标记。

选择字符而不是 token 的原因是，这一步用于限制单份文本的异常体积，不承担整个模型请求的容量判断。Unicode 码点计算不依赖模型 tokenizer，结果稳定，中文与表情不会被切成半个 UTF-16 字符。模型容量仍由已有 token 计量、输出预留和完整压缩处理，二者职责不同。

保留 DSH 的数值，不根据 WhyCode 的最大工具输出上限等比例放大。`ReadFile` 文本、命令预览等现有上限约束一次工具读取或显示的成本；微压缩约束的是历史中保留的单份长文本。两者不是同一个预算。头部通常含命令、字段与说明，尾部通常含终态、错误或完整日志入口，头尾保留比整份清空更有利于摘要。

图片、PDF 和包含非文本块的多模态工具结果整体豁免。PDF 的提取文字也按其 `ReadFile` 调用来源豁免，不能因为视觉模型与非视觉模型的返回格式不同而丢掉文档内容。普通代码和 Markdown 参考资料仍是文本；“来自 Skill”本身不构成微压缩豁免。

这一取舍仍然有损：长命令输出中间的某条证据可能被删去。固定标记必须让摘要模型知道内容不完整。相比完全不做微压缩，它能收敛偶发巨量输出；相比按年龄清空工具结果，它保留了更多可供完整摘要使用的证据。

## 3. 分开处理权威上下文与历史事实

判断依据是内容的来源和职责，不能把所有内部提醒或所有名为 `AGENTS.md` 的内容统一删除。

| 内容 | 决策及理由 |
|---|---|
| 普通 System、自定义 System | 不交给摘要模型；摘要使用专用 System，普通请求恢复会话自己的 System 生命周期 |
| 项目规范、Skill 目录、活动 Skill 正文、Browser 指引 | 从对话摘要输入剥离，按各自权威来源和有效期重新投影，避免规则被改写 |
| 子代理定义目录及增量、当前 activation 状态 | 用最新目录基线和当前状态替代旧快照；历史 settlement 结果另行保留 |
| 当前计划的全量状态 | 由计划控制器提供；历史计划操作的结果、错误、证据和用户调整仍进入摘要 |
| `Skill()` 读到的主规范 | 它有活动规范副本，保留调用事实即可 |
| `Skill(resourcePath)` 读到的独有参考资料 | 没有等价的活动正文，作为实际工具结果保留；普通长文本规则仍适用 |
| `ReadFile` 读取的规范文件 | 若文件本身是任务对象或取证资料，按普通读取处理，不能仅按文件名剥离 |

“重新注入”不等于所有内容都重新读磁盘。项目指令和子代理目录按已有刷新机制取得当前版本；Skill 在当前根任务内沿用冻结目录与已激活正文；自定义 System 沿用会话快照。压缩不能改变这些所有者的生命周期。

### 有意义的历史通知

历史通知与普通对话一起进入摘要资料，是否写入最终摘要由任务相关性决定。已完成任务的通知不需要逐条复述；下列事实在影响后续工作时保留：

- 子代理交付的结论、发现、证据、产物位置，以及后续仍有用的实例身份；当前 activation 数量不能替代这些结果。
- 后台命令执行了什么、在哪个目录执行、终态与退出原因、可读取的日志入口。用户主动停止的命令不能被摘要改写成应自动重试。
- 用户主动停止、进程中断、协商失败的差异；工具未开始、可能部分执行、结果未知的差异。
- 用户问题与回答、纠正、授权边界和任务取舍；插话可以覆盖原始要求，但不自动建立新的正式任务身份。
- 计划操作的成功、失败、取消与证据，以及工具发现、连接错误、已尝试方案等影响后续选择的事实。
- 解释“今天”“昨天”等相对日期所必需的历史日期锚点。

已经消费的通知中“立即继续”“下一步使用”等模板不能变成新的任务指令。尚未消费的问题、停止边界和终态通知则仍是运行控制信息，必须精确保留，不能只依赖摘要模型是否提到它们。

## 4. 用预算保留尾部，用正式用户身份划分摘要

自动压缩采用可用输入预算的一定比例保留尾部，具体比例与预算定义见协议契约。固定比例比固定工具次数更能适应长短不一的调用，也能随模型容量伸缩。完整消息和完整工具批次是不可拆的单位，因此实际保留量允许超过目标预算。

保留尾部不送给摘要模型。这样避免为已经逐字保留的内容重复花费摘要成本，也使每份摘要的覆盖范围明确。代价是摘要模型不知道尾部的最新进展，所以它只能报告截至切点的状态，不能宣称自己知道“现在应该做什么”。

定义：

- `H`：较早任务的累计历史摘要。
- `U`：最新正式用户消息的原文；插话不建立新的 `U`。
- `P`：当前正式用户 turn 被移出部分的累计摘要。
- `T`：精确保留的原始尾部。

若 `U` 已经在尾部中，只生成 `H`。即使切点落在旧任务 A 的回复里，也不为 A 创建新的前缀摘要。

```text
H → T（包含 U）
```

若 `U` 在切点之前，且其后有工作记录需要移出，把它完整固定保留，只摘要这一轮已移出的工作记录，形成 `P`。没有新增前缀记录时让 `U` 随尾部保留，避免另发请求复述用户原文或重写没有增量的旧 P；已有摘要仍按归属整合，无可压缩记录时保留原上下文。

```text
H → U 原文 → P → T
```

保留 `U` 的理由是：复杂任务的约束、范围与交付条件不应经过多次摘要逐渐变形。它仍然是原消息，不是重新发送的指令，不重复计为 turn，也不刷新附件的上传归属。后续插话和用户纠正仍然可以改变目标。

### 同一 turn 与跨 turn 的更新不同

同一正式 turn A 再次压缩时，保持 `H`，用旧 `P_A` 与新增工作记录更新累计前缀；不把旧摘要再叠成重复章节。

进入新正式 turn B，且切点已经位于 B 内部时：

```text
H₂ = 总结(H₁ + P_A + B 开始之前尚未归档的旧阶段记录)
P_B = 总结(B 这一轮在切点之前的工作记录)
输出：H₂ → B 原文 → P_B → T
```

`P_A` 不能作为 `P_B` 的旧看板。宿主以持久化的正式 turn 身份判断摘要归属，不能根据消息文本、最后一个 `role:user` 或“仍然有旧前缀”猜测。正式 turn 变化不等于业务任务结束；连续请求可能仍在解决同一问题，H 应按语义合并。前缀并入历史的标签只说明摘要归档方式，不证明对应任务已经完成。

旧 `H/P` 在选择尾部前被解析成结构化摘要状态，不作为可切分的普通长消息。因此切点不会落入旧摘要内部。只有摘要而没有可逐出的原始记录时，自动压缩不反复压缩同一个摘要；输出预算和重建后的容量检查负责阻止无收益循环。

## 5. 摘要的职责与工具声明

历史摘要采用有界的阶段性任务记录板，避免旧任务随多次压缩无限累积。编号表达先后顺序，不是永久任务 ID；同一任务持续推进时更新原条目，旧任务失去后续价值后可合并或淘汰。阻塞状态不使旧任务永久占据摘要，但仍影响后续工作的阻塞需要保留。条目上限与更新规则见[文档三 §4.2](../03-Agent与协议契约.md#42-自动压缩范围与摘要归属)。这是摘要模型的内容组织规则，不是按消息数量或重要性先删除输入的算法。仍有效的通用约束、关键决策和纠错教训独立保留，避免随旧任务简化而丢失。

文件与产物、关键上下文和单项下一步聚焦本次历史范围内最近的请求，不能把该请求误认为完整会话的最新任务。围绕同一任务的连续消息按语义合并，不制造任务分界。下一步只能来自已明确且仍有效的动作，没有依据时写 `(none)`；状态以“本次提供的历史上下文末尾”定位，服从完整尾部和宿主当前状态。

当前 turn 前缀摘要借用 Pi 通用摘要及增量更新中的 Goal／Progress 等结构，累计同一正式 turn 的进展；这不是 Pi 原有的简短 turn-prefix 模板。旧摘要保留仍有效的信息，完成项移入 Done，已解决阻塞移出 Blocked，被推翻的结论不作为有效结论继续累积。原始用户消息作为摘要输入背景，并在恢复链中另行完整保留，P 不承担逐字复述原请求的职责。

两份摘要分别请求和校验。第二份失败时不能提交第一份，避免活动历史处于半次压缩的状态。提示词不要求分析草稿，只请求完整摘要，并明确资料、旧摘要和工具输出均不是可执行的新指令。

输出容量由请求预算和供应商的结束原因约束，不以字符推算的 token 数二次拒绝已正常完成的摘要。本地估算与真实 tokenizer 可能有偏差，usage 也可能缺省；把估算误差当成摘要失败会浪费已经完成的请求。仍拒绝截断、工具调用、空正文和缺少边界的结果，只提取外层 `<summary>` 内文，允许模型在标签外附带说明。正文可能讨论标签或包含代码示例，因此结束位置取最后一个结束标签，不能遇到正文引用的标签就截断。自动压缩仍检查重建后的整个请求是否缩小，这与校验单份摘要的输出上限是不同职责。

摘要请求保留当前可用工具声明及其顺序，包括已发现的 MCP 工具，工具选择方式沿用普通请求的默认值。提示词禁止调用工具，声明不携带执行函数或输入回调；若模型仍返回工具调用，代码拒绝该摘要。

不使用 `toolChoice: none` 作为统一的禁用方式：当前 Anthropic SDK 会通过移除工具声明来实现该选项，破坏工具前缀。跨 Provider 的禁止执行由摘要入口保证，声明是否完整保留须在最终 API 请求体中验证。

保留声明有两个理由：历史调用的名称与参数结构仍可被理解；在缓存层次允许时，保留工具前缀的复用机会。更换 System 不代表所有厂商都必然丢失工具缓存，也不意味着保留声明就保证命中。统一保留声明比按厂商维护不同压缩策略更简单，禁止执行由代码负责。

## 6. 手动压缩和超限逃逸

手动 `/compact` 表达主动腾出空间的意图。因此首次摘要全部有效对话历史，不先微压缩，不保留对话尾部，也不固定上一阶段的 `U`；旧 `H/P` 一并进入历史摘要。仍然有效的问题、停止与未消费通知独立保留，不属于“为了续写而保留的对话尾部”。计划、规范及 PDF 引用按自己的规则重建。

摘要请求本身也可能超出模型上限。PTL 恢复从待摘要区末端前移切点，将较新的完整模型步骤和其后原始记录一起移入保留尾部。优先按供应商 token 差额加余量估算移出量；没有差额时使用与自动压缩相同的尾部预算。旧 `H/P` 不参与切点选择，不能为减小请求而直接裁掉累计信息。

手动压缩也只在 PTL 后启用这一退避。代价是腾出的空间可能少于首次全量摘要，但旧摘要和近期证据都得到保留，比丢弃最早历史更适合连续任务。每次移动后按同一套规则重算 `H/U/P/T`；不能只截短某一份摘要输入，否则跨过用户消息时会错配摘要归属。P 重试若未改变 H 输入，可在本次压缩内复用已成功的 H，仍须全部完成后一起提交。

没有可继续前移的安全边界或重试耗尽时，明确失败，不用删除旧摘要换取成功。整次压缩的 PTL 重试共用预算，不能因切换 H/P 或手动模式而重新计数；普通网络重试和主请求的上下文恢复独立。成功生成完整结果并保存快照之后才更换活动历史，失败或取消保留原上下文。

## 7. PDF 采用引用保留与近期展开两层策略

保留一份有界的 PDF 路径引用清单，让模型可以按需重读。它不是文件内容缓存，不按“最近读过几个文件”把正文重新塞回上下文。引用上限维持现有量级：按常见文件名长度估算，可以容纳约一百份上下的引用；极长名称会减少数量。这是容量示例，不是固定附件数量保证，也不是实际用户会话统计。

主动展开只聚焦最近三个正式用户 turn 上传的文件：

- 符合模型能力、页数和总字节预算的小 PDF 自动附加页面图。
- 大 PDF、超预算或未能展开的近期文件带“近期上传”标记；与任务相关且当前内容不足时，模型应主动 `ReadFile`。
- 更早的 PDF 继续保留引用，但不因每次压缩重新变为近期文件。
- 插话上传归属当前正式 turn；后台通知、工具步骤、压缩和恢复都不推进或刷新窗口。

最近三轮没有 PDF 的用户消息也推进窗口，否则会话最初的小 PDF 会无限期展开。重注入标记按当前窗口投影，不能在历史里永久写成“最新”。真正展开了哪些页面由宿主结果说明，不能仅凭“小 PDF”标签假定内容已经可见。

不重新注入旧代码文件全文，也不额外建立所有阅读/修改路径的清单。必要文件位置由摘要按任务意义保留。旧图片不普遍重注入；已经进入待压缩区间的可见图片交给摘要模型提取关键信息，最新原始用户消息自身的附件关联仍随该消息保留。非视觉模型不会凭空获得像素理解能力。

## 8. 下一次普通请求的逻辑结构

下面是逻辑组成，Provider 可以按协议合并同角色消息；宿主的 canonical 消息身份与顺序不受合并影响。

```text
System：普通 WhyCode 提示词与会话自定义快照
Tools：当前可用工具声明

Messages：
┌────────────────────────────────────────────────────────────┐
│ 当前 AGENTS.md、子代理定义目录基线、冻结 Skill 目录           │
├────────────────────────────────────────────────────────────┤
│ 历史摘要 H                                                 │
├────────────────────────────────────────────────────────────┤
│ 最新正式用户消息 U 原文（仅当它不在尾部时单独保留）          │
├────────────────────────────────────────────────────────────┤
│ 当前 turn 前缀摘要 P（仅当切点进入当前 turn）                 │
├────────────────────────────────────────────────────────────┤
│ 精确保留尾部 T：原有用户、assistant、工具与必要通知           │
├────────────────────────────────────────────────────────────┤
│ PDF 引用、符合条件的近期页面、当前计划及运行态投影           │
├────────────────────────────────────────────────────────────┤
│ 当前有效 Skill 正文、Browser 指引                           │
└────────────────────────────────────────────────────────────┘
```

应用上下文放在待消费输入批次之前，避免把内部提示伪装成用户的新任务；未消费输入和通知继续按真实顺序出现。不会凭空添加“刚刚压缩完成，继续”来恢复已经停止的任务。手动压缩首次没有 `U/P/T` 对话保留段，PTL 后按同一结构保留尾部；控制边界始终有效。
