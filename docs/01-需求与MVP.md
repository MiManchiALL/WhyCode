# WhyCode 项目需求与 MVP 范围

> 活文档：边调研、边决定、边开发。已实现模块的详细实现写入架构文档，本文档保持纯净。

## 1. 核心定位

WhyCode 是一款 Windows 优先的通用桌面 Agent（Electron GUI，风格参考 OpenAI Codex 桌面端的简洁风格），尤其擅长代码编写、代码理解、调试及其他编程相关任务，同时正常处理生活、写作、规划、知识问答等通用任务。支持多模型厂商（OpenAI / Anthropic / Google Gemini / DeepSeek / 智谱 / 小米 MiMo），核心特色是**多 Agent 协商决策**：多个平级推理 Agent（Main / B / C）围绕同一问题独立探索、互相投票、达成规则性共识后由 Main 执行（协议见 `E:\Agent\multi-agent-decision-protocol.md`）。

后续将接入桌面宠物（E:\vising，WPF 应用）：宠物动作实时反映 WhyCode 工作状态、拖文件到宠物即发送给 WhyCode。需在事件协议层预留接口。

## 3. 已实现能力基线与后续方向

### 工具体系完善（2026-07-11 完成，2026-07-13 验收收口）

目标：在不牺牲权限、检查点、会话恢复和多模型一致性的前提下，让 WhyCode 同时具备可靠的软件开发工具与通用 Agent 输入能力。

已采用的实现顺序：

1. **最小运行时基础**：为控制面、网络访问补一等语义，非只读工具至少在会话内串行执行；允许多个运行体共享同一根目录前再升级为工作区级串行。权限、检查点 `prepare → execute → finalize` 与回滚不得并发交错；先解决现有任务工具借用 `kind=read`、多个写调用可能并发的问题，不提前建设完整插件框架。
2. **首批：主动提问**：Main 增加 `AskUserQuestion`，一次支持 1～6 个必要问题，每题含短标题、2～4 个建议选项和自由输入；仅当回答会实质改变下一步且没有安全默认值，或独立新复杂任务是否覆盖休眠计划仍不明确时使用，成功后结束当前 turn、持久化 `waiting-user` 并保留活动计划。界面逐题收集，最后一题才把完整批次作为一次回答提交。问题卡答案继续对应上下文，但只有问题本来属于已接合计划的必要等待点且 TaskPlanState 未 interrupted 时才结构化接合；硬中断必须先 Resume。明确恢复或替换不重复确认，普通新消息按最新意图处理。任务已可交付时必须正常完成，可选问题只进最终文本。M1/B/C 不独立向用户提问，避免三方同时阻塞用户。
3. **第二批：编码基本功**：让统一的结构化 `EditFile` 完成单文件或多文件的多次精确替换，补 `DeleteFile/MoveFile`；增强 `Grep/Glob/ListDir` 的路径、上下文、分页和截断语义，并让 `ReadFile` 流式分段读取。
4. **第三批：后台命令生命周期**：长时间进程必须同时具备会话 task ID、增量日志、stdin/EOF、停止进程树、会话切换、重启和应用退出边界；不能只给 RunCommand 增加一个 background 参数。
5. **后续：通用输入与扩展**：图片、PDF、多协议视觉、模型目录、安全密钥、默认工作根、CLIProxyAPI、网页研究、项目指令、文件式自定义 System，以及 MCP 延迟检索、连接页和 Context7/GitHub 主路径均已验收并合并。GitHub OAuth 的代码主通道已完成，但公开发行前还必须注册专用 GitHub App/OAuth App；没有宿主客户端身份时 PAT 是唯一可实际使用的官方远程认证方式。精确 DOM、导航等待、JavaScript 渲染和页面交互属于后续浏览器模块；PDF OCR/全文检索、远程图片 URL、跨会话附件复用、视觉 B/C、LSP/诊断、Notebook 和其它附件仍按真实场景独立推进。

明确不单独造工具：Git status/diff、计算器、当前日期、文件 stat 等优先由现有命令或现有工具字段扩展解决；不为“看起来齐全”增加窄工具。`ApplyPatch` 也不直接照搬 Codex：WhyCode 是多 Provider Agent，需先对当前真实模型做成功率与可恢复性对比。

已实现边界：

- 工具类别包含只负责内部状态或保护性动作的 `control`，任务计划、协议提交和 `StopCommand` 不伪装成文件读取；可继续驱动进程产生副作用的 `WriteCommandInput` 属于 execute。所有工具先独立完成统一权限判定，同一模型步骤的待审批调用再聚合成一张精确清单；审批等待不占用副作用锁。批准后，非只读工具按“最新硬边界重查 → 检查点 → 执行 → finalize”串行，已放行的只读工具仍可并发。Local 多对话在宿主层把同项目 edit/execute 与检查点恢复纳入跨会话 FIFO；Main 的长驻后台进程可由显式 Worktree 获得目录隔离。Subagent 复用同一父会话权限与宿主副作用队列，拥有独立 owner/transcript/scratch，不创建第二套项目写入或交付通道。
- Main 获得 `AskUserQuestion`：仅当回答会实质改变下一步、信息无法自行查明且没有安全合理默认值，或新复杂任务是否覆盖休眠计划仍不明确时使用；一次提交 1～6 个必要问题，每题有短标题、2～4 个选项与自由输入。Renderer 逐题收集，回车与按钮语义一致，最后一题才原子提交完整回答。成功后以可持久化 `waiting-user` 结束 turn 并保留活动计划；完整问题批次随同一稳定 step 落盘，只有来自已接合计划必要等待点的问题携带 `resumesTaskPlan`，其精确问题卡回答在 TaskPlanState 未 interrupted 时可结构化接合，硬中断仍须先 Resume。替换澄清不再持久化专用绑定，回答后由模型重新判断；明确恢复或替换不得重复弹卡。无活动计划的问题也能在崩溃、重启和文件+对话回滚后恢复。任务已可完整交付时不得弹卡，“是否满意/是否继续/可选后续”只用最终文本表达。整个协商任务期间禁用该工具，M1/B/C 不会分别打断用户。
- RunCommand 是不接受 stdin 的短前台命令：Windows 以 `-NoProfile -NonInteractive` 启动 PowerShell，所有平台都关闭 stdin，需要输入或持续观察时使用 StartCommand。停止与超时会终止完整进程树；Windows 使用系统树终止能力，POSIX 使用独立进程组。界面立即进入“停止中…”，清理结束前禁用重复停止和消息提交。命令副作用不建立文件检查点。
- `Glob/Grep` 优先使用 PATH 中显式解析的 ripgrep，可取消、20 秒超时并在产生结果时按行截断；不存在 rg 时使用有界并发 Node.js 回退。Glob/ListDir/Grep 均支持路径和分页，Grep 增加内容/文件/计数模式、include、大小写、纯文本和上下文；依赖、VCS、构建和常见缓存目录统一排除。
- `ReadFile` 改为按行流式读取，获得所需行后停止，限制 1000 行与单行 2000 字符，拒绝含 NUL 的二进制文件，避免为小片段加载整个大文件；超长单行与网页正文共用 Unicode 安全前缀截断，不在 UTF-16 surrogate pair 中间切开。
- `EditFile` 统一接收 1～50 个跨单文件或多文件的 `{path,oldText,newText,replaceAll?}` 精确替换；全部 `oldText` 都匹配调用开始时的原始文件快照，默认必须唯一，显式 `replaceAll` 才替换所有非重叠命中，重叠/嵌套或依赖前一项新文本的编辑直接拒绝。所有文件完成预检后才写盘，写入异常会恢复本次已尝试文件。`DeleteFile` 一次接受 1～50 个普通文件并在删除前全量预检，`MoveFile` 只移动单个普通文件且拒绝静默覆盖；三个专用工具均声明 `exact-files` 检查点。
- 新增 Main 专属 `StartCommand/ListCommands/GetCommandOutput/WriteCommandInput/StopCommand`：宿主管理器按会话隔离任务并跨 AgentSession 存活。有限长任务默认由 `StartCommand` 等待终态并把进度流回同一工具调用，用户停止 turn 会同步终止进程树；只有显式 `detach=true` 的 server/watch/跨回合 stdin 任务在切换对话后继续。工具返回前原子武装终态通知；若命令已经结束则仍在当前工具结果中交付，避免双重续轮。仍在运行的任务会同时持久化“已交给后台”事实，Header 只展示这类任务的有界摘要：运行项置顶，终态项下沉并沿用每会话最近 16 项规则；完成后自动续轮只用图标区分，不展示内部计划身份。之后自然 completed/failed 时，宿主按 `(sessionId, taskId)` 去重，把有界终态元数据注入所属 Main：运行中在下一稳定步骤边界接续，空闲或已卸载会话在既有并发名额、路由闸门和恢复租约可用后开启隐藏续轮，不切换用户当前对话、不伪造用户气泡、不轮询。只有任务启动时真正 engaged 的计划 ID 才可恢复同一未中断计划；旧、已替换或 interrupted 计划只接收结果而不获得执行权。已武装且尚未投递终态通知的后台任务会保留未完成计划，通知续轮结束时再自然关闭；完整日志仍由 `GetCommandOutput` 按字节偏移读取并限制单任务 8 MiB，绝不进入 Header 快照。用户 `StopCommand` 和应用退出不产生额外续轮，超时作为 failed 通知。正常重启只保留日志和终态，不重放旧完成通知；异常退出遗留的 running 明确恢复为 interrupted，不伪装成可重连进程。删除会话先丢弃待交付通知、停止所属任务再删除日志。M1/B/C 和协议回合物理移除这些工具。
- 前后台命令都可能影响文件、进程、网络或项目外状态，因此不声明 checkpointScope、不扫描工作区，并形成 none 回滚边界；跨过该边界时只能恢复专用工具跟踪且未被后改的文件，不能同时截断对话。具体文件修改必须使用专用文件工具。

本批当时不做跨会话工作区级串行、网络/附件工具、MCP/Skill/Subagent/Fork；这些能力均已在后续独立模块落地，仍共用原有权限、持久化与工具提交边界。

验证：该批次当时以独立 `BatchEdit` 完成全仓 typecheck、93/93 自动化测试和生产 build；ripgrep 与无 rg 回退、读取、批量预检、文件移动/删除、前后台命令中止、stdin、增量日志、会话隔离和重启恢复均有回归，真实 DeepSeek V4 Flash 与 GLM-4.7 也完成了编辑、删除、移动及后台进程往返。2026-08-09 独立 `BatchEdit` 已并入统一 `EditFile`，不再作为模型工具暴露，原子预检和精确回滚能力保留。

未来深入方向（非当前排期）：显式 Worktree 已覆盖 Main 的目录与长驻进程隔离；后续只有出现真实需求时再增加一键 handoff/合并冲突预览、孤儿 Worktree 可视化回收与存储配额。搜索可打包内置 ripgrep，避免终端 PATH 无 rg 时降级；后台命令后续只剩全局任务中心、真正 PTY/终端尺寸与配额等产品化深化。跨重启仍只恢复日志/状态，除非未来有可靠 OS 级进程托管，不承诺危险的 PID 重连。

### Agent Skills P0（2026-08-01～05 客户端已验收并随 Office P1 合并）

目标：让用户和 Main 复用符合开放 Agent Skills 目录结构的任务指令，同时保持 WhyCode 的多模型、权限、队列、持久化和提示缓存边界只有一套。

- 应用发布包内嵌 `code-review/debug/documents/presentations/simplify/skill-creator/spreadsheets/verify`，启动时按内容指纹物化到 `$HOME/.whycode/skills/.system` 并标记为 `system`；指纹未变不重写，变化时只替换这个应用托管目录。用户 Skill 写入 `$HOME/.whycode/skills` 的普通子目录，项目 Skill 仍写入 Git 根到当前目录各层 `.agents/skills`；用户扫描明确跳过 `.system`，同名项不被内置项覆盖。`skill-creator` 带检查清单，三套 Office Skill 各带 builder API 与格式专属交付质量清单，并都通过同一 `Skill` 资源路径按需读取。
- 五个通用内置项保持单一职责和短正文：description 前置“做什么、何时使用、关键边界”；`code-review` 按 upstream/本地引用选择真实 merge base，并以明确准入条件和 P0～P3 只报本次引入的可行动缺陷，`debug` 用最小复现和可证伪假设追首个错误状态，`simplify` 只清理当前任务目标并保持接口行为，`skill-creator` 默认指令优先且只生成 WhyCode 支持的元数据，`verify` 以直接行为和相关反例给出 PASS/FAIL/PARTIAL。不得照搬其它宿主专用 frontmatter、动态注入或子代理流程。
- 每个根任务重新枚举磁盘；未变化文件按文件身份、`mtime+ctime+size` 复用同时受 20,000 项与 32 MiB 双上限约束的解析结果，当前任务正文快照另有 32 MiB 总上限并按发现优先级稳定截断。显式 `/` 选择在第一条模型请求前解析为完整快照；隐式使用只把有界元数据目录交给模型，由 `Skill {skillId,resourcePath?}` 渐进读取。相同名称不覆盖，身份由精确 ID+路径决定。
- 生命周期属于“当前根任务”，不是会话：运行中 steering 可增加 Skill，压缩后仍精确重投影；任务结束后活动正文和当前资源结果退出，下一根任务重新选择/调用。排队、恢复、重提、重启和可编辑中止回合均由当前 schema v11 沿用的 `user-input.skills` 保存完整快照，不从变化后的磁盘重建历史语义；开发期 v10 及更早会话不迁移。
- 缓存红线：System 与工具定义不因 Skill 内容变化而重建；稳定目录提醒位于项目指令之后的缓存前缀，目录未变化时 revision 和字节保持稳定；活动正文只附加在当前请求尾部。Skill 工具正文不进入摘要，历史结果冻结为占位，压缩后由当前任务快照重新注入；token usage 基线显式校正投影差值，活动正文自身超过模型预算时在请求前结束该任务，不向 Provider 发送超限请求。
- P0 只给正常 Main 与最终执行阶段。Skill 本身不授予权限，脚本仍须由既有命令工具执行并经过原权限/审批/检查点边界；M1、B/C、discussion 和协议输出没有 Skill 目录、正文或工具。pending managed/Worktree 尚无真实执行目录时展示用户级与内置 Skill，首条消息物化后该根任务才增加真实目录的项目级项。

### Office 制品 P1（2026-08-05 完成客户端验收并合并）

目标：把“模型偶尔能用命令拼出 Office 文件”收敛成多 Provider 共用、可复现、可结构验证、可视觉复核和可回滚的正式能力，而不是限制只有视觉模型才能生成。

- 所有普通 Main 模型都获得 `BuildOfficeArtifact` 与 `InspectOffice`。前者在一次性 Utility Process 的 SES Compartment 中执行函数，注入经能力收窄的 docx、PptxGenJS、ExcelJS、JSZip、fast-xml-parser 和显式 assets；没有 Node 全局、import/require、进程或环境路径能力。输出仍采用 `exact-files` 检查点、同目录临时文件、flush、原子替换与发布前后 SHA-256 校验。
- `InspectOffice` 支持 `content/objects/styles/relationships/validation/template/formula-trace`。对象视图覆盖 DOCX 段落、表格、节、图形、页眉页脚、批注/脚注，PPTX shape/group/图片/图表/表格/备注，XLSX 单元格、名称、表、绘图、批注、验证、条件格式和工作表设置；locator 精确到 OOXML part 与对象/单元格。`template` 专门给出 DOCX 物理段落的格式/locator 和 PPTX 每个源页的 layout、shape、文字/媒体槽、边界与字体指标；PPTX 媒体还给出关系 target、资源类型、SHA-256、字节数、活动页复用次数、裁剪、父组与组成员，避免按截图猜布局或把源主题媒体误当装饰。XLSX 可按 sheet/range 定位并追踪普通、共享公式与定义名称依赖；`startUnit` 是当前视图的结构单元索引，不是工作表行号，只有返回的 `nextUnit` 可作为下一页起点。检查预算为单表最多 100,000 个非空单元格、整簿最多 200,000 个、共享字符串 200,000 个、定义名称 20,000 个，超限明确返回 `too-large`，不以 OOM 或截断结果冒充完整检查。
- 只有当前模型画像 `supportsImageInput=true` 时才动态增加 `RenderOffice`。它必须独占模型步骤；`view=pages` 每次最多 4 页，负责文字、裁切和对象细节，`view=overview` 每次最多 50 页并合成单张总览，负责模板选页和整套页序、角色、构图轮廓、视觉密度与节奏。后台转换成临时 PDF 后复用现有 PDF.js/Canvas/Sharp，图片沿原工具调用进入模型和会话事务。模型仍须用 pages 遍历全部最终页面，修改后重新执行结构与视觉检查；overview 不能代替逐页 QA。非视觉模型不隐藏生成/处理能力，也不把结构检查冒充视觉检查。
- `ViewImage` 继续负责项目内普通 PNG/JPEG/WebP 的导入、裁剪与像素映射；`CaptureScreenshot` 只负责真实桌面/窗口/区域。Office QA 不走任何桌面截图或外部查看器，因此无需删除或改变这两个既有工具。
- 继续限制源文件 100 MB、构建脚本 512 KB、最多 32 个 assets（单个 50 MB、总计 150 MB），拒绝加密、ZIP64、多磁盘、不安全路径、宏载荷和格式伪装；全部 XML/关系部件都会解压并验证。Content Types、关系 owner/target、DOCX 书签/批注/修订/脚注/编号/样式引用、PPT slide/shape ID 与 chart axis、XLSX sheet/style/table/range/drawing 均有格式专属校验。XLSX 样式计数只枚举 `cellXfs` 的直接 `xf` 子节点，工作表已知节点按 SpreadsheetML 顺序校验，避免自闭合样式误计数或生成 Excel 无法打开的非法节点序列。确定性版式问题作为可分页警告返回，最终视觉仍以 RenderOffice 为准。
- 构建调用必须显式选择 `mode=create|template`；模板模式把原件作为 asset 并用 `templateAssetKey` 唯一指向它，create 模式禁止携带模板 key。DOCX/PPTX 优先用注入的 `OfficeTemplate` 复制原包/源页并按已检查 locator 编辑。PPTX 每个输出页的每个 slide-level 媒体对象必须恰好由一个 `keep|image|delete` 动作覆盖：图片替换只改克隆页关系并保留原框位置、尺寸、裁切和层级，delete 可删除单个 shape 或整个 group 并移除该页不再引用的关系，keep 只允许 `brand|decoration`；所有媒体动作记录 `reason`。最终文件（XLSX 是真实重算后的最终文件）再次与模板比较：Word 样式/编号/设置/页眉页脚/媒体、PPT master/layout/theme/media、XLSX styles/theme/chart/drawing/pivot 共享部件必须原样保留；DOCX 表格/分节/图形锚点和 PPTX 同 layout 源页对象有序子集血缘不成立就停止发布，因而可删除源内容对象但仍拒绝新增、重排或空白重建。
- 含公式 XLSX 在构建后先用独立隐藏 Microsoft Excel `CalculateFullRebuild` 并等待完成；Windows 不可用时回退带独立 profile 的 LibreOffice 打开另存。重算结果重新进入 Utility Process 做完整检查，只有公式数量保持一致、`formulaUncalculatedCount=0`、`formulaErrorCount=0` 才原子发布，并返回实际引擎证据。ExcelJS `result` 仍只是输入缓存，不作为重算证明；外部工作簿链接因安全边界禁用更新，检测到时停止发布而不宣称其来源数据已刷新。
- Windows 渲染优先探测 LibreOffice headless；不存在时使用 `cscript //B` 的 late-bound Microsoft Office 隐藏实例，禁止宏、提示、事件和链接更新，Word/PowerPoint/Excel 均以无窗口方式导出 PDF。转换有 120 秒上限；只有确认新自动化 PID 后才配置和打开文件，成功、失败、取消和超时均按 PID、进程名与命令行定向清理并确认退出，不附着或主动终止用户已有实例。系统没有可用后台渲染器时，结构链仍正常，视觉工具返回清楚的 renderer-unavailable 错误。
- 三项内置 Skill 固化只读/创建/模板编辑/验收路由；任何创建或修改先读取对应 builder API 与质量清单，PPTX 模板任务另读 `template-following.md`，再完成内容研究和结构/叙事/数据模型。PPTX 先以 overview 盘点全部源页的叙事角色、构图轮廓、视觉密度、编辑槽和媒体槽，再把输出页映射到同类 sourceSlide；不能把结束/章节页当封面或正文，也不能反复选择少数纯文字页规避内容视觉。输入资料中的相关图表、界面和图片优先导出/裁切成显式 assets；模板只提供视觉系统，不充当新内容素材库。DOCX/PPTX 当前仍是单计划对象→bytes，不存在可变模板链式 API；沙箱在调用 ExcelJS 等受控库时保持注入 asset 的 `Uint8Array` 类型，`workbook.xlsx.load(assets.template.bytes)` 是真实可执行接口。每个任务只维护一个 builder；接口或构建错误继续修正同一 builder，禁止改用命令或普通文件工具手写、打包或覆盖最终 OOXML。最终依次完成结构检查、源/成品 overview 对照、媒体身份核对和 pages 全页细查。默认只交付用户请求的 Office 文件，不把 builder、总览图或检查中间文件当成交付物。
- 本轮不新增会话 schema 或旧对话分支。P0 输入输出以项目路径或现有授权目录为边界；Office composer 附件、聊天内制品预览、跨平台自带 LibreOffice、Visio、实时 Word/PowerPoint/Excel 控制和第二视觉模型调度都留给独立需求。

### M5 Main 长任务控制（2026-08-11 渐进式计划协议收口）

目标：让复杂任务能够持续执行、跨压缩与重启恢复，并以可验证进度而不是固定调用次数判断是否完成。

已定范围：

- 仅普通 Main 与协商后的 Main 执行阶段拥有正式计划；M1/B/C 仍只负责有界分析和协议输出。Main 执行不设固定总步数上限，协议/讨论回合保留 40 步边界。
- `TaskPlanState` 是单一持久状态，只包含版本、至多一个完整 `activePlan`、`resumeRequired` 和中断原因，不保存历史计划。执行上下文由它与当前 runLoop 共同推导：无活动计划为 none；硬中断后 `resumeRequired=true` 为 interrupted；本轮计划工具稳定授予执行权，或回答未 interrupted 的计划绑定问题后为 engaged；其余有活动计划的情况为 dormant。生命周期状态与本轮执行权不得混为一谈。
- 复杂任务先定向扫描关键文件，形成整体宏观认知，再用 `CreateTaskPlan` 建立 3～7 个结果导向的里程碑。每项只保存 `outcome`，不写实现步骤、验收小字或终态总结；最后一项必须是唯一 verification。详细子步骤属于进入当前项后的即时执行信息，不进入计划状态，也不要求模型逐条输出。
- 普通 Main 只注册 `CreateTaskPlan / ResumeTaskPlan / UpdateTaskItem / CloseTaskPlan`。Create 后所有里程碑均为 `pending`；开始某项时先用 Update 将其显式置为 `in_progress`，再重新读取相关代码、确认当下实现细节并直接实施。Update 的模型参数只有可选 `changes[]` 与顶层 `item_id/status/evidence`；`changes` 原子添加、删除、修改或重排里程碑，顶层状态只允许 `in_progress|completed`。状态设置通用幂等：精确重放成功但不增加 revision、TaskPlanState version 或界面事件；结构无变化仍返回 `no_state_change`，非法跳转仍 fail-closed。一个 `in_progress` 里程碑可跨多个文件、命令和模型步骤持续推进，completed 必须附真实且之后不可改写的 evidence；结构和状态全部校验成功后才整体提交。
- 切换独立复杂目标时，用户明确放弃后先调用无参数 Close；在后续稳定 step 重新扫描新目标关键文件，再 Create 新计划，不提供 Replace 或隐式原子切换。仅提出另一个目标不等于授权放弃当前计划，语义不明确时仍由 AskUserQuestion 确认。Create、Resume、Close 都必须独占完整模型 step，取消、异常或丢弃不会产生幽灵计划或幽灵恢复。
- 同一时间至多一项 `in_progress`；完成或删除当前项不会自动启动下一项，继续执行时必须显式把选定里程碑置为 `in_progress`。正常最终正文在同一稳定 step 由会话协议自动把全项完成计划记为 `completed`、其余记为 `ended` 并清空 active；Close 只用于显式放弃/切换，不接收参数或总结。最终对话正文是交付总结的唯一来源。简单问答和一步操作不创建计划。
- 内置 System 只保存稳定行为规则，不拼接计划 ID、进度或执行态；可选自定义 System 也只使用会话起点固化的同一快照。动态完整 `TaskPlanState` 通过内部 `<system-reminder>`、任务工具结果和压缩应用上下文进入消息链；新的顶层 Turn 在真实用户消息之前写 interrupted/dormant 执行边界，真实用户消息仍是最后一条指令。每次模型请求发送完整活动消息历史，不再从最近中断处切片，模型可正确解析“之前的蔚蓝”等跨边界指代。
- 用户停止或进程中断以 `<whycode-turn-aborted>` 结束旧 runLoop；只有当时确实 engaged 的活动计划才持久化 `resumeRequired` 与原因，之后必须对匹配计划调用 Resume，dormant 临时问答不会误伤旧计划。共识失败/取消原子回滚到任务起点的 messages+TaskPlanState 并保留中断边界。普通新 Turn 只进入 dormant；用户自然语言要求暂缓时直接结束当前 execution run 并保留计划，不使用独立 Pause 工具，也不改变计划生命周期。
- engaged 期间未硬停止而到达的 mid-turn 消息作为真实 user steering 在步骤间注入：模型先遵循技术纠正、约束、提醒或临时提问，再继续原任务；用户明确要求暂缓时才自然结束为 dormant。代码不识别暂停关键词；steering 的决策窗口通常由下一模型步骤消费，但仅调用 `UpdateTaskItem` 保存进度时跨步保留到最终文本，其它工具仍表示继续实质处理。urgent 打断只丢弃未提交 step，稳定事实和计划状态不回滚。
- engaged 计划连续 10 个完整 assistant step 没有计划变更时注入一次中性进度提醒；它只要求在确有进度或任务项变化时更新，不制造进度，也不增加 TaskPlanState version。模型完整给出无工具最终正文时自然结束计划，并在同一稳定 step 追加一次 canonical `active_plan:null` 状态边界；后续普通 Turn 不重复追加。用户停止、AskUserQuestion 等待和已登记后台终态唤醒保留计划；后台结果回到同一逻辑任务后，最终正文再自然结束。重复工具循环和传输无活动仍安全暂停并保留计划。
- 压缩、重启、Fork、文件+对话回滚和共识事务都原子保存/恢复完整 `TaskPlanState`。完整压缩只要会话曾产生计划状态（`version>0`）就重注入当前 canonical 状态，包括 `active_plan:null`；从未建立计划的普通会话不注入空状态。自动压缩只在同一 engaged run 中写入绑定 turn/plan 的 continuation；硬中断状态不能被摘要变成自动续跑。恢复旧复杂目标时必须依据当前代码重新扫描并创建新计划，不能复活旧任务项或旧执行权。
- UI 只显示当前活动计划，或最近关闭计划的终态快照：完成比例、单行里程碑、状态图标和最终验证标识。计划卡不重复显示计划目标，也不显示阻塞原因、验收小字、状态说明行、关闭总结或历史计划折叠区；实时事件与重启恢复共用同一状态投影。

M5 本期当时不做：后台守护/定时唤醒、多 Agent 并行领任务、任务 DAG/owner、Plan/Act 用户模式、跨会话全局任务板、Skill/Subagent/Fork、附件和界面整体重设计。Agent Skills P0、会话 Fork 与通用 Subagent 后续均已独立落地；它们只复用计划的自然完成与 continuation 语义，不把各自状态塞回 Main 的 TaskPlanState。

原 M5 验证（2026-07-13）：全仓 190/190 自动化测试通过（Core 166、Desktop 24），全仓 typecheck 与生产 build 通过。2026-08-11 渐进式计划协议升级为 session schema v9，旧 v8 及更早开发会话不迁移；当前验证结果记录在 `04-START-HERE.md` 与 `05-暂存区便签.md`。

未来深入方向（非当前排期）：证据指向已提交工具事件、交替调用/重复错误等语义无进展检测、显式 UI 恢复、用户直接调整当前计划和更长的多 Provider 压力测试。Subagent 已使用父会话 owner、宿主中止和终态通知边界；若以后出现交付合并需求，再单独设计冲突预览，不扩张当前运行协议。

### 用户可见会话完整恢复（2026-07-10 验收合并）

目标：用户恢复历史会话后，界面应像始终在同一个窗口中连续对话，而不是只显示“恢复了多少条模型上下文”。

已定范围：

- 同一份 append-only JSONL 同时保存模型上下文事实和经 Zod 校验的用户可见事件；不增加第二份界面快照，也不迁移或推断旧会话。
- 恢复用户消息、Main 正文与推理、工具卡、M1/B/C 候选、紫色评审卡、投票、协商决定、提示和错误；内部 system/protocol 提示、审批弹窗和运行中状态不进入恢复时间线。
- Main/B/C 的文本、推理和工具流按 step 分通道缓冲，只有稳定提交后才写入；urgent 打断或异常的半截 step 全部丢弃。用户硬停止是唯一窄例外：仅把已经展示的 assistant 正文写稳，推理、工具、问题卡和计划状态仍丢弃，避免重启后出现永远“运行中”的工具卡。
- 模型压缩只改变活动模型消息链，不裁剪用户可见时间线；文件+对话回滚通过重放 `checkpoint-restored` 截断对应 turn。资源 manifest 与 `checkpoint-created` 可见事件持久化后，恢复会话仍显示有效回滚按钮；已回滚的按钮由失效列表清除。
- Renderer 的实时事件与历史恢复共用同一纯状态投影，避免两套显示逻辑逐渐不一致。
- Renderer 页面本身不再被视为运行态所有者：开发热更新或 Renderer 崩溃重建时，从 Electron Main 重新取得当前会话稳定时间线、模型/项目、真实 busy 状态和待审批请求；初始化期间按事件序号接续快照之后的新事件，避免重复或覆盖。运行中的未提交 step 不伪造进历史，但恢复“停止”入口。

### M4 会话持久化与安全恢复（2026-07-10 验收通过）

目标：让单机桌面会话在正常退出或进程崩溃后可列出、恢复并安全继续，为长时任务、回放和后续会话管理提供事实源。

已定范围：

- `userData/sessions/` 下每会话一份 append-only JSONL；每条记录带版本、UUID、`parentUuid`、时间戳和 Zod 校验后的结构化载荷。
- JSONL 是事实源；轻量 metadata 仅用于列表，损坏或缺失时可从 transcript 重建，不引入 SQLite。
- 用户输入在模型请求前提交；assistant/tool 消息只在完整 step 结束后提交；压缩或对话回滚追加新根快照，不原地改写历史。
- 重启只恢复最后一条有效 JSONL 记录；坏尾行不拖垮整会话。未完成 turn 标记为中断，**不得自动重放工具、审批或命令**。
- UI 提供新建、列表、恢复、删除；不同项目会话隔离。持久化内容不含 Provider API key。
- full_consensus 半轮中断不续算；任务起点保存“执行前稳定状态”，任务终点原子提交 `sessionScore`、B/C `memory_summary`、`taskLog`，失败/取消回滚任务内模型上下文。
- 先用 Node 内置测试能力建立存储/恢复/权限/协商回归，不为测试新增 npm 依赖。

本模块当时不做：SQLite/远程同步、Provider 原始流 trace、工具副作用重放、Fork UI、MCP、通用 Subagent runtime、后台 worker。跨重启文件回滚、Fork、MCP 与 Subagent 已由后续独立模块补齐，并继续以主会话 JSONL 和各自从属事实源保持所有权边界。

验收：重启可恢复最后完整 step；尾部半写可恢复；压缩后链正确；中断工具不重放；会话增删与项目隔离正确；类型检查、构建、存储测试及 M3 回归全部通过；新增代码职责清晰、可测试，超过约 300 行/50 行的审查触发线时有合理内聚理由，不向现有大文件无节制堆逻辑。

实现结果：

- `core/src/session/` 已落地版本化 JSONL schema、父链重建、原子 metadata 缓存、串行 journal、坏尾行容错、结构损坏拒绝、压缩/回滚/恢复新根以及项目隔离删除。

### 持久化资源检查点（2026-07-10 验收合并）

- 回滚事实源是 `sessions/{sessionId}/checkpoints/manifests/` 下的版本化资源清单；精确文件内容放会话级内容寻址 blob，不使用项目级共享快照。
- WriteFile/EditFile/DeleteFile/MoveFile 的精确路径不经过 `.gitignore` 或排除表，覆盖项目外、敏感文件、二进制和“原本不存在”的状态；移动同时覆盖源和目标。Agent 新建且未被用户再改的文件回滚时会删除，并只清理本次新建且仍为空的父目录。
- 项目外写入经用户单次批准后，只对当前工具调用扩展路径权限并正常建立精确检查点；只有用户勾选“记住”才进入会话授权。Main 会看到用户主目录，具体文件创建/修改必须优先使用 WriteFile/EditFile，不用 RunCommand 绕过授权。
- RunCommand 与后台命令不扫描项目、不建立文件检查点；命令 prompt 和稳定 System 均明确副作用不可回滚。前台执行关闭 stdin，Windows PowerShell 使用非交互模式；提示型命令快速失败并由模型修正，需要输入则改用后台命令工具。成功但没有 stdout 时明确显示“命令成功，无标准输出”。
- 每个可回滚写工具必须声明 `exact-files` checkpointScope。未声明或建点失败的写操作形成 `none` 边界；跨边界仍可“仅文件”恢复明确路径并执行 after 冲突检测，但禁止“文件+对话”，且命令副作用原样保留。之后新建的精确检查点可独立恢复。
- 恢复只捕获 manifest 中的明确路径并比较 Agent 操作后的预期状态；发现用户/其他会话后改即拒绝覆盖。通过后按 manifest 逆序恢复并校验最终状态；任一步或会话日志提交失败，补偿回恢复前状态。只有资源和对话都提交成功才截断 UI/模型上下文并使后续按钮失效。
- 同一 turn 的每个完整工具检查点仍作为精确恢复事实持久化，但 Renderer 只在本轮最早的有效检查点显示“回滚本轮”；后续工具不重复显示入口。每个 turn 独立派生一个入口，检查点失效后自动消失，实时事件与重放结果一致。
- 回滚确认后全局交互态立即显示“本轮回滚中…”，状态随 runtime snapshot 跨 Renderer 重载恢复，完成或失败都可靠清除。恢复事务不可取消，因此不显示无效停止按钮；新建/恢复/删除会话和切项目会明确提示等待回滚完成。
- manifest/blob 完全归属单个会话；删除会话随事实源一并删除，不触碰同项目其它会话或项目文件。应用启动会清理旧版本遗留且已不再使用的共享命令快照目录。
