# CLIProxyAPI 路由审核

仅在用户明确要求新增或改变 CLI 路由时读取。删除指向退役画像的悬空项不需要重做路由审核。

## 定向取得证据

1. 从 `cli-proxy-models.ts` 的来源注释和最近提交定位已审版本。核对当前发布版，以及 `internal/registry/model_updater.go` 指向的官方远程目录提交；优先读取所需文件或仓库 API，普通路由更新不克隆完整仓库。
2. 查找本次精确 ID 在远程目录、内嵌离线目录、Provider/客户端元数据中的定义，以及加载优先级和启动可用性。若已有来源仍有效，只核查本次型号条目和变化涉及的加载逻辑；不能仅因离线目录中不存在就认定官方未支持。
3. 在已有可用凭据范围内，读取目标实例鉴权后的 `/v1/models` 确认实际公布的路由。该接口只证明可用 ID，不证明能力、真实后端身份或当前客户端已启用。
4. 针对该路由核实 OAuth Provider、账号范围、入口协议、推理参数翻译、图片、工具、结构化输出、签名/加密推理回传。已审且未变化的转换链路可复用；新后端、参数变化或多 Provider 共用 ID 时再追踪相关源码，不重审无关厂商。

远程目录与源码均记录提交或发布版。网页缓存与仓库结果矛盾时核对官方仓库 API；本机旧副本不能作为当前路由身份的唯一依据。

静态路由必须由官方目录证明等价，再与实例目录求交集。路由名、成功响应、模型自述或近似 alias 都不能单独证明身份；未知路由不出现在可启用列表。目标实例缺少 ID 时可以交付已充分审核的静态候选，但必须说明其当前不可启用、未完成真实验收。

## 只保存收窄约束

官方画像仍来自 Core。`cli-proxy-models.ts` 只记录路由差异，由现有唯一合成函数计算有效画像：

| 字段 | 合成规则 |
|---|---|
| 身份和官方说明 | 保持官方画像，CLI 不得反向修改 |
| 上下文、最大输出 | 取双方上限较小值 |
| 布尔能力 | `false` 优先；不能开启官方未验证能力 |
| 结构化输出 | 取双方共同保证的最高档位 |
| 推理档位 | 取闭集交集，不能补回路由缺少的档位 |
| 默认档位 | 路由明确默认优先，否则只能沿用交集内的官方默认 |

缺失字段表示未知。仅在同型号身份和对应字段完整透传均已验证时才可继承，否则关闭能力或暂不开放路由。多个 OAuth Provider 共用 ID 且实例无法区分时取安全交集；无法证明交集时拆分可辨识路由或不接入。

名字中的 low/high 不能代替请求体选档；`supported_parameters`、模态和推理档位互不证明，Codex `ultra` 等产品编排模式不属于通用 API 推理强度。路由独立默认值必须显式记录。

不为 CLI 复制完整能力画像，不新增动态远程目录拼装。审核约束固定随 WhyCode 发布；将不直观的限制及来源提交写在对应路由旁，沿用现有目录求交、请求和约束测试。
